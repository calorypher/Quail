# Quail 0.3 Direction

## Status

**Release direction and initial milestone map approved. Source-neutral dependency direction was clarified during M15 QA, M17.5 was added after M16 exposed a separate full build/rebuild performance gap, and M17-S was inserted after M17 triggered its short-query storage stop condition. The dedicated Quail 0.3 execution thread owns evidence-driven planning and adaptation inside the approved 0.3 release boundary.**

This document records the product and architectural direction for Quail 0.3. The current release sequence is M15 through M24 with M17-S acting as a bounded short-query search-structure decision gate before M17 can resume, followed by M17.5 after M17 is resolved. The milestone decomposition may evolve inside the dedicated Quail 0.3 execution thread when implementation or QA evidence justifies it, provided the approved 0.3 release goal and scope boundary remain intact. Detailed implementation prompts are intentionally not stored here; they are prepared from fresh repository state when each milestone starts.

## Release intent

Quail 0.3 should be able to replace Everything for ordinary daily local-file search on the developer's Windows PC.

This is a workflow target, not a feature-parity target. Quail does not need to reproduce Everything's complete syntax, UI, administrative surface, or long tail of options.

The minimum successful daily workflow is:

```text
Windows starts
  -> Quail starts automatically
  -> the filesystem index stays current automatically
  -> the global hotkey summons Quick Search
  -> normal queries feel immediate
  -> useful results rank near the top
  -> Enter opens the intended file or folder
```

When the user needs to inspect or narrow a larger result set:

```text
Quick Search
  -> Full Search
  -> sort / filter / inspect
  -> open, reveal, or copy the path of the selected result
```

## Architectural direction

Quail is intended to become a source-neutral search application in which filesystem is one source rather than the architectural center of the product.

The approved **compile-time dependency direction** is:

```text
Quail.App ---------> Quail.Core
                         ^
                         |
Quail.FileSystem -------+

later:
Quail.Browser ----------+
Quail.Mail -------------+
Quail.Cloud ------------+
Quail.Calendar ---------+
```

`Quail.Core` must not depend on `Quail.FileSystem` or any other concrete source. Core owns only the minimal contracts and orchestration genuinely needed by normal search surfaces. Concrete source modules implement those Core-owned contracts and depend on Core, not the reverse.

At runtime the application may of course orchestrate registered sources through Core:

```text
Quail.App
    -> Quail.Core search orchestration
        -> registered source instances
            -> FileSystem
            -> later Browser / Mail / Cloud / ...
```

This runtime flow must not be confused with a compile-time `Core -> FileSystem` project dependency.

A very small internal contract such as `ISearchSource`, or an equivalent dependency-inversion seam, is explicitly acceptable when it covers demonstrated requirements such as search, Core-level result projection, opaque result actions, and aggregation across registered sources. This does **not** authorize a provider framework.

For 0.3:

- `Quail.Core` becomes the source-neutral application/search core and normal GUI-facing search boundary;
- NTFS/MFT/USN enumeration, filesystem persistence, change tracking, filesystem identity, filesystem ranking/search implementation, and filesystem actions belong to `Quail.FileSystem`;
- the normal App search/coordinator/presentation path must use source-neutral Core contracts and naming rather than file-specific orchestration types;
- Core result semantics must not require every future result to be a file merely because FileSystem is currently the only production source;
- filesystem-specific administration may still have an App frontend, but filesystem implementation/storage/security logic belongs to `Quail.FileSystem`;
- source-native filesystem identity must remain preserved inside the filesystem source rather than being reduced to path identity.

`Quail.App -> Quail.FileSystem` may remain temporarily for static composition and explicitly filesystem-specific administration/UAC paths. Those references should remain isolated so a later move from static composition to optional source loading does not require redesigning Quick Search, Full Search, the search coordinator, presentation pipeline, ranking orchestration, or Core result semantics.

### Long-term physical source optionality

First-party source modules are intended to become physically optional.

The long-term target is that omitting or removing a source assembly such as `Quail.FileSystem.dll` removes only that source's:

- search results;
- source-specific actions;
- indexing/synchronization behavior;
- source-specific settings and administration.

The rest of Quail should still start and normal source-neutral search surfaces should continue to work with whatever other sources are available.

M15 does **not** implement runtime module discovery/loading or require a successful `Quail.FileSystem.dll` deletion test. It must only avoid dependencies that would make physical optionality require another broad search-stack refactor. A later runtime-loading step should primarily replace static composition with optional composition.

Do **not** use this decision to build a public provider SDK, dynamic plugin loader, provider discovery/versioning system, generalized capability matrix, provider lifecycle framework, version negotiation, or universal storage/object database. Broader contracts should still be extracted only after multiple real source implementations demonstrate common requirements.

## Search performance

Performance is a product feature in 0.3, not a cleanup task.

M16 established a repeatable physical-host comparison and showed that normal narrow filename queries are already in the intended immediate perceptual class, while one/two-character queries and broad-result paths remain materially slower. The detailed baseline, targets, and guardrails are canonical in `docs/milestones/M16-results.md`.

M17 then produced a candidate that met every performance target, including roughly 40.9 ms for one-character and 43.4 ms for two-character queries. Post-candidate QA invalidated that result because the short-query optimization selected a bounded `rowid` candidate window before ranking; later exact/prefix candidates could therefore be omitted. The strategy was reverted and permanent correctness regressions were added.

On the correctness-safe existing storage model, a full exact-candidate lookup for a one-character query with no exact match measured about 1.46 seconds on the physical C: index. Existing FTS5 trigram search does not index terms shorter than three characters. The evidence therefore triggers M17's explicit stop condition for a durable short-query structure or material search/storage change.

The M16 short-query target remains unchanged at this decision point. The fact that the current storage model cannot meet it correctly is evidence for a bounded design decision, not by itself evidence that the product target is wrong. M17 remains paused and PR #10 remains blocked until M17-S completes and the Quail 0.3 execution thread records the resulting in-version decision.

Everything remains a practical latency reference, not a requirement to reproduce its internal architecture or default ranking.

## Short-query search structure decision

M17-S is a bounded feasibility/measurement spike inserted because M17 cannot correctly meet the approved 1–2-character latency budget on the existing read/storage path.

The spike should not assume a specific solution. Credible candidates may include a small persistent short-query index, another compact auxiliary lookup structure, a memory-resident structure derived from existing index data, or another bounded approach that preserves literal substring semantics and complete candidate recall before the existing relevance logic is applied.

The decision must consider more than benchmark latency. For each credible option, M17-S should gather enough evidence about:

- representative 1–2-character latency, including no-exact-match cases;
- correctness and candidate recall/relevance;
- database or memory footprint;
- startup/cold-load cost where relevant;
- build/rebuild cost contribution;
- incremental update/maintenance cost;
- consistency/recovery implications;
- implementation and long-term maintenance complexity.

M17-S is not the production implementation milestone. It ends with an explicit decision in the Quail 0.3 execution thread. That thread may amend M17, choose another bounded implementation path, or revise a target/product behavior that remains inside the approved 0.3 release goal and scope boundary. It does not need to return to the parent roadmap thread merely because the milestone structure or technical plan changes.

Return to the parent roadmap thread only if the evidence requires changing the 0.3 release goal or boundary, moving substantial scope between releases, or changing a major cross-version product/architecture direction.

This ordering also protects M17.5. If M17 ultimately adds a durable auxiliary structure, M17.5 should measure rebuild performance on the actual 0.3 search/index shape rather than benchmark a storage design that is immediately made obsolete by short-query work.

## Index build/rebuild performance

M16 comparison work also exposed a distinct lifecycle-performance finding outside the original M16/M17 contract.

On the physical host, Quail currently takes about three minutes to rebuild a filesystem index containing roughly 0.86 million records. A user-owned 30 FPS Everything recording showed its rebuild of roughly 0.93 million indexed objects completing in about 2.6-2.7 seconds. These are not identical datasets or storage models: Quail stores broader metadata and uses SQLite/FTS with its own durability and staging behavior. The comparison therefore does not establish a parity requirement. The magnitude of the gap is nevertheless large enough that 0.3 should understand it before continuous-maintenance and recovery behavior are finalized.

M17.5 remains a bounded investigation, not a production-optimization milestone. It runs only after M17-S has produced an in-version decision and M17 has been resolved, so its baseline reflects the actual search/index structure selected for 0.3. If M17 adds a short-query auxiliary structure, M17.5 must include that structure's build/finalization/storage contribution.

M17.5 should:

- establish a repeatable end-to-end Quail build/rebuild baseline;
- break elapsed time down across MFT/enumeration, metadata acquisition, SQLite base-row writes, FTS/search-index maintenance, any accepted short-query structure, and WAL/checkpoint/finalization;
- measure staging/durability overhead where material;
- determine whether per-row FTS triggers, transaction/bulk-insert behavior, metadata acquisition, serial execution, CPU utilization, or I/O dominate;
- evaluate bounded parallelism or reader/worker/writer pipelines only as measured hypotheses rather than assuming that more threads or concurrent SQLite writers solve the problem;
- record Quail database size, object count, approximate bytes/object, and stabilized memory footprint, plus comparable Everything figures where obtainable and appropriately qualified;
- end with an evidence-based target/range and a recommendation on whether a separate bounded production build/rebuild optimization should be added to 0.3 before M18/M19.

Do not weaken durability/integrity or redesign schema/storage merely for benchmark wins.

If M17.5 recommends a production optimization that remains inside the approved 0.3 release goal and boundary, the Quail 0.3 execution thread may add, split, reorder, or replace the required milestone work and continue. Return to the parent roadmap thread only if the evidence requires changing the release boundary, moving substantial scope between versions, or changing a major cross-version architecture/product direction.

M17.5 follows successful resolution of M17 because full rebuild measurements should describe the real 0.3 search storage design. It still precedes M18 ranking work and, more importantly, M19/M20 making build/rebuild part of the automatic-maintenance and recovery lifecycle.

## Ranking and relevance v2

0.2 introduced a bounded deterministic filesystem ranking model. 0.3 should make ranking useful enough that normal search does not require scanning past large numbers of technically matching but practically irrelevant results.

The next pass should address real observed workflows, including:

- exact/prefix/token/substring text relevance as supported by measured behavior;
- useful user-space versus hidden/internal/system-heavy matches;
- candidate recall before final ranking;
- the known path-aware recall limitation when an over-limit same-text-tier candidate set hides better results;
- stable deterministic ordering;
- representative names with many duplicate or near-duplicate matches.

Avoid fuzzy search, ML ranking, interaction-history learning, recency-learning systems, or a large heuristic framework unless measurements and real queries show that the simpler model cannot meet the product goal.

M18 remains filesystem-specific ranking work. Final heterogeneous/cross-source ranking is not a 0.3 requirement.

## Automatic filesystem maintenance

Manual Refresh/Rebuild is incompatible with the 0.3 daily-use goal.

The healthy filesystem source should maintain its indexes automatically from the existing NTFS/USN foundation. The design must handle correctness lifecycle, not merely watch for changes.

Expected concerns include:

- incremental USN consumption;
- persistent checkpointing;
- catch-up after Quail or Windows restarts;
- sleep/resume behavior where real testing requires explicit handling;
- journal ID/range/continuity validation;
- detection of a state where incremental correctness can no longer be guaranteed;
- safe automatic recovery where simple and reliable;
- explicit rebuild-required state where automatic repair would be unsafe or ambiguous;
- clear filesystem index health/status in the UI.

A Windows Service is a plausible mechanism for privileged/background NTFS work, but its exact contract is not pre-approved. Prefer the smallest privileged boundary that satisfies automatic maintenance and leaves the interactive application unelevated.

Because this boundary can process privileged filesystem operations and protected index state, its security and integrity deserve strong, potentially adversarial, review. That rigor must not be generalized into exhaustive hardening of unrelated low-risk product flows.

## Launch on startup

0.3 should provide a normal settings option to launch Quail with Windows using a straightforward supported Windows mechanism appropriate to the actual deployment model.

Do not turn startup registration into a generalized deployment subsystem.

## Quick Search polish

Quick Search remains the fastest interaction surface and should prioritize perceived immediacy.

Expected polish includes:

- smoother result-list expand/collapse behavior;
- restrained transition animation consistent with the approved UI direction;
- reliable focus and summon/dismiss lifecycle;
- a delayed search/busy indicator only when a query takes long enough for the wait to become perceptible.

A spinner should not flash on normal fast searches. If a delay threshold is required, choose it from practical UX testing rather than treating an illustrative value such as 150-250 ms as a frozen requirement.

## Unified Settings

0.3 should replace the current split ordinary Settings + Index Manager experience with one coherent settings window.

Expected first structure:

```text
Settings
  -> General
      -> Launch at startup
      -> Global hotkey
      -> Theme
  -> Indexing
      -> indexed volumes
      -> health / status
      -> rebuild / recovery actions
      -> useful diagnostics
  -> About
```

In 0.3 the `Indexing` area is filesystem-focused because FileSystem is the only production source. Do not turn this into a general settings-extension framework yet. Preserve a clean enough boundary that a future optional FileSystem module can also make its filesystem-specific settings disappear without breaking ordinary Settings.

Only create sections that contain real 0.3 functionality. Do not add empty Browser, Cloud, Providers, Plugins, or similar pages to reserve future navigation space.

## Full Search v1

The approved mockup direction includes a larger Full Search / Object Explorer surface. 0.3 should implement the first functional filesystem-only version.

Its role is not to become a second Windows Explorer. It should support workflows where Quick Search is too transient or too small for the result set.

Expected capabilities:

- normal persistent resizable window;
- shared Core search semantics and ranking with Quick Search;
- larger scrollable result set;
- name;
- path/context;
- file/folder kind;
- size;
- modified date/time;
- created date/time only if the indexed model can provide it correctly;
- keyboard navigation;
- open;
- open containing folder;
- copy path;
- useful sorting;
- basic filters.

Practical initial filters include file/folder, extension/file type, size range, modified before/after, created before/after when supported correctly, and hidden/system/read-only as advanced filesystem filters where useful.

Prefer compact filter controls/chips/dropdowns over a full visual query builder. Boolean expression construction, grouped AND/OR logic, saved searches, tabs, relationship views, and multi-pane file-manager behavior are outside 0.3.

Quick Search and Full Search should use the same source-neutral internal GUI-to-Core search request/orchestration path. M22 may add structured filesystem fields needed by Full Search, but it must not re-establish filesystem as the mandatory shape of every future Core result.

## Approved milestone map

The release currently uses the following roadmap-level milestone map:

1. **M15 — Core / FileSystem Boundary Extraction** — behavior-preserving extraction of filesystem implementation plus a source-neutral, dependency-inverted Core/source seam; no runtime plugin loading.
2. **M16 — Search Performance Investigation & Target** — repeatable Quail-vs-Everything baseline, profiling, bottleneck identification, and evidence-based interactive-search targets.
3. **M17 — Search Engine Performance** — currently blocked after correctness QA triggered the short-query storage stop condition; resumes after M17-S and an explicit Quail 0.3 execution decision.
4. **M17-S — Short-Query Search Structure Spike** — bounded comparison of correctness-preserving 1–2-character search/storage approaches, including latency, footprint, build/rebuild, and incremental-maintenance consequences; no production implementation before the spike decision is recorded.
5. **M17.5 — Index Build/Rebuild Performance Investigation & Target** — after M17 is resolved, perform phase-level investigation of the minutes-scale rebuild gap, including any accepted short-query structure, and act as a decision gate for production build/rebuild optimization.
6. **M18 — Ranking / Relevance v2** — improve filesystem candidate recall and practical top-N result quality while staying inside the M16/M17 performance budget.
7. **M19 — Continuous Maintenance Boundary Spike** — determine and validate the smallest safe privileged/background architecture for automatic NTFS/USN maintenance.
8. **M20 — Continuous Filesystem Maintenance** — production automatic maintenance, restart catch-up, continuity validation, safe recovery, and filesystem index health.
9. **M21 — Unified Settings & Launch on Startup** — one coherent Settings/Indexing surface plus launch with Windows.
10. **M22 — Full Search v1** — filesystem-only persistent result browser with larger result sets, sorting, filters, and normal result actions over the source-neutral search path.
11. **M23 — Quick Search & UI Polish** — animations, lifecycle/focus polish, delayed busy indication, and visual/keyboard coherence across the 0.3 UI.
12. **M24 — 0.3 Stabilization / Release Candidate** — integrated regression, lab/physical-host verification, Everything-replacement smoke, final performance/relevance/security checks, and release-candidate evidence.

The sequence is intentionally evidence-driven rather than immutable. The Quail 0.3 execution thread may refine, split, add, remove, reorder, or replace milestones when implementation or QA evidence justifies it, provided the release goal and approved scope boundary remain intact.

For the current blocker, M17 is paused rather than silently broadened. M17-S owns the short-query storage decision. After the spike, the Quail 0.3 execution thread records the chosen in-version decision and may amend M17/resume the existing work without a parent-roadmap round trip if the decision remains inside 0.3.

Likewise, if M17.5 recommends a bounded production build/rebuild optimization, the Quail 0.3 execution thread may insert and execute that work before M18/M19 when it remains inside the approved release boundary.

M19 remains before M20 because privileged/background maintenance deserves a bounded feasibility/security decision before production implementation. M22 remains after performance, ranking, maintenance, and settings/index-health work so Full Search is built on the intended 0.3 foundation.

## Engineering proportionality

0.3 must follow the risk-based engineering proportionality rules in `AGENTS.md`.

The following areas deserve unusually strong verification because failure can have high impact or invalidate the core product promise:

- privileged/background filesystem boundary;
- protected index storage and ACL/reparse-point interactions;
- index integrity and checkpoint/change-tracking correctness;
- recovery after loss of incremental continuity;
- measured interactive-search performance;
- short-query candidate recall/relevance when optimizing 1–2-character search;
- measured build/rebuild performance when M17.5 is active;
- ranking regressions against representative real workflows.

Ordinary Settings, launch-on-startup, tray/lifecycle behavior, install/uninstall transitions, and UI animation/polish need solid supported-path testing without combinatorial expansion unless a real high-impact defect appears.

Meeting milestone acceptance criteria is a stopping point. Do not keep adding hardening, migration machinery, provider abstractions, deployment flexibility, or generalized infrastructure after PASS merely because more theoretical cases can be imagined.

## 0.3 non-goals

0.3 is intentionally filesystem-focused. It should not add the following unless a bounded prerequisite is required to achieve the approved release goal:

- browser-history/bookmark source;
- Google Drive, Gmail, OneDrive, calendar, contacts, or other remote/heterogeneous sources;
- file-content indexing;
- full file identity/history product features;
- deleted-item history retention;
- application-provider/launcher expansion as a release goal;
- public/dynamic plugin system;
- runtime source/module discovery/loading as an M15 requirement;
- generalized provider SDK, provider lifecycle, capability matrix, or version negotiation;
- universal source/object storage model;
- full visual query builder or saved searches;
- preview/file-manager operations;
- automatic update installation;
- installer replacement without evidence that the current deployment blocks a 0.3 requirement;
- Linux implementation;
- AI functionality;
- enterprise deployment features without a concrete requirement;
- exhaustive migration compatibility for arbitrary historical development-release installations.

## Relationship to file identity/history

0.3 should preserve the foundations needed for later NTFS identity/history work, especially stable volume/file identity and a reliable change stream. It should not implement full historical retention merely because the data passes through the maintenance pipeline.

The preferred post-0.3 direction is Quail 0.4, focused on filesystem identity/history without turning Quail into a filesystem-forensics product. Expected areas are identity semantics, a minimal history persistence model, rename/move lineage, explicit deletion/history retention semantics, richer Full Search/Object Explorer history/details UX, and release stabilization.

Retention of deleted or historical source data must remain an explicit product/privacy decision rather than an accidental side effect of indexing.

## Relationship to the first heterogeneous source

After the filesystem-focused 0.3 and likely 0.4 work, browser history/bookmarks remain the preferred candidate for Quail 0.5 or the next suitable release.

That release should prove the source-neutral Core contract against a genuinely different source. It should refine broader shared contracts from evidence rather than repair a `Core -> FileSystem` dependency. Physical optionality/runtime source loading may be introduced when it becomes a concrete product or packaging need; the dependency direction established by M15 should make that primarily a composition change.

## Execution boundary

The parent Quail roadmap thread owns release goals, version boundaries, cross-version sequencing, and major product/architecture decisions whose consequences extend beyond the active release.

The dedicated Quail 0.3 execution thread owns the detailed plan and technical decisions needed to deliver the already-approved 0.3 goal. It should:

- read fresh canonical repository state before every milestone or decision gate;
- prepare and approve the active milestone contract from current evidence;
- coordinate Codex implementation, independent QA, and fixes;
- refine, split, add, remove, reorder, or replace milestones when implementation/QA evidence justifies it;
- make bounded technical, storage, performance, maintenance, and architecture decisions inside the approved 0.3 boundary;
- update the 0.3 roadmap and direction documents when the in-version plan changes;
- continue through release-candidate readiness without parent-roadmap approval for ordinary in-version adaptations.

Return to the parent roadmap thread only when evidence requires one of the following:

- changing the Quail 0.3 product goal or release boundary;
- moving substantial scope between 0.3 and another release;
- changing a major cross-version product/architecture direction;
- making a decision that invalidates the established direction of later releases rather than merely changing how 0.3 is implemented.

Milestone restructuring, bounded spikes, implementation-method changes, performance/storage decisions, or new technical work needed to satisfy the existing 0.3 goal do not by themselves require a parent-roadmap round trip.
