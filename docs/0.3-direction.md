# Quail 0.3 Direction

## Status

**Release direction and milestone map approved. Source-neutral dependency direction clarified during M15 QA. Individual implementation milestones are executed in the dedicated Quail 0.3 coordination thread.**

This document records the product and architectural direction for Quail 0.3. The approved release sequence is M15 through M24. Detailed implementation prompts are intentionally not stored here; they are prepared from fresh repository state when each milestone starts.

## Release intent

Quail 0.3 should be able to replace Everything for ordinary daily local-file search on the developer's Windows PC.

This is a workflow target, not a feature-parity target. Quail does not need to reproduce Everything's complete syntax, UI, administrative surface, or long tail of options.

The minimum successful daily workflow is:

```text
Windows starts
  -> Quail starts automatically
  -> the filesystem index stays current automatically
  -> the global hotkey summons Quick Search
  -> normal queries feel immediate
  -> useful results rank near the top
  -> Enter opens the intended file or folder
```

When the user needs to inspect or narrow a larger result set:

```text
Quick Search
  -> Full Search
  -> sort / filter / inspect
  -> open, reveal, or copy the path of the selected result
```

## Architectural direction

Quail is intended to become a source-neutral search application in which filesystem is one source rather than the architectural center of the product.

The approved **compile-time dependency direction** is:

```text
Quail.App ---------> Quail.Core
                         ^
                         |
Quail.FileSystem -------+

later:
Quail.Browser ----------+
Quail.Mail -------------+
Quail.Cloud ------------+
Quail.Calendar ---------+
```

`Quail.Core` must not depend on `Quail.FileSystem` or any other concrete source. Core owns only the minimal contracts and orchestration genuinely needed by normal search surfaces. Concrete source modules implement those Core-owned contracts and depend on Core, not the reverse.

At runtime the application may of course orchestrate registered sources through Core:

```text
Quail.App
    -> Quail.Core search orchestration
        -> registered source instances
            -> FileSystem
            -> later Browser / Mail / Cloud / ...
```

This runtime flow must not be confused with a compile-time `Core -> FileSystem` project dependency.

A very small internal contract such as `ISearchSource`, or an equivalent dependency-inversion seam, is explicitly acceptable when it covers demonstrated requirements such as search, Core-level result projection, opaque result actions, and aggregation across registered sources. This does **not** authorize a provider framework.

For 0.3:

- `Quail.Core` becomes the source-neutral application/search core and normal GUI-facing search boundary;
- NTFS/MFT/USN enumeration, filesystem persistence, change tracking, filesystem identity, filesystem ranking/search implementation, and filesystem actions belong to `Quail.FileSystem`;
- the normal App search/coordinator/presentation path must use source-neutral Core contracts and naming rather than file-specific orchestration types;
- Core result semantics must not require every future result to be a file merely because FileSystem is currently the only production source;
- filesystem-specific administration may still have an App frontend, but filesystem implementation/storage/security logic belongs to `Quail.FileSystem`;
- source-native filesystem identity must remain preserved inside the filesystem source rather than being reduced to path identity.

`Quail.App -> Quail.FileSystem` may remain temporarily for static composition and explicitly filesystem-specific administration/UAC paths. Those references should remain isolated so a later move from static composition to optional source loading does not require redesigning Quick Search, Full Search, the search coordinator, presentation pipeline, ranking orchestration, or Core result semantics.

### Long-term physical source optionality

First-party source modules are intended to become physically optional.

The long-term target is that omitting or removing a source assembly such as `Quail.FileSystem.dll` removes only that source's:

- search results;
- source-specific actions;
- indexing/synchronization behavior;
- source-specific settings and administration.

The rest of Quail should still start and normal source-neutral search surfaces should continue to work with whatever other sources are available.

M15 does **not** implement runtime module discovery/loading or require a successful `Quail.FileSystem.dll` deletion test. It must only avoid dependencies that would make physical optionality require another broad search-stack refactor. A later runtime-loading step should primarily replace static composition with optional composition.

Do **not** use this decision to build a public provider SDK, dynamic plugin loader, provider discovery/versioning system, generalized capability matrix, provider lifecycle framework, version negotiation, or universal storage/object database. Broader contracts should still be extracted only after multiple real source implementations demonstrate common requirements.

## Search performance

Performance is a product feature in 0.3, not a cleanup task.

Before algorithmic changes, establish a repeatable comparison using the same machine, representative indexed corpus, and representative query set. The investigation should include as appropriate:

- cold and warm query behavior;
- one- and two-character queries where supported;
- normal filename queries;
- broad-result queries;
- repeated typing / interactive query changes;
- Quick Search end-to-end latency rather than database-only latency;
- Core/database time versus UI/presentation/icon time where measurements show separation is useful.

Do not choose an arbitrary microbenchmark target before measuring the current gap. Normal search should feel effectively immediate. A visible wait approaching 0.5 seconds is a degraded case, not the normal target experience.

Everything is a practical reference point, not a requirement to reproduce its internal architecture.

## Ranking and relevance v2

0.2 introduced a bounded deterministic filesystem ranking model. 0.3 should make ranking useful enough that normal search does not require scanning past large numbers of technically matching but practically irrelevant results.

The next pass should address real observed workflows, including:

- exact/prefix/token/substring text relevance as supported by measured behavior;
- useful user-space versus hidden/internal/system-heavy matches;
- candidate recall before final ranking;
- the known path-aware recall limitation when an over-limit same-text-tier candidate set hides better results;
- stable deterministic ordering;
- representative names with many duplicate or near-duplicate matches.

Avoid fuzzy search, ML ranking, interaction-history learning, recency-learning systems, or a large heuristic framework unless measurements and real queries show that the simpler model cannot meet the product goal.

M18 remains filesystem-specific ranking work. Final heterogeneous/cross-source ranking is not a 0.3 requirement.

## Automatic filesystem maintenance

Manual Refresh/Rebuild is incompatible with the 0.3 daily-use goal.

The healthy filesystem source should maintain its indexes automatically from the existing NTFS/USN foundation. The design must handle correctness lifecycle, not merely watch for changes.

Expected concerns include:

- incremental USN consumption;
- persistent checkpointing;
- catch-up after Quail or Windows restarts;
- sleep/resume behavior where real testing requires explicit handling;
- journal ID/range/continuity validation;
- detection of a state where incremental correctness can no longer be guaranteed;
- safe automatic recovery where simple and reliable;
- explicit rebuild-required state where automatic repair would be unsafe or ambiguous;
- clear filesystem index health/status in the UI.

A Windows Service is a plausible mechanism for privileged/background NTFS work, but its exact contract is not pre-approved. Prefer the smallest privileged boundary that satisfies automatic maintenance and leaves the interactive application unelevated.

Because this boundary can process privileged filesystem operations and protected index state, its security and integrity deserve strong, potentially adversarial, review. That rigor must not be generalized into exhaustive hardening of unrelated low-risk product flows.

## Launch on startup

0.3 should provide a normal settings option to launch Quail with Windows using a straightforward supported Windows mechanism appropriate to the actual deployment model.

Do not turn startup registration into a generalized deployment subsystem.

## Quick Search polish

Quick Search remains the fastest interaction surface and should prioritize perceived immediacy.

Expected polish includes:

- smoother result-list expand/collapse behavior;
- restrained transition animation consistent with the approved UI direction;
- reliable focus and summon/dismiss lifecycle;
- a delayed search/busy indicator only when a query takes long enough for the wait to become perceptible.

A spinner should not flash on normal fast searches. If a delay threshold is required, choose it from practical UX testing rather than treating an illustrative value such as 150-250 ms as a frozen requirement.

## Unified Settings

0.3 should replace the current split ordinary Settings + Index Manager experience with one coherent settings window.

Expected first structure:

```text
Settings
  -> General
      -> Launch at startup
      -> Global hotkey
      -> Theme
  -> Indexing
      -> indexed volumes
      -> health / status
      -> rebuild / recovery actions
      -> useful diagnostics
  -> About
```

In 0.3 the `Indexing` area is filesystem-focused because FileSystem is the only production source. Do not turn this into a general settings-extension framework yet. Preserve a clean enough boundary that a future optional FileSystem module can also make its filesystem-specific settings disappear without breaking ordinary Settings.

Only create sections that contain real 0.3 functionality. Do not add empty Browser, Cloud, Providers, Plugins, or similar pages to reserve future navigation space.

## Full Search v1

The approved mockup direction includes a larger Full Search / Object Explorer surface. 0.3 should implement the first functional filesystem-only version.

Its role is not to become a second Windows Explorer. It should support workflows where Quick Search is too transient or too small for the result set.

Expected capabilities:

- normal persistent resizable window;
- shared Core search semantics and ranking with Quick Search;
- larger scrollable result set;
- name;
- path/context;
- file/folder kind;
- size;
- modified date/time;
- created date/time only if the indexed model can provide it correctly;
- keyboard navigation;
- open;
- open containing folder;
- copy path;
- useful sorting;
- basic filters.

Practical initial filters include file/folder, extension/file type, size range, modified before/after, created before/after when supported correctly, and hidden/system/read-only as advanced filesystem filters where useful.

Prefer compact filter controls/chips/dropdowns over a full visual query builder. Boolean expression construction, grouped AND/OR logic, saved searches, tabs, relationship views, and multi-pane file-manager behavior are outside 0.3.

Quick Search and Full Search should use the same source-neutral internal GUI-to-Core search request/orchestration path. M22 may add structured filesystem fields needed by Full Search, but it must not re-establish filesystem as the mandatory shape of every future Core result.

## Approved milestone map

The release is split into the following roadmap-level milestones:

1. **M15 — Core / FileSystem Boundary Extraction** — behavior-preserving extraction of filesystem implementation plus a source-neutral, dependency-inverted Core/source seam; no runtime plugin loading.
2. **M16 — Search Performance Investigation & Target** — repeatable Quail-vs-Everything baseline, profiling, bottleneck identification, and evidence-based performance targets.
3. **M17 — Search Engine Performance** — implement the smallest changes justified by M16 to make normal search effectively immediate.
4. **M18 — Ranking / Relevance v2** — improve filesystem candidate recall and practical top-N result quality while staying inside the performance budget.
5. **M19 — Continuous Maintenance Boundary Spike** — determine and validate the smallest safe privileged/background architecture for automatic NTFS/USN maintenance.
6. **M20 — Continuous Filesystem Maintenance** — production automatic maintenance, restart catch-up, continuity validation, safe recovery, and filesystem index health.
7. **M21 — Unified Settings & Launch on Startup** — one coherent Settings/Indexing surface plus launch with Windows.
8. **M22 — Full Search v1** — filesystem-only persistent result browser with larger result sets, sorting, filters, and normal result actions over the source-neutral search path.
9. **M23 — Quick Search & UI Polish** — animations, lifecycle/focus polish, delayed busy indication, and visual/keyboard coherence across the 0.3 UI.
10. **M24 — 0.3 Stabilization / Release Candidate** — integrated regression, lab/physical-host verification, Everything-replacement smoke, final performance/relevance/security checks, and release-candidate evidence.

The sequence remains intentionally mostly linear. The M15 dependency clarification does not add another milestone or change the 0.3 release boundary.

M16 precedes search-engine optimization so changes are measurement-driven. M19 precedes M20 because privileged/background maintenance deserves a bounded feasibility/security decision before production implementation. M22 remains after performance, ranking, maintenance, and settings/index-health work so Full Search is built on the intended 0.3 foundation.

The roadmap may be revised if an earlier milestone produces evidence that invalidates a later milestone's assumptions. Such a change is a roadmap decision; it must not be silently improvised inside an implementation milestone.

`ROADMAP.md` contains the roadmap-level scope and acceptance boundary. The active `docs/milestones/M15.md` contains the clarified executable M15 contract.

## Engineering proportionality

0.3 must follow the risk-based engineering proportionality rules in `AGENTS.md`.

The following areas deserve unusually strong verification because failure can have high impact or invalidate the core product promise:

- privileged/background filesystem boundary;
- protected index storage and ACL/reparse-point interactions;
- index integrity and checkpoint/change-tracking correctness;
- recovery after loss of incremental continuity;
- measured search performance;
- ranking regressions against representative real workflows.

Ordinary Settings, launch-on-startup, tray/lifecycle behavior, install/uninstall transitions, and UI animation/polish need solid supported-path testing without combinatorial expansion unless a real high-impact defect appears.

Meeting milestone acceptance criteria is a stopping point. Do not keep adding hardening, migration machinery, provider abstractions, deployment flexibility, or generalized infrastructure after PASS merely because more theoretical cases can be imagined.

## 0.3 non-goals

0.3 is intentionally filesystem-focused. It should not add the following unless a separately approved milestone establishes a narrow prerequisite:

- browser-history/bookmark source;
- Google Drive, Gmail, OneDrive, calendar, contacts, or other remote/heterogeneous sources;
- file-content indexing;
- full file identity/history product features;
- deleted-item history retention;
- application-provider/launcher expansion as a release goal;
- public/dynamic plugin system;
- runtime source/module discovery/loading as an M15 requirement;
- generalized provider SDK, provider lifecycle, capability matrix, or version negotiation;
- universal source/object storage model;
- full visual query builder or saved searches;
- preview/file-manager operations;
- automatic update installation;
- installer replacement without evidence that the current deployment blocks a 0.3 requirement;
- Linux implementation;
- AI functionality;
- enterprise deployment features without a concrete requirement;
- exhaustive migration compatibility for arbitrary historical development-release installations.

## Relationship to file identity/history

0.3 should preserve the foundations needed for later NTFS identity/history work, especially stable volume/file identity and a reliable change stream. It should not implement full historical retention merely because the data passes through the maintenance pipeline.

The preferred post-0.3 direction is Quail 0.4, focused on filesystem identity/history without turning Quail into a filesystem-forensics product. Expected areas are identity semantics, a minimal history persistence model, rename/move lineage, explicit deletion/history retention semantics, richer Full Search/Object Explorer history/details UX, and release stabilization.

Retention of deleted or historical source data must remain an explicit product/privacy decision rather than an accidental side effect of indexing.

## Relationship to the first heterogeneous source

After the filesystem-focused 0.3 and likely 0.4 work, browser history/bookmarks remain the preferred candidate for Quail 0.5 or the next suitable release.

That release should prove the source-neutral Core contract against a genuinely different source. It should refine broader shared contracts from evidence rather than repair a `Core -> FileSystem` dependency. Physical optionality/runtime source loading may be introduced when it becomes a concrete product or packaging need; the dependency direction established by M15 should make that primarily a composition change.

## Execution boundary

Roadmap design belongs in the parent Quail roadmap thread. Implementation coordination belongs in the dedicated Quail 0.3 thread.

The Quail 0.3 thread should:

- read fresh canonical repository state before every milestone;
- execute milestones in the approved roadmap order unless the roadmap thread changes that order;
- prepare the implementation-agent/Codex prompt for the current milestone;
- perform independent QA and route fixes back to the same milestone branch;
- stop and return to roadmap planning if implementation evidence requires a material change to later milestone scope or architecture.

It should not independently redesign the whole release roadmap or expand 0.3 beyond the approved release boundary.
