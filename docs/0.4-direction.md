# Quail 0.4 Direction

## Status

**Approved roadmap planning baseline. Execution is intentionally paused pending migration of the Quail development workflow to Consensus.**

Quail 0.3.1 is the current released baseline. Do not begin Quail 0.4 implementation, create executable 0.4 milestone branches, or treat the initial milestone map below as active work until the roadmap explicitly records that the workflow migration to Consensus is complete.

The repository remains the canonical technical source for Quail. Consensus is intended to become the operational coordination layer for tasks, bugs, review, decisions, comments, and agent handoffs; it does not replace repository-owned architecture, release, verification, or durable technical state.

## Release goal

> Quail 0.4 should treat a local NTFS file or directory as a durable object across supported rename/move operations, let the user find the current object through its observed previous names and locations, and expose useful bounded lineage without turning Quail into a forensic or auditing system.

Quail 0.4 remains a filesystem-focused release. Its purpose is to move the product from "search the current path" toward "search the object and understand where it has been."

## Core product scope

The approved 0.4 product boundary includes:

- stable source-native NTFS identity semantics for indexed local filesystem objects;
- evidence-based handling of volume identity, file-reference reuse, hardlinks, directory moves, rename/move correlation, journal gaps, rebuild epochs, and other cases that affect whether identity can be trusted;
- observed same-volume rename/move lineage for current objects;
- search by observed previous names and locations, returning the current object rather than a misleading historical duplicate;
- result projection that can explain a historical match;
- the smallest persistence model needed for identity/lineage, including schema evolution, recovery, storage-growth measurement, retention, and clearing semantics;
- a bounded Full Search / Object Explorer history/details experience for current objects;
- CLI parity for meaningful non-visual identity/history behavior through the same shared application/search semantics;
- a bounded tranche of post-0.3.1 dogfooding defects that are ordinary correctness or UX fixes and do not change the release goal;
- a bounded maintenance-service memory characterization before history persistence materially increases the maintenance workload;
- the previously approved post-0.3 extraction of source-neutral search-session orchestration from the WinUI-specific application layer when needed to keep GUI and CLI behavior shared;
- final stabilization, upgrade/recovery verification, physical-host maintenance acceptance, and frozen-RC dogfooding before publication.

## Identity and history semantics

0.4 should model **observed lineage**, not claim a complete forensic history of the filesystem.

Historical names and paths are properties/search signals of a current object. A current direct match should remain distinguishable from a historical match, and the UI should make the reason for the match understandable.

Same-volume rename/move is the primary supported continuity case. Cross-volume movement must not automatically be treated as the same object unless a later verified mechanism can prove that relationship safely; the conservative default is separate delete/create semantics.

Hardlinks, file-reference reuse, directory moves, journal discontinuity, rebuild boundaries, and related NTFS details must be resolved by the identity/semantics spike before the production persistence model is frozen.

## Deleted items and retention

A searchable archive of deleted filesystem objects is **not** part of the Quail 0.4 product boundary.

The implementation may retain the minimum tombstone or lifecycle metadata required for correctness, file-reference reuse protection, recovery, or lineage semantics, but such internal state must not silently become a user-visible indefinite deleted-item archive.

History retention must be bounded and understandable. 0.4 must define clearing behavior and must not retain history indefinitely merely because the maintenance stream can observe it. The exact retention duration or policy should be selected from product need, privacy considerations, and measured storage growth rather than frozen before implementation evidence exists.

## Maintenance baseline

Quail 0.3.1 establishes the maintenance baseline for 0.4:

- authoritative Sync reads a captured finite journal frontier;
- same-volume Quail-owned post-Sync records may advance only an in-memory wait frontier under the accepted exact-classification rules;
- durable checkpoints advance only after authoritative committed work;
- startup catch-up remains immediate;
- normal steady-state external/change wakes use the fixed 60-second non-resetting coalescing window;
- Search remains direct read-only SQLite and does not depend on service IPC;
- continuity uncertainty remains fail-closed.

The approximately 60-second steady-state freshness window is an accepted 0.4 starting point, not a permanent product promise. Do not redesign batching/coalescing merely because a more sophisticated scheduler can be imagined.

If real dogfooding demonstrates that freshness or batch cost is materially harmful, the 0.4 execution thread may add a bounded measurement/optimization milestone inside the approved release boundary. Do not introduce a generic scheduler framework or speculative persistent-deadline machinery without evidence.

## Maintenance memory investigation

The final 0.3.1 physical acceptance observed finite maintenance batches that could temporarily raise the service to roughly 600-700 MB of working/private memory before releasing a substantial portion afterward. There is no current evidence of a monotonic leak.

0.4 therefore includes a bounded characterization step before assuming a fix is required. Measure, where practical:

- Working Set and Private Bytes;
- managed heap size and allocation rate;
- GC generations and LOH behavior;
- relevant SQLite/native cache or buffer contribution;
- correlation with Sync/batch size;
- release after a batch;
- repeated-batch plateau behavior.

A production optimization is added only if measurements establish a material bottleneck or unhealthy retained state. Do not assume in advance that GC, SQLite, native buffers, or any other single component is the cause.

## Known dogfooding defect tranche

The first known bounded 0.4 dogfooding defect is the Settings -> Indexing presentation issue where one target's active update can project global `Updating` state onto other cards and make multiple targets appear active.

The implementation must inspect the actual operation/queue model before choosing the UX. The fix may distinguish active, queued, blocked, idle, or not-built states as the real behavior requires. Do not infer the underlying scheduling semantics from the presentation bug alone.

Additional ordinary defects may join this tranche only if they are discovered before the tranche is frozen for execution and remain bounded within the 0.4 release goal. A newly discovered release-critical defect in the shipped 0.3.1 baseline should instead trigger an explicit patch-release decision rather than being hidden inside 0.4.

## Deferred from 0.4

The following are intentionally not part of the approved 0.4 boundary unless a later roadmap decision changes the release goal:

- per-user/limited installation mode;
- the general non-service user-mode filesystem indexing backend;
- SMB/network-share indexing;
- Settings-driven Windows Service install/start/restart/repair/uninstall workflow;
- automatic updater work;
- code-signing/SAC deployment work beyond any separate roadmap/maturity decision;
- browser, mail, cloud, calendar, or other heterogeneous sources;
- content indexing;
- public/dynamic plugin SDK or generalized source framework;
- deleted-item archive/search;
- file-manager behavior, preview subsystem, or general knowledge graph;
- Linux implementation;
- mobile, peer-to-peer, or multi-device features.

The restored deployment/indexing-mode direction remains valid future work; it is simply not combined with the first identity/history release.

## Initial milestone map

This is an initial roadmap decomposition, not an immutable execution contract. Once 0.4 execution begins after the Consensus migration, the dedicated execution workflow may refine, split, add, remove, reorder, or replace milestones within the approved release boundary when implementation or QA evidence justifies it.

### M25 — 0.3.1 Dogfooding Defect Tranche

Freeze and fix a small set of reproducible post-0.3.1 correctness/UX defects that do not change the 0.4 product goal. The known Indexing-card operation-state presentation issue belongs here.

### M26 — Maintenance Memory Characterization

Measure transient and retained maintenance-service memory across representative batches and repeated cycles. End with either evidence that no production change is needed or a bounded optimization recommendation.

If optimization is justified, the execution workflow may add a small follow-on milestone before history persistence.

### M27 — NTFS Identity & History Semantics Spike

Resolve the product/technical semantics for volume/file identity, reuse, hardlinks, rename/move/delete correlation, directory moves, journal gaps, rebuild epochs, observed-history guarantees, retention boundaries, and failure behavior before freezing the production persistence model.

### M28 — Shared Search/Application Orchestration Boundary

Perform the smallest behavior-preserving extraction needed to keep source-neutral search-session semantics shared outside the WinUI-specific frontend and preserve CLI/Core parity before history-aware search expands product behavior.

Do not create a speculative application framework or second search engine.

### M29 — Identity / Lineage Persistence & Maintenance

Implement the smallest persistence and maintenance model selected by M27, including schema evolution from the 0.3.1 baseline, atomicity, recovery, storage-growth evidence, clearing/retention semantics, and service integration.

### M30 — Historical Search & Relevance

Make observed previous names and locations useful search signals for the current object, keep current direct matches distinct from historical matches, preserve deterministic ranking, and expose the reason for a historical match through shared search semantics.

### M31 — Object Explorer v2 / History UX

Expose bounded identity/lineage details for current filesystem objects in Full Search / Object Explorer, including useful previous-name/location context and the required retention/clear controls. Preserve CLI parity where the behavior is meaningful outside the GUI.

### M32 — 0.4 Stabilization / Frozen Release Candidate

Verify upgrade/recovery, identity/history correctness, retention/privacy, storage growth, search performance/relevance, maintenance resources, the mandatory installed physical-host maintenance topology, and the frozen-RC dogfooding gate.

Tagging and publication remain separate explicit approval gates after the release candidate passes.

## Execution hold and Consensus migration

All Quail feature development is intentionally shelved while Consensus is being built.

Before 0.4 implementation starts:

1. complete the usable Consensus workflow needed to coordinate Quail development;
2. explicitly migrate Quail's active task/review/decision workflow into Consensus;
3. preserve the repository as the canonical technical source and retain the existing Git/PR, QA, verification, and safety gates unless a deliberate cross-version methodology decision changes them;
4. record that the migration is complete;
5. only then open 0.4 execution and activate the milestone plan.

Do not design speculative Quail-specific Consensus extensions in this document. The migration should use the capabilities that actually exist when Consensus is ready.
