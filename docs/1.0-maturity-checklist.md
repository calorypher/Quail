# Quail 1.0 Maturity Checklist

## Status

**Planning checklist for the road to Quail 1.0.**

This document does not add new product features to the frozen Quail 1.0 scope. It records maturity concerns that should be resolved, measured, or explicitly waived before calling the frozen target product 1.0.

## Areas to close before 1.0

### Schema evolution and migration

Quail should have a deliberate, tested way to evolve persistent schemas and source state across supported upgrades. A normal product upgrade should not require an avoidable full rebuild merely because an internal schema changed.

Migration failure must fail safely and leave a clear recovery path.

### Recovery semantics

For each persistent/source subsystem, define what happens after interrupted writes, crashes, incomplete migrations, stale synchronization cursors, expired authentication, missing sources, corrupted derived state, or other failures relevant to that subsystem.

Where correctness cannot be proven, Quail should surface an explicit degraded/rebuild/re-authentication state rather than silently trusting stale or inconsistent data.

### Source health and observability

As heterogeneous sources are introduced, users need a compact source-health model such as healthy, syncing, stale, disconnected, authentication required, rebuild required, or equivalent source-specific states.

Useful status should include last successful synchronization or equivalent freshness information where the source model supports it, without exposing unnecessary implementation detail.

### Data lifecycle and cleanup

Quail should make local data retention understandable. Users should be able to determine, at a practical level, which sources/history/content/derived state consume local storage and clear data at appropriate source or feature boundaries.

Retention and deletion behavior should remain consistent with the privacy rules in `docs/product-vision.md`.

### Privacy and exclusions

Before 1.0, exclusions and retention controls should form a coherent product model rather than accumulating unrelated special cases for every source. The exact abstraction should be derived from real sources rather than imposed prematurely.

### Upgrade path

The supported transition between normal released versions should be explicit and verified for installer/runtime state, persistent schemas, source configuration, service/background components where present, and credentials or authorization state where relevant.

This does not require a particular automatic-updater technology before 1.0.

### Storage-efficiency gate

The existing storage-efficiency gate in `docs/1.0-scope-boundary.md` remains part of the final 1.0 readiness decision. Storage optimization is evidence-driven; transparent whole-database compression is not an architectural requirement.

## Use during roadmap planning

After Quail 0.3, version planning should map these concerns onto the remaining pre-1.0 releases when the relevant persistent/source capabilities exist. Do not create speculative infrastructure before a concrete source or migration path needs it.

A checklist item may be closed by implementation, measured evidence, or an explicit decision that it is not applicable to the actual 1.0 product shape. The checklist should not be used to smuggle post-freeze product ideas into pre-1.0 scope.
