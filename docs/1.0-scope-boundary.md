# Quail 1.0 Scope Boundary

## Status

**Approved cross-version product-scope policy, frozen on 2026-09-06.**

This document defines the product boundary for Quail 1.0. Its purpose is to keep 1.0 as a finite target rather than allowing every later idea to move the release goal indefinitely.

The freeze baseline is repository `main` at commit `3a90a26a1eec2a70e0c397106992d25cfd9ac630` together with the canonical product/roadmap documents that existed at that point.

## 1.0 product envelope

Quail 1.0 is the completion of the product direction already recorded in the canonical repository at the freeze baseline.

This means that later pre-1.0 version planning may reorganize the route to 1.0, but it must not silently expand the product envelope merely because a new feature idea is attractive.

The existing documents retain their original semantics and status. A capability already described as a product goal, approved architectural direction, or directional pre-1.0 area remains part of the material that may shape the road to 1.0. A capability merely mentioned as plausible, optional, or explicitly uncommitted does not become mandatory for 1.0 just because it appeared in the repository before the freeze.

After Quail 0.3 is complete, roadmap planning should turn this frozen envelope into a more concrete 1.0 completion map and classify the already-recorded work into:

- required before 1.0;
- optional pre-1.0 work that may be deferred without changing the 1.0 product definition;
- explicitly post-1.0 work.

That classification may clarify the current documents, but should not use new feature ideas to enlarge the 1.0 target.

## Allowed pre-1.0 roadmap changes

The path to 1.0 remains evidence-driven. Before 1.0 the roadmap may:

- split, merge, reorder, add, remove, or rename intermediate `0.x` releases;
- move already-approved scope between pre-1.0 releases;
- add bounded spikes, migrations, refactors, or technical prerequisites required to deliver the frozen product target correctly;
- change implementation details, storage designs, service boundaries, source contracts, verification strategy, or other technical architecture when evidence requires it;
- defer an existing optional candidate when it is not necessary for the coherent 1.0 product.

None of these changes requires moving the 1.0 goal itself.

## New ideas after the freeze

New product ideas proposed after the freeze are **post-1.0 by default**.

They should be recorded in `docs/post-1.0-ideas.md` rather than inserted into the pre-1.0 roadmap. Recording an idea there does not commit Quail to implementing it and does not establish priority or version assignment.

A post-freeze idea may move into pre-1.0 scope only through an explicit cross-version roadmap decision showing that it is genuinely required to satisfy the already-frozen 1.0 product definition, correctness, security, compatibility, or another unavoidable prerequisite. "Useful", "interesting", or "fits the vision" is not sufficient by itself.

## 1.0 release meaning

The version number `1.0` should mean that the frozen target product is coherent, verified, and mature enough to stop treating the main product boundary as provisional.

There is no requirement to publish every intermediate version number. The project may move from any suitable `0.x` release directly to `1.0` once the frozen completion criteria are satisfied.

Likewise, the number of intermediate releases is not a success metric. The point of this policy is that the destination remains fixed while the engineering route can continue to adapt.
