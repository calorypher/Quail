## Confirmed root cause

The persisted checkpoint returned by `IndexStore.Sync` is the authoritative
frontier that was read and applied. `Sync` then necessarily performs protected
SQLite writes, WAL checkpoint/truncation, and WAL-to-DELETE finalization. The
service subsequently atomically republishes maintenance health. On C:, all of
those protected writes occur on the same journal that the target loop watches.

The loop nevertheless starts `WaitForChangesAsync` from the persisted applied
checkpoint, which predates those writes. The wait therefore completes
immediately on Quail's own records. The next authoritative `Sync` applies that
gap, persists another checkpoint and refresh timestamp, finalizes SQLite again,
and republishes health, creating another wake source.

The bounded USN range from checkpoint `1681146816` to cursor `1683373616`
contained 15,256 records. Its dominant repeated groups were:

- 839 create/data/close/delete sequences for the protected `db-journal`;
- 419–420 create/data/close/delete sequences for `db-wal` and `db-shm`;
- 419 database overwrite sequences;
- 421 rename/data/close sequences for `maintenance-health.json`, plus the
  corresponding atomic-replacement temporary files.

The observed causal cycle is therefore:

```text
authoritative Sync from persisted checkpoint
  -> checkpoint / last-refreshed SQLite commit
  -> WAL checkpoint and WAL-to-DELETE finalization
  -> atomic maintenance-health publication
  -> same-volume USN records after the applied checkpoint
  -> wait starts at the older applied checkpoint and completes immediately
  -> next authoritative Sync
```

D:-style maintenance does not self-wake from these records because its wait is
on the D: journal while the protected database and health writes occur on C:.

The fix must keep the persisted applied checkpoint unchanged as the durability
authority. It may use a newer in-memory wait frontier only after proving that
the gap contains exclusively Quail-owned protected-state activity. Any external
or unknown record in the gap must force another authoritative Sync before wait.
This preserves the Sync-to-wait race: a real change during gap inspection is
either observed by that inspection or immediately satisfies the wait started
from the inspected cursor.

## Production change

`MaintenanceJournalGap` now handles the narrow same-volume boundary after an
authoritative sync and health publication:

1. separate-volume targets keep the applied checkpoint as their wait frontier;
2. same-volume targets re-query and validate journal continuity;
3. the service resolves the native identities of the protected Quail,
   `Indexes`, and `Locks` directories;
4. it reads the bounded gap from the durable applied checkpoint;
5. exact database, journal, WAL/SHM, lock, health, atomic-health temporary, and
   protected-directory records are recognized as Quail-owned;
6. an exclusively owned gap produces a newer in-memory wait frontier only;
7. any external or unknown record immediately loops through another
   authoritative `Sync`;
8. transient inspection failures enter the existing controlled retry path;
9. journal disappearance, deleted entries, malformed records, unsupported
   records, and continuity loss remain fail-closed as `RebuildRequired`.

The classifier accepts both 128-bit USN v3 parent identifiers and zero-extended
64-bit USN v2 identifiers. It does not suppress arbitrary ProgramData records.
Inspection remains inside the existing global protected-writer boundary, so a
different target cannot publish protected state between sync and gap
inspection. The sole-writer, read-only search, durable checkpoint, SQLite
finalization, ACL, and reparse-point boundaries are unchanged.

The candidate version is `0.3.1`; assembly and file versions are `0.3.1.0`.
The installer transition guard additionally allows the bounded released 0.2.0
or withdrawn 0.3.0 to 0.3.1 transition at the canonical path. Other historical
development builds remain uninstall-first.

## Automated regression coverage

Focused regression tests cover:

- an owned same-volume gap advancing only the transient wait frontier;
- an external record in the Sync-to-wait gap forcing another authoritative
  sync;
- continuity loss preserving fail-closed `RebuildRequired`;
- transient post-Sync journal inspection failure preserving the durable
  checkpoint and entering controlled retry;
- `ERROR_JOURNAL_NOT_ACTIVE`, `ERROR_JOURNAL_ENTRY_DELETED`, malformed records,
  and unsupported records mapping to `RebuildRequired` rather than faulting the
  runtime or retrying forever;
- exact protected-artifact classification, including USN v2/v3 parent IDs;
- separate-volume maintenance bypassing same-volume gap inspection;
- the journal wait consuming the caller-provided frontier as signal-only.

The existing M20 integration and runtime checks continue to cover complete
database searchability, incomplete-database rejection, health publication,
protected command authorization, service lifecycle behavior, and the native
USN wait contract. Real VM verification below covers CREATE, metadata, RENAME,
MOVE, DELETE, downtime catch-up, restart, separate-volume maintenance, and
fail-closed recovery.

The health timestamp did not advance, and neither WAL nor SHM existed during

the pre-fix 642,193,602-byte/30-second self-generated write loop and its 110/112
WAL/SHM existence transitions.

On C:, one stable file identity was exercised through the complete real-change
sequence:

- CREATE became searchable in 1,710.3 ms;
- a relevant size/last-write metadata update became searchable in 217.8 ms;
- RENAME removed the old path and exposed the new path in 320.4 ms;
- MOVE exposed the destination path in 213.5 ms;
- DELETE removed the result in 208.6 ms.

The checkpoint advanced from `1683570216` to `1683617136`, the target remained
`Healthy` and trusted, and the service returned to quiescent idle.

For downtime catch-up, the service was stopped cleanly, a C: file was created,
and the service was restarted. The file became searchable and the target
returned to `Healthy`. A normal Windows restart then repeated this test with a
new marker created immediately before reboot; after boot, the service was
Running, both configured targets were healthy, and the marker was searchable.
Post-boot Windows activity generated a decaying finite catch-up workload rather
than the prior autonomous loop: later 30-second samples fell to 11.3 MB of
writes and 22,368 checkpoint bytes, with WAL/SHM present in only 5 of 300
samples and 8 existence transitions. The exact-zero pre-reboot observation is
the controlled VM idle result; these post-boot counters are not represented as
physical-host idle evidence.

For the separate-volume control, D: remained healthy with its protected state
on C:. A D: CREATE became searchable in 643.2 ms and DELETE removed it. A
deliberately impossible future D: checkpoint then produced
`RebuildRequired` with `saved-usn-after-journal-frontier`; the database hash
remained stable and no automatic rebuild occurred. An explicit rebuild restored
the D: target to complete, healthy, and trusted.

## Physical-host acceptance gate

This gate is mandatory and has not been executed from the implementation
environment. Do not publish 0.3.1 until the following bounded test passes on the
physical PC that reproduced the 0.3.0 defect:

1. Install the final candidate normally and confirm `QuailMaintenance` is
   Running.
2. Confirm C: is registered, complete, and `Healthy`, no Build/Rebuild is in
   progress, and `%ProgramData%\Quail` resolves to C:.
3. Record service PID, CPU time, working set, private bytes, read/write bytes,
   read/write operations, handle/thread counts, both target checkpoints, health
   timestamps, and current WAL/SHM existence.
4. Observe for at least five minutes without deliberate user filesystem
   activity. Sample counters and WAL/SHM existence at one-second intervals.
5. Record the same counters and checkpoints. Reject the candidate if there is
   sustained logical-CPU use, continuous Quail-owned write growth comparable to
   the old approximately 30 MB/s loop, autonomous unbounded WAL/SHM churn, or
   checkpoint advancement attributable only to Quail's protected writes.
6. On C:, perform CREATE, size/last-write metadata update, RENAME, MOVE, and
   DELETE with one uniquely named test file. After each operation, bound the
   time until search shows the expected state.
7. Observe another two-minute idle interval and confirm the service returns to
   quiescence.
8. Create a second uniquely named C: marker, restart Windows normally, and
   confirm the service returns to Running, catches up the marker, and both C:
   and the D: control are healthy.
9. After ordinary boot activity settles, repeat the five-minute counter,
   checkpoint, and WAL/SHM observation.
10. Save the before/after counter tables and note any real external filesystem
    activity that explains non-zero bounded work.

Absolute 0 B/s is not required. The acceptance criterion is absence of a
continuous, monotonic Quail-owned workload and preservation of real-change and
restart catch-up correctness.
