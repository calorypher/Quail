## Confirmed root cause

The persisted checkpoint returned by `IndexStore.Sync` is the authoritative
frontier that was read and applied. `Sync` then necessarily performs protected
SQLite writes, WAL checkpoint/truncation, and WAL-to-DELETE finalization. The
service subsequently atomically republishes maintenance health. On C:, all of
those protected writes occur on the same journal that the target loop watches.

The loop nevertheless starts `WaitForChangesAsync` from the persisted applied
checkpoint, which predates those writes. The wait therefore completes
immediately on Quail's own records. The next authoritative `Sync` applies that
gap, persists another checkpoint and refresh timestamp, finalizes SQLite again,
and republishes health, creating another wake source.

The bounded USN range from checkpoint `1681146816` to cursor `1683373616`
contained 15,256 records. Its dominant repeated groups were:

- 839 create/data/close/delete sequences for the protected `db-journal`;
- 419–420 create/data/close/delete sequences for `db-wal` and `db-shm`;
- 419 database overwrite sequences;
- 421 rename/data/close sequences for `maintenance-health.json`, plus the
  corresponding atomic-replacement temporary files.

The observed causal cycle is therefore:

```text
authoritative Sync from persisted checkpoint
  -> checkpoint / last-refreshed SQLite commit
  -> WAL checkpoint and WAL-to-DELETE finalization
  -> atomic maintenance-health publication
  -> same-volume USN records after the applied checkpoint
  -> wait starts at the older applied checkpoint and completes immediately
  -> next authoritative Sync
```

D:-style maintenance does not self-wake from these records because its wait is
on the D: journal while the protected database and health writes occur on C:.

The fix must keep the persisted applied checkpoint unchanged as the durability
authority. It may use a newer in-memory wait frontier only after proving that
the gap contains exclusively Quail-owned protected-state activity. Any external
or unknown record in the gap must force another authoritative Sync before wait.
This preserves the Sync-to-wait race: a real change during gap inspection is
either observed by that inspection or immediately satisfies the wait started
from the inspected cursor.

## Production change

`MaintenanceJournalGap` now handles the narrow same-volume boundary after an
authoritative sync and health publication:

1. separate-volume targets keep the applied checkpoint as their wait frontier;
2. same-volume targets re-query and validate journal continuity;
3. the service resolves the native identities of the protected Quail,
   `Indexes`, and `Locks` directories;
4. it reads the bounded gap from the durable applied checkpoint;
5. exact database, journal, WAL/SHM, lock, health, atomic-health temporary, and
   protected-directory records are recognized as Quail-owned;
6. an exclusively owned gap produces a newer in-memory wait frontier only;
7. any external or unknown record immediately loops through another
   authoritative `Sync`;
8. transient inspection failures enter the existing controlled retry path;
9. journal disappearance, deleted entries, malformed records, unsupported
   records, and continuity loss remain fail-closed as `RebuildRequired`.

The classifier accepts both 128-bit USN v3 parent identifiers and zero-extended
64-bit USN v2 identifiers. It does not suppress arbitrary ProgramData records.
Inspection remains inside the existing global protected-writer boundary, so a
different target cannot publish protected state between sync and gap
inspection. The sole-writer, read-only search, durable checkpoint, SQLite
finalization, ACL, and reparse-point boundaries are unchanged.

The candidate version is `0.3.1`; assembly and file versions are `0.3.1.0`.
The installer transition guard additionally allows the bounded released 0.2.0
or withdrawn 0.3.0 to 0.3.1 transition at the canonical path. Other historical
development builds remain uninstall-first.

### Physical-host short-query blocker forensic diagnosis

The mandatory physical-host idle gate did not reproduce the withdrawn 0.3.0

The persisted neighborhood is bounded by directory entries `Speech` at label
107298816 and `sysfile` at label 107319296. The three retained SRU leaves have
labels 107315196, 107315198, and 107315199, the characteristic result of
repeated midpoint insertions followed by deletion of older leaves. A later
`SRU0072F.log` exists on the filesystem but is absent from the rolled-back
database; it is evidence of the same normal rotation workload, not the failing
record by itself.

Forensic replay against a disposable copy of the exact database distinguishes
the failure mechanism. Inserting a synthetic leaf at the `SRU0072F.log` sort
position succeeds because `TryRecoverExhaustedLeafGap` relabels the bounded
leaf neighborhood. Inserting an otherwise identical directory fails with the
same `Short-query rank label gap is exhausted; rebuild is required` exception.
The current recovery deliberately returns false for directories because their
rank labels are referenced by children. Therefore the physical failure was an
ordinary directory insertion into an already fragmented local gap; the failed
transaction does not retain the new directory row, so its exact path is not
recoverable from the database alone. Raw journal access was not available to
the unelevated diagnostic process, but the retained state plus exact-database
replay establishes the causal code path without modifying the protected index.

The withdrawn 0.3.0 self-wake loop is not required for this failure. Its
metadata-only updates do not relabel short-query entries, and there is no
evidence that it created this specific SRU neighborhood. A freshly built 0.3.1
index can nevertheless reach the same state through normal long-lived
insert/delete/reinsert churn because deletion does not compact labels and the
directory path has no recovery once a gap reaches spacing one. The production
correction must therefore regenerate only the derived short-query state from
the authoritative namespace atomically within the failing journal batch,
without advancing the durable checkpoint until the complete batch commits.

The physical C: target remains `RebuildRequired`/untrusted. No rebuild, index
deletion, uninstall, manual database repair, CRUD campaign, or reboot was
performed after the failure.

### Transactional short-query recovery

Rank-gap exhaustion now has a typed failure boundary. The journal batch first
applies the triggering authoritative namespace mutation. If incremental
short-query insertion exhausts a local label gap, the remainder of that batch
continues as namespace-only mutations and the complete short-query derived
state is regenerated once from the final authoritative namespace. Regeneration
and the later generation/checkpoint advance remain in the same SQLite
transaction.

This gives the following bounded behavior:

- one derived-state regeneration at most per journal batch;
- later CREATE and DELETE records in that batch are represented in the rebuilt
  result;
- directory parent-label references are regenerated from final namespace
  relationships rather than patched locally;
- Search cannot observe a healthy stale generation;
- a failure before commit rolls namespace, derived state, generation, and the
  durable checkpoint back together;
- replay after rollback applies the unchanged durable journal batch normally;
- genuine namespace/derived structural failures still fail closed.

The existing local leaf-gap recovery remains the cheap path. Full derived-state
regeneration is used only after the narrow typed label-gap exhaustion, not for
unrelated exceptions and not as a retry loop.

Focused `IncrementalIndexStoreTests` passed 44/44. Coverage includes the exact

### Physical recovery blocker: one Sync followed the moving journal tail

The authorized physical C: Rebuild request
`168330c2-5d3e-42af-adf0-c6a9269b178a` was accepted and resolved to C:, but
never reached `control-operation-build-start`; no staging `.building` database
was created. The existing C: target remained in `startup-catch-up`, and the
Rebuild waited for `StopTargetLoopAsync` to join that target loop. D: also
reported catch-up because the C: target retained the process-wide protected
writer boundary; the UI's global `Updating` presentation was not evidence of a
second rebuild.

A bounded 71.4-second observation showed 71,296.875 ms of service CPU time
(99.84% of one logical processor), 87,523,548,329 logical read bytes
(approximately 1.225 GB/s), 47,949,258 logical write bytes (approximately
671 KB/s), 21,368,190 read operations, and 14,757 write operations. Neither
volume's health checkpoint advanced, the complete final C: database did not
grow, no staging database appeared, and the 115,598,992-byte WAL stayed the
same size while its timestamp continued to change. C: durable `next_usn` was
`2322454000`, 10,240,592 beyond the published health checkpoint
`2312213408`. This is forward work trapped inside one `IndexStore.Sync`, not
the previously fixed post-Sync wait loop.

The causal mechanism is explicit in the pre-correction code:

1. `IndexStore.Sync` queries a finite journal state but passes only the durable
   checkpoint to `NtfsJournal.Read`.
2. `NtfsJournal.Read` repeatedly issues `FSCTL_READ_USN_JOURNAL` until a read
   returns no records; it has no upper frontier.
3. Each callback applies and commits a batch to protected SQLite on the watched
   C: volume, generating later USN records.
4. The next native read starts at the returned live cursor and can consume
   those new records, whose application creates still more records.
5. `Sync` therefore need not reach an empty read on an active same-volume
   writer. It cannot return to `MaintenanceJournalGap`, observe cancellation,
   or release the global writer, so the requested Rebuild cannot begin.

The required correction is a half-open, captured range. One Sync invocation
may consume only records with `record.Usn < journal.NextUsn` where
`journal.NextUsn` is the high-water mark captured by its initial successful
query. A native buffer may cross that boundary; records at or beyond it belong
to the next authoritative iteration, and the current durable checkpoint may
advance only to the captured frontier after every earlier record has been
successfully applied. This preserves later external and Quail-owned changes:
the post-Sync gap inspection observes the range beginning at that exact durable
frontier, and either forces another Sync for any external/unknown record or
uses a newer in-memory wait frontier only after proving the gap is exclusively
Quail-owned.

VM, and package candidate.

### Bounded Sync source correction

`NtfsJournal.Read` now requires a captured exclusive upper frontier for every
production read performed by `IndexStore.Sync`, initial-build journal handoff,
and `MaintenanceJournalGap`. Its deterministic page seam validates forward,
ordered cursors and processes only the half-open range from the durable
checkpoint to that captured frontier. A native page whose returned next cursor
crosses the frontier is filtered by record USN; the callback receives the
captured frontier as its batch cursor, while records at or above it are left for
the next read beginning at exactly that durable value. An empty captured range
performs no native read. A backward, stalled, mismatched, or otherwise
inconsistent page fails closed through the existing malformed-journal path.

This makes one Sync finite without a sleep, debounce, polling loop, arbitrary
batch count, ProgramData suppression, or speculative checkpoint advance. Each
non-empty batch still commits namespace, derived state, generation, and its
proven cursor atomically. Only after the entire bounded read succeeds does
`PersistSuccessfulSync` record the exact captured frontier and refreshed time.
If a callback fails, its transaction rolls back and the failing cursor is not
published. A later external or Quail-owned record has a USN at or above the
captured frontier and is therefore inspected by the post-Sync gap path; an
external/unknown record forces another Sync, while a record arriving after gap
