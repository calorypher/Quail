# M01 — NTFS/MFT/USN feasibility

## Goal

Validate whether official Windows/NTFS mechanisms are a sufficient technical basis for Quail's own local file index before freezing the persistent schema, production index architecture, or Windows Service boundary.

M01 is a feasibility spike. It must produce evidence and architectural conclusions, not a production indexer.

## Scope

Implement a small experimental C#/.NET 10 probe and use it to validate the following on Windows 11 x64 NTFS:

1. Discover local volumes and identify NTFS volumes.
2. Open a selected NTFS volume and determine the actual privilege requirements for volume access and USN/MFT operations.
3. Query the USN Change Journal and capture at least:
   - Journal ID;
   - First USN;
   - Next USN;
   - Lowest Valid USN;
   - supported record versions;
   - other cheap diagnostic fields that materially help later decisions.
4. Enumerate the NTFS namespace through official Windows mechanisms such as `FSCTL_ENUM_USN_DATA`.
5. Parse the records required by the test environment and obtain at least:
   - file reference number;
   - parent file reference number;
   - file name;
   - attributes;
   - USN;
   - other cheaply available metadata only when useful to later architecture decisions.
6. Validate on a small controlled dataset that FRN + parent FRN + name are sufficient to model parent/child namespace relationships and reconstruct representative paths.
7. Read the USN Change Journal and observe controlled operations including:
   - file creation;
   - directory creation;
   - modification;
   - rename;
   - move;
   - deletion.
8. Demonstrate restart/catch-up feasibility by saving an experimental checkpoint, stopping the probe, making filesystem changes, restarting the probe, and reading changes from the saved point.
9. Validate continuity-loss detection, including:
   - Journal ID mismatch;
   - a saved USN that is no longer readable;
   - the practical meaning of `FirstUsn` and `LowestValidUsn` for recovery decisions;
   - a clear experimental distinction between `catch up` and `rebuild required`.
10. Measure representative full-volume enumeration throughput and resource use on the physical host.
11. Produce an evidence-based recommendation for the smallest sensible privileged Windows Service responsibility for later milestones.

The preferred implementation style is a small experimental project under `experiments/`, for example `experiments/Quail.NtfsProbe`. Keep the Windows interop thin and isolated. Do not treat the experimental project structure as a frozen production architecture.

## Technical direction

- C#.
- .NET 10 LTS baseline.
- Official Windows APIs for NTFS/MFT/USN access.
- Thin P/Invoke only where needed.
- No custom NTFS parser.
- No native C++ or Rust component without evidence that the official API approach cannot satisfy the milestone.
- No SQLite or production persistence in M01.

## Privilege and safety policy

### Physical host

- Codex must not receive unrestricted administrative execution on the physical host.
- Normal repository work runs unelevated.
- Elevated host operations must be explicitly scoped and, when needed, executed manually by the user.
- Destructive filesystem operations on the physical host are limited to the designated test directory:
  `C:\Users\<user>\Documents\Quail-M01-Test`.
- The physical `C:` volume must not be formatted, repartitioned, cleared, or have its USN Journal deleted/recreated.
- `Clear-Disk`, `diskpart clean`, destructive `Format-Volume`, destructive partition operations, and equivalent operations against physical disks are prohibited.
- Host-volume NTFS/MFT/USN experiments outside the designated test directory must be read-only unless a narrower operation is explicitly approved.

### Disposable VHDX

- Journal reset/recreation and other storage-state experiments may be performed only when the target is positively identified as the disposable `QUAIL_M01` volume.
- The target must be re-validated before a destructive command.
- If target identity is ambiguous, stop instead of guessing.

### Hyper-V lab VM

- Codex may use administrative privileges inside the disposable VM.
- Codex may restart the VM and manipulate the disposable VM data disk as required by this milestone.
- Destructive operations should still target the disposable data disk rather than the VM system disk unless a system-disk test is explicitly required by an acceptance criterion.
- If a test could destroy the lab VM, ensure the `M01-clean` checkpoint exists first.
- No destructive action outside the VM is authorized by this milestone.

## Experimental checkpoint model

The initial hypothesis to validate is that restart catch-up can be based on a checkpoint containing at least:

```text
volume identity
USN Journal ID
next USN
```

A likely recovery decision is:

```text
query current journal

if saved Journal ID != current Journal ID:
    continuity lost -> rebuild required
else if saved USN is no longer readable:
    continuity lost -> rebuild required
else:
    read from saved USN
```

This is an experimental hypothesis for M01, not a frozen M03 production algorithm. The results must document any important nuance involving `FirstUsn`, `LowestValidUsn`, journal truncation, or record-version behavior.

## Controlled namespace dataset

Use a small deterministic dataset on a disposable NTFS volume, for example:

```text
Quail-M01-Test/
  alpha/
    alpha-one.txt
    alpha-two.bin
  beta/
    nested/
      nested-one.txt
  root-file.txt
```

The exact file contents are unimportant. The structure should be sufficient to validate parent relationships, sample path reconstruction, and controlled USN operations.

A representative mutation sequence should include:

1. create a file;
2. modify it;
3. rename it;
4. move it between directories;
5. rename a directory;
6. move a nested directory;
7. delete a file;
8. delete a directory tree.

Do not assume that one user-visible filesystem operation produces exactly one USN record. Capture and report the actual record/reason sequence.

## Enumeration benchmark method

Use the physical `C:` NTFS volume for the representative M01 benchmark.

Run:

- 1 warm-up enumeration;
- 3 measured enumerations.

Record every measured run and report the median. At minimum capture:

- record count;
- elapsed wall-clock time;
- records per second;
- process CPU time;
- peak working set;
- parsing/error count;
- Windows build;
- .NET version.

Do not introduce elaborate cache-clearing procedures or restart the machine solely to manufacture synthetic benchmark conditions. M01 needs a realistic baseline, not a benchmark competition.

No arbitrary performance PASS threshold is defined in advance. The result must be evaluated for architectural viability based on measured evidence.

## Out of scope

M01 must not implement or freeze:

- SQLite persistence or the production index schema;
- a production indexer;
- production path reconstruction;
- production handling of create/delete/rename/move in persistent state;
- search or ranking;
- FTS or another search-index technology;
- the production Windows Service;
- production IPC between service and user process;
- launcher GUI;
- global hotkeys;
- installer/update machinery;
- filesystem-content indexing;
- filesystem watchers as an alternative architecture;
- custom NTFS parsing;
- native C++/Rust components;
- cross-platform abstractions;
- performance comparisons against Everything or other products;
- optimizations unrelated to obtaining reliable feasibility evidence.

A minimal temporary Windows Service privilege spike is allowed only if the evidence obtained during M01 shows that it is necessary to determine the service boundary. It must not evolve into the production service or IPC architecture.

## Acceptance criteria

M01 is complete only when all applicable criteria are satisfied and the evidence is recorded durably.

1. The experimental probe builds and runs on Windows 11 x64 with the .NET 10 baseline.
2. Local NTFS volumes can be identified and relevant capabilities reported.
3. Actual privilege behavior is documented for the required volume/USN operations, including unelevated behavior.
4. MFT-oriented enumeration completes successfully on a representative real NTFS volume.
5. All encountered record versions that are required to complete the approved tests are either parsed correctly or a documented limitation triggers a stop/review decision.
6. FRN, parent FRN, filename, attributes, and required cheap metadata can be obtained for representative records.
7. Controlled data demonstrates that parent relationships support representative namespace/path reconstruction.
8. Controlled USN experiments expose the required create/modify/rename/move/delete behavior with raw reason/record evidence.
9. Restart/catch-up from an experimental checkpoint is demonstrated.
10. Continuity loss can be detected safely, including at least Journal ID mismatch and an unreadable/expired saved position.
11. Journal reset/recreation behavior is demonstrated on a disposable volume or VM and leads to a correct `rebuild required` conclusion.
12. Representative full-volume enumeration measurements are recorded for the physical host.
13. The results document whether `FSCTL_ENUM_USN_DATA` plus the USN Change Journal is a viable basis for Quail using one of:
    - `GO`;
    - `GO WITH LIMITATIONS`;
    - `NO-GO`.
14. The results contain a recommendation for the smallest sensible privileged Windows Service responsibility for M02/M03.
15. The results explicitly identify consequences, constraints, and unresolved questions for M02 and M03.

A successful build alone is not completion.

## Stop conditions

Stop instead of expanding the milestone if any of the following becomes true:

- satisfying the milestone appears to require a custom NTFS parser;
- a native C++/Rust component appears necessary;
- official Windows APIs do not expose data required for the intended namespace/index model;
- a production Windows Service or production IPC implementation would be required to proceed;
- an unsupported record-version or API behavior requires material architectural expansion rather than a bounded compatibility fix;
- a required test would need destructive action on a physical host volume;
- target disk/volume identity is ambiguous before a destructive operation;
- required hardware/system access is unavailable;
- canonical project documents conflict with the milestone;
- unrelated local changes are present in the working tree at milestone start;
- evidence points to a material architectural problem that should be reviewed before continuing.

When stopping, preserve the evidence obtained so far and describe the exact blocker and the decision required.
