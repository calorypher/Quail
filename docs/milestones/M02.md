# M02 — Persistent initial index

## Goal

Build Quail's first persistent production-oriented NTFS namespace index for one local NTFS volume.

M02 converts the M01 feasibility findings into a durable SQLite-backed initial index that can be built from official Windows APIs, closed, reopened, inspected, rebuilt safely, and used to reconstruct representative paths. It does not yet maintain the index incrementally from the USN Change Journal.

## M01 constraints carried forward

M02 must preserve the conclusions established in `docs/milestones/M01-results.md`:

- official Windows APIs remain the NTFS source of truth for initial enumeration;
- native file identifiers must not be truncated; the implementation must remain capable of representing 128-bit identifiers observed in USN v3 records;
- namespace state is represented by file identifier + parent identifier + name rather than canonical full-path storage;
- production initial enumeration must use streaming or batching rather than materializing the complete namespace in memory;
- the approximately 291 MB peak working set measured by the M01 probe was dominated by its full `List<UsnRecord>` materialization and is not an acceptable production memory model;
- USN record v4 remains an unresolved bounded compatibility issue for future journal processing and is not an M02 requirement;
- the likely future privileged boundary is a narrow Windows Service responsible for privileged volume access, enumeration, journal query, and journal reads, but production service/IPC work remains outside M02.

## Scope

Implement the first production-oriented file-engine slice with the following capabilities.

### 1. Project structure

Create a small production structure under `src/` and `tests/`.

Preferred baseline:

```text
src/
  Quail.Core/
  Quail.Cli/
tests/
  Quail.Core.Tests/
```

Responsibilities:

- `Quail.Core` owns NTFS enumeration, index-domain types, SQLite persistence, rebuild semantics, path reconstruction, and diagnostics;
- `Quail.Cli` is a thin command-line frontend used to drive and inspect the M02 backend;
- `Quail.Core.Tests` verifies deterministic logic and persistence behavior.

Do not introduce speculative provider/plugin abstractions or GUI dependencies.

### 2. One local NTFS volume

M02 supports one selected local NTFS volume per index database/build operation.

The implementation must:

- validate that the selected source is a local NTFS volume;
- persist a stable volume identity that is not based only on the current drive letter;
- retain the current mount/drive information only as diagnostic data where useful;
- reject unsupported/non-NTFS sources clearly.

Multi-volume orchestration is not required in M02.

### 3. Persistent SQLite namespace index

Use SQLite for durable storage.

Persist at least the information required for the namespace model and later milestones:

- volume identity;
- native file identifier without width loss;
- native parent identifier without width loss;
- file/directory name;
- relevant file attributes;
- record metadata that is cheap, reliable, and materially useful for later milestones;
- build/index metadata required for completeness, diagnostics, and safe rebuild behavior.

Do not store the full path as the canonical namespace representation.

The schema must make directory rename/move compatible with later updates without requiring a full descendant-subtree rewrite merely because an ancestor path changed.

### 4. Initial NTFS enumeration

Use the official Windows mechanism validated in M01, such as `FSCTL_ENUM_USN_DATA`, through thin Windows interop.

Initial indexing must:

- parse the required record versions safely;
- stream or batch records into persistence;
- keep memory bounded independently of total namespace size to a reasonable degree;
- avoid accumulating the full namespace as a `List<UsnRecord>` or equivalent before writing;
- use transactions/batches that provide useful throughput without turning the complete full-volume build into one fragile unbounded in-memory operation.

The exact batch size is an implementation detail and should be selected from simple measured behavior rather than speculative tuning.

### 5. Path reconstruction

Implement production path reconstruction from the persistent parent-ID + name model.

It must support:

- reconstructing representative file paths after the process has been closed and restarted;
- detecting missing-parent and cyclic/corrupt parent relationships rather than looping indefinitely;
- clear diagnostics when a path cannot be reconstructed completely.

Path reconstruction exists for correctness/diagnostic validation in M02. It is not yet the M04 search result pipeline.

### 6. Safe initial build and rebuild

A partially built index must never be reported as a complete usable index.

Implement explicit build state or equivalent transactional metadata so that:

- a fresh build starts in a non-complete state;
- successful completion marks the new index complete only after all durable work required by M02 has succeeded;
- interruption, crash, or ordinary process termination during build cannot leave the database looking valid merely because a SQLite file exists;
- `status` can distinguish complete, incomplete/failed, and absent indexes;
- rebuilding an existing index does not silently destroy the last known complete state before a replacement is ready, unless an equally safe transactional strategy is demonstrated.

Prefer a simple replacement/staging strategy if it provides clearer failure semantics than a complicated in-place rebuild.

Do not implement M03 journal replay or crash-consistent USN mutation/checkpoint transactions yet.

### 7. Future checkpoint metadata boundary

The schema/design must leave an explicit place for later M03 continuity metadata, including conceptually:

```text
volume identity
USN Journal ID
next USN
relevant readable-range metadata
```

M02 may persist current journal metadata as diagnostic/build provenance when cheap and useful, but it must not claim that a stored checkpoint is a valid incremental-replay checkpoint unless M03 semantics are implemented.

Do not prematurely freeze the complete M03 recovery algorithm.

### 8. Diagnostic CLI

Provide a small English-language CLI sufficient to drive and verify M02.

Required operations should cover at least:

- build an initial index for a selected volume;
- inspect index status;
- rebuild the selected volume index;
- report record count and relevant build metadata;
- reconstruct/show a path for a selected known record or another deterministic diagnostic lookup suitable for validation.

Exact command names and argument syntax are implementation details. Keep the CLI thin and predictable.

Search/ranking/query-language behavior belongs to M04 and must not be introduced here.

## Persistence design constraints

The persistence design must satisfy the following:

- SQLite-backed;
- schema is versioned from the beginning using a simple explicit schema-version mechanism;
- identifiers preserve their native width without numeric truncation;
- parent relationships are indexable efficiently enough for path reconstruction and later namespace updates;
- database invariants and uniqueness rules are explicit;
- incomplete builds are distinguishable durably;
- ordinary SQLite durability features are used rather than custom storage machinery;
- no FTS table or search-specific index unless strictly required for a diagnostic operation, which is not expected.

Do not optimize schema size prematurely at the expense of correctness or inspectability.

## Test environments

### Quail-Lab

`Quail-Lab` remains the preferred environment for repeatable elevated NTFS testing.

Before M02 execution:

- ensure the VM has a clean `main` clone at the approved M02 baseline;
- verify `QUAIL_LAB_DATA` exists, is healthy, and is NTFS;
- verify passwordless SSH and the elevated remote token;
- verify .NET 10, Git, and GitHub CLI;
- create a new Hyper-V checkpoint named `M02-clean` from the intended M02 baseline before milestone operations that materially alter the reusable lab state.

Do not delete or overwrite `M01-clean` as part of M02.

Use a deterministic controlled namespace on `QUAIL_LAB_DATA` for correctness testing. Codex may recreate controlled test data on the disposable VM data disk after positively identifying it by label.

### Physical host

Use the physical Windows 11 host for one representative full `C:` initial-index build and resource measurement after correctness is established in the VM.

The physical host remains user-controlled for elevated volume access. Codex must not obtain unrestricted administrative execution on the physical host.

If the production-oriented M02 indexer still requires elevated physical-host access, Codex must provide exact read-only commands for the user to execute manually.

The physical `C:` volume must not be reformatted, repartitioned, have its USN Journal reset, or be subjected to destructive storage operations.

## Controlled dataset

Use a deterministic dataset on `QUAIL_LAB_DATA`, for example:

```text
Quail-M02-Test/
  alpha/
    alpha-one.txt
    alpha-two.bin
  beta/
    nested/
      nested-one.txt
  empty/
  root-file.txt
```

The test should know the expected parent relationships and representative reconstructed paths.

The dataset should include at least files, directories, nesting, and an empty directory. File contents are unimportant.

## Representative host measurement

For T10, record at least:

- Windows build;
- .NET version;
- physical volume identity and current mount point;
- number of indexed records;
- wall-clock build time;
- process CPU time;
- peak working set;
- resulting SQLite database size;
- SQLite journal mode and material persistence settings relevant to the measurement;
- parsing/unsupported/error counts;
- final complete/incomplete state.

One representative successful physical-host build is sufficient for M02 unless an obvious anomaly requires repetition. M02 is not a benchmark competition.

The key resource question is whether the streaming/batched implementation materially avoids the M01 probe's full-namespace memory materialization pattern.

Do not define an arbitrary PASS threshold. Interpret the measurements against Quail's lightweight design goals and document any concern for later optimization.

## Out of scope

M02 must not implement:

- USN-driven incremental index mutations;
- create/delete/rename/move journal processing;
- restart journal catch-up;
- journal reset/overwrite recovery beyond storing clearly non-authoritative build provenance where useful;
- crash-consistent atomic coupling of USN checkpoints with index mutations;
- a production Windows Service;
- production IPC between privileged and user processes;
- simultaneous multi-volume indexing/orchestration;
- user-facing file search;
- ranking;
- query syntax;
- FTS5, trigram indexing, or another search engine decision;
- M05 metadata filters;
- launcher GUI;
- global hotkey;
- tray/settings UI;
- installer/updater;
- application/browser/utility providers;
- content indexing;
- network/cloud filesystem indexing;
- dynamic/third-party plugin infrastructure;
- custom NTFS parsing;
- native C++/Rust;
- speculative cross-platform abstractions;
- unrelated performance optimization.

## Acceptance criteria

M02 is complete only when all applicable criteria below are satisfied with durable evidence.

1. Production-oriented `Quail.Core` and thin `Quail.Cli` projects build on the .NET 10 Windows baseline, with automated core tests.
2. A selected local NTFS volume can be validated and identified independently of only its drive letter.
3. A fresh SQLite database can be created with an explicit schema version and durable build state.
4. Initial namespace enumeration writes records incrementally/streamingly or in bounded batches rather than materializing the complete namespace before persistence.
5. Native file and parent identifiers persist without width truncation, including representation compatible with M01's 128-bit v3 finding.
6. The canonical namespace representation is parent identifier + name rather than persisted full paths.
7. Representative paths can be reconstructed correctly after closing and reopening the database.
8. Missing-parent/cycle corruption cannot cause infinite path reconstruction and produces a clear diagnostic result.
9. A successful build becomes complete/usable only after all required work is durably finished.
10. An interrupted/failed build is never reported as a complete usable index.
11. Rebuild semantics preserve a valid previous state until a replacement is safely usable, or provide an equivalently safe documented atomic strategy.
12. The controlled Quail-Lab dataset is indexed and validated successfully using real NTFS enumeration.
13. A representative physical-host `C:` initial build completes and records time, CPU, peak working set, record count, and DB size.
14. The physical-host measurement demonstrates bounded/streamed memory behavior rather than the M01 probe's full-list architecture, with any remaining memory concern documented rather than hidden.
15. `status` diagnostics can distinguish absent, incomplete/failed, and complete indexes and report useful volume/build metadata.
16. M02 does not claim incremental correctness or a valid USN replay checkpoint; those remain M03 responsibilities.
17. `docs/milestones/M02-results.md` records the verified behavior, measurements, limitations, and concrete implications for M03.

A successful build alone is not completion.

## Stop conditions

Stop instead of expanding the milestone if any of the following becomes true:

- the approved namespace model cannot represent a real case encountered during M02 without a material redesign;
- preserving native identifier width would require an architectural change that conflicts with canonical project direction;
- SQLite proves unsuitable for the required persistent namespace semantics based on reproducible evidence;
- official Windows enumeration APIs no longer provide the required data;
- a custom NTFS parser or native C++/Rust component appears necessary;
- production Windows Service or IPC implementation becomes necessary to satisfy M02 rather than merely to automate host elevation;
- correct M02 behavior would require implementing USN incremental mutation logic from M03;
- safe rebuild/incomplete-build semantics cannot be achieved without a materially larger architecture than approved;
- a required physical-host test would need destructive storage action;
- target volume identity is ambiguous before any operation that changes disposable lab data;
- required lab/system access is unavailable;
- canonical project documents conflict;
- unrelated local worktree changes are present at milestone start;
- evidence reveals a material architecture/correctness problem that should be reviewed before proceeding.

When stopping, preserve useful evidence and state the exact blocker and decision required.
