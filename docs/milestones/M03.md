# M03 — Incremental correctness

## Goal

Maintain the persistent NTFS namespace index introduced in M02 from the USN Change Journal with correct restart catch-up, continuity validation, and crash-consistent checkpoint advancement.

M03 proves incremental correctness for one local NTFS volume. It adds one-shot synchronization and safe rebuild handoff, but it does not yet introduce a production Windows Service, background watcher, polling loop, search, GUI, or installer.

## Inputs from earlier milestones

M03 must preserve the verified findings from `docs/milestones/M01-results.md` and `docs/milestones/M02-results.md`:

- official Windows APIs remain the source of truth for NTFS namespace enumeration and journal reads;
- `FSCTL_ENUM_USN_DATA` returned USN v2 in M01/M02 while journal reads returned USN v3;
- native identifiers must preserve their width, including 128-bit identifiers from USN v3;
- multiple USN records may represent one logical user operation;
- rename emits `RENAME_OLD_NAME` and `RENAME_NEW_NAME` records;
- journal continuity requires at least stable volume identity, Journal ID, a saved next-USN position, and readable-range validation;
- Journal ID mismatch or a saved position before the current readable range requires rebuild;
- malformed or unsupported required records must fail closed rather than silently advancing state;
- the persistent namespace representation is parent identifier + name rather than canonical full-path storage;
- M02 uses SQLite, staged replacement, explicit build state, and schema versioning;
- M02 does not yet claim a valid replay checkpoint or incremental correctness.

## Interim project boundary

`Quail.Core` is an interim project boundary inherited from M02. Its current contents must not be treated as a declaration that all future file-index, provider, or application-core functionality belongs in that project.

M03 must not introduce generic provider/plugin abstractions or perform a speculative project split. The separation between the NTFS index backend, the file-search domain/provider, and shared application-level core will be reassessed when the search layer becomes active, most naturally around M04 or the following cleanup boundary.

The future product model may use multiple file-index backends, including the service-backed NTFS/MFT/USN backend for full mode and a different limited backend for per-user mode, while exposing file results through one logical file-search provider. That future distinction does not change M03 scope.

## Scope

### 1. One-shot incremental synchronization

Add a thin one-shot synchronization operation for one selected local NTFS volume and one existing index database.

The operation must:

- validate the selected volume against the index's persisted stable volume identity;
- query the current USN Journal;
- validate continuity before applying changes;
- read journal records from the persisted checkpoint;
- apply namespace mutations to SQLite;
- advance the persisted checkpoint only as part of the same durable transaction as the mutations it covers;
- stop when the currently readable change stream has been consumed;
- exit rather than remaining resident.

Do not add a daemon, service loop, polling loop, timer, filesystem watcher, scheduler, or autostart behavior in M03.

### 2. Authoritative checkpoint and consistency frontier

Introduce an authoritative incremental checkpoint for schema version 2.

Persist at least the information needed to validate and resume continuity:

- stable volume identity;
- USN Journal ID;
- next USN;
- relevant readable-range provenance such as `FirstUsn` and `LowestValidUsn` where useful for diagnostics/validation;
- journal record-version compatibility metadata only if materially useful.

Checkpoint semantics:

> The persisted `next USN` means all required journal records before that position have been successfully applied to the persistent namespace state in the same durable SQLite history.

A checkpoint must never advance ahead of the mutations it represents.

### 3. Crash-consistent mutation batches

For each persisted journal batch:

1. begin a SQLite transaction;
2. apply all parsed namespace mutations represented by the batch;
3. update the authoritative checkpoint to the returned/read cursor covered by that batch;
4. commit once.

If the process fails before commit, neither the mutations nor the checkpoint advancement may become visible.

After restart, replaying the same unread range must be safe and must converge to the same namespace state.

Use ordinary SQLite transactional guarantees. Do not build custom journaling or storage machinery.

### 4. Initial-build to incremental handoff

A schema-v2 initial build/rebuild must establish a journal-consistent handoff rather than attaching an arbitrary checkpoint after MFT enumeration.

Use a simple safe sequence equivalent to:

1. query journal state and record the starting Journal ID and `NextUsn`;
2. perform the initial MFT/namespace enumeration using the official mechanism validated by M01/M02;
3. re-query/validate journal continuity after enumeration;
4. replay journal changes from the recorded starting `NextUsn` through the current readable frontier;
5. atomically persist final replayed mutations and the resulting authoritative checkpoint;
6. only then mark/promote the staging index as complete.

The exact batching and implementation details are routine implementation choices, but the resulting state must not contain an unclosed mutation window between the initial enumeration and the first incremental checkpoint.

If the Journal ID changes during the build, the starting position becomes unreadable, or another continuity condition becomes invalid, do not promote the staging index as complete.

### 5. Schema version 2

M03 introduces schema version 2 for authoritative incremental state.

An existing schema-v1 M02 index has no valid incremental checkpoint. M03 does not need a general migration framework.

Preferred behavior:

- detect schema v1 explicitly;
- report that rebuild is required because no authoritative incremental checkpoint exists;
- rebuild safely through the normal schema-v2 staging path;
- preserve the prior complete database until the schema-v2 replacement is ready.

Do not retrofit a guessed checkpoint into a schema-v1 index.

### 6. Incremental namespace mutation semantics

Process USN records as a change stream, not as one-record-per-user-action events.

At minimum, M03 must correctly maintain the namespace for:

- file creation;
- directory creation;
- deletion;
- rename;
- move between directories;
- directory rename/move without descendant subtree rewrites;
- ordinary records for already-existing objects where refreshing the current file ID / parent ID / name / attributes is necessary to converge after initial-build handoff or restart catch-up.

Do not require a fragile in-memory rename-pair aggregation across buffers or process lifetimes.

A simple idempotent model is preferred where:

- delete / old-name semantics remove the prior namespace entry when appropriate;
- new-name / create / relevant existing-object records upsert the current namespace entry;
- repeated replay of an uncommitted batch converges safely.

Exact handling must follow the actual USN reason flags and data available from the official API rather than assuming one logical operation maps to one record.

### 7. Journal record compatibility

M03 must correctly parse and preserve the identifier widths required by the journal records it requests.

The validated baseline is USN record major versions 2 and 3.

- explicitly negotiate/request only versions the production parser supports where the Windows API allows this;
- malformed required records fail closed;
- unsupported required record versions fail closed;
- failure must not advance the authoritative checkpoint;
- USN v4 support is not required in M03.

Document the bounded v4 limitation in M03 results.

### 8. Continuity validation and rebuild-required state

Before applying incremental changes, validate at least:

- index schema supports an authoritative checkpoint;
- selected volume identity matches the persisted volume identity;
- current Journal ID matches the saved Journal ID;
- saved `next USN` is not invalid relative to the current readable range;
- the journal read operation can actually resume from the saved position.

`FSCTL_READ_USN_JOURNAL` behavior remains the authoritative runtime test of whether the saved position is readable.

If continuity is lost:

- do not apply partial incremental mutations as though the index were current;
- do not advance the checkpoint;
- report an explicit `rebuild-required` state and diagnostic reason;
- retain the prior database physically where useful, but do not present it as a current usable index;
- a later rebuild must use the safe schema-v2 staged build/handoff path.

Required rebuild reasons should include at least:

- schema lacks authoritative checkpoint;
- volume identity mismatch;
- Journal ID mismatch;
- saved USN before the readable range / unreadable saved position;
- another verified continuity failure returned by the Windows API.

### 9. Diagnostic CLI

Extend the existing thin English-language CLI only as needed for M03.

Required operations should cover at least:

- existing build/rebuild;
- `sync` or an equivalent one-shot incremental catch-up command;
- status showing incremental readiness/currentness and checkpoint metadata useful for diagnostics;
- existing path diagnostics.

Exact command names/argument syntax are implementation details.

Status must make it possible to distinguish at least:

- absent index;
- incomplete build;
- complete/current schema-v2 index with authoritative checkpoint;
- rebuild-required index with a clear reason.

Do not add search/query behavior from M04.

### 10. Deterministic test seams

Automated tests may use small explicit seams for:

- parsed journal-record batches;
- deterministic transaction failure before commit;
- continuity metadata validation;
- malformed/unsupported record parsing.

Do not introduce a general fault-injection framework or large abstraction layer merely for testing.

## Hard-link limitation

The current M02 namespace schema uses one `file_id` primary key with one parent/name entry. NTFS hard links can expose multiple namespace entries that refer to one underlying file record.

M03 does not expand scope to solve general hard-link representation unless the approved mutation model cannot correctly satisfy the milestone without doing so.

Do not claim complete general NTFS namespace correctness for hard-link cases that the schema cannot represent.

If real M03 evidence shows that hard-link semantics materially invalidate the approved parent-ID + name model or ordinary create/delete/rename/move correctness, stop and report the architectural decision required instead of silently redesigning the schema.

Record the verified limitation explicitly in `M03-results.md`.

## Test environment

### Quail-Lab

Use `Quail-Lab` for repeatable elevated and restart-sensitive NTFS tests.

Before M03 runtime work:

- physical-host and VM repositories must both be on clean, current `main` containing the M02 merge and the approved M03 specification;
- verify the disposable data volume positively by label `QUAIL_LAB_DATA`, filesystem type NTFS, health, and current drive letter;
- verify passwordless SSH and elevated remote token;
- verify .NET 10, Git, and GitHub CLI;
- create a new Hyper-V checkpoint named `M03-clean` from the intended clean M03 baseline before milestone operations materially change reusable lab state;
- do not delete or overwrite `M01-clean` or `M02-clean`.

Do not assume the VM's IP address or the data disk's drive letter. Discover both when needed.

Controlled test data may be created, changed, renamed, moved, and deleted autonomously on the positively identified disposable `QUAIL_LAB_DATA` volume.

Restart/catch-up tests may stop the Quail process or power/restart the VM when the milestone test requires it, subject to the repository safety rules. Do not restore a checkpoint in a way that discards work without explicit approval.

### Physical host

A physical-host full-volume benchmark is not required for M03.

M01 already verified physical-host journal access and M02 verified physical-host persistent initial indexing. M03's core risk is incremental correctness and crash/restart behavior, for which the controlled VM is the primary acceptance environment.

A small optional host smoke test may be performed if it adds useful evidence without expanding scope, but it is not required for completion and must not require destructive host operations.

Do not obtain unrestricted administrative execution on the physical host.

## Controlled runtime scenarios

Use deterministic Quail-Lab operations that exercise at least:

- create a file;
- create a directory;
- modify an existing object sufficiently to produce relevant journal records;
- rename a file;
- move a file between directories;
- rename a directory containing descendants;
- move a directory containing descendants;
- delete a file;
- delete a controlled directory/tree;
- stop the Quail process, make filesystem changes, restart/sync, and verify catch-up;
- deliberate continuity loss / mismatch scenarios using the disposable lab journal where safe;
- safe rebuild after continuity loss.

Verify resulting persistent namespace state and representative reconstructed paths after process reopen.

## Acceptance criteria

M03 is complete only when all applicable criteria below are satisfied with durable evidence.

1. Existing M02 production structure remains simple; no speculative service/provider/plugin framework is introduced.
2. Schema version 2 persists an authoritative incremental checkpoint including stable volume identity, Journal ID, and next USN without identifier truncation.
3. A schema-v1 M02 index is detected as lacking an authoritative checkpoint and requires safe rebuild rather than guessed migration state.
4. One-shot sync validates volume and journal continuity before applying changes.
5. Journal records required by the supported path are parsed fail-closed; malformed/unsupported records cannot advance the checkpoint.
6. Namespace mutations and checkpoint advancement are committed atomically in SQLite.
7. Failure before commit leaves both namespace state and checkpoint at the prior durable frontier and permits safe replay after restart.
8. Create/delete/rename/move operations on controlled files are reflected correctly after sync.
9. Directory rename/move updates ancestor namespace state without rewriting all descendant rows, while reconstructed descendant paths change correctly.
10. Restart catch-up recovers changes made while Quail is not running.
11. Journal ID mismatch, unreadable/expired saved position, volume mismatch, and other verified continuity failures produce explicit `rebuild-required` behavior without pretending the stale index is current.
12. Safe schema-v2 rebuild establishes a journal-consistent initial-build handoff and does not expose an enumeration-to-checkpoint mutation gap as complete state.
13. Rebuild preserves the previous complete database until the replacement has become a valid schema-v2 complete index with authoritative checkpoint.
14. Quail-Lab runtime evidence covers T06–T14 on real NTFS using the positively identified disposable data volume.
15. `docs/milestones/M03-results.md` records exact behavior, checkpoint semantics, verification results, limitations, hard-link caveat, and implications for later service/lifecycle work.
16. M03 does not introduce background monitoring, production service/IPC, search, GUI, installer, or M04+ functionality.

A successful build or one successful sync alone is not completion.

## Stop conditions

Stop instead of expanding the milestone if any of the following becomes true:

- the current namespace schema cannot correctly represent an ordinary required M03 create/delete/rename/move case without material redesign;
- hard-link behavior encountered in required tests materially invalidates the approved namespace model;
- preserving 128-bit identifiers conflicts with the current architecture;
- Windows journal APIs do not provide the data/continuity semantics needed for the approved checkpoint model;
- crash-consistent mutation + checkpoint persistence cannot be achieved with straightforward SQLite transactions;
- safe initial-build-to-journal handoff would require a materially larger architecture than approved;
- production Windows Service/IPC is required for correctness rather than merely future privilege separation;
- USN v4 support becomes required to pass the actual selected Windows runtime path rather than remaining a bounded future compatibility issue;
- a custom NTFS parser or native C++/Rust component appears necessary;
- a required test would need destructive physical-host storage/journal operations;
- the disposable VM target cannot be identified unambiguously;
- required VM/system access is unavailable;
- canonical project documents conflict;
- unrelated local worktree changes are present;
- evidence reveals another material architecture/correctness problem that should be reviewed before proceeding.

When stopping, preserve useful evidence and state the exact blocker and decision required.
