# M04.5 Results — Developer Agent Tooling v1

## Status

**Verified.** M04.5 adds two small, provider-neutral PowerShell entry points for recurring implementation-agent work. They do not change Quail product behavior, indexing, search, architecture, CI/CD, release handling, or safety gates.

## Public entry points

### Repository preflight

```powershell
.\scripts\agent-preflight.ps1 `
  [-ExpectedBranch <branch>] [-RequireClean] [-RequireCurrentOrigin] [-CheckTools]
```

`agent-preflight.ps1` derives the repository root from `$PSScriptRoot`. It reports branch, full HEAD, clean state, origin configuration, and optional tool availability in one line. With `-RequireCurrentOrigin`, it performs an ordinary `git fetch origin` only after confirming that the worktree is clean, then rejects a branch that is behind or diverged from `origin/main`; a local branch ahead of `origin/main` remains current because it has no missing main commits. With `-CheckTools`, it verifies Git, .NET, SSH/SCP, PowerShell, and the Hyper-V network cmdlet.

Success contract:

```text
PASS branch=<branch> head=<full-sha> clean=<true|false> current=<true|unchecked> tools=<ok|unchecked> origin=configured
```

Failure contract: exit code `1`, a one-line `FAIL reason=<reason> log=<local-path>` summary, and a detailed ignored local log under `.quail-tooling/`. It never stashes, resets, cleans, switches branches, pulls, or otherwise changes user work.

### Quail-Lab bounded verification

```powershell
.\scripts\vm-verify.ps1 `
  -VmUser <lab-user> -ArtifactPath <repository-relative-file> `
  [-VmName Quail-Lab] [-Scenario CliStatus] `
  [-DataVolumeLabel QUAIL_LAB_DATA] [-RemoteRoot C:/Temp/Quail-M04.5]
```

`vm-verify.ps1` dynamically reads the named VM's current IPv4 addresses through Hyper-V, probes SSH using the supplied lab user, and explicitly runs remote `powershell -NoProfile`. It positively selects exactly one healthy NTFS volume by label, deploys the requested repository-relative artifact file with SCP, compares local and remote SHA-256 values, and runs the bounded `CliStatus` smoke scenario against a temporary database on the disposable data volume.

The v1 contract deliberately accepts one file artifact. A self-contained single-file CLI publish is sufficient for the implemented smoke path; directory manifests and milestone-specific deployment layouts were not added before they have repeated use.

Success contract:

```text
PASS vm=<name> ssh=true volume=<label> artifactSha256=<sha256> scenario=CliStatus
```

Failure contract: exit code `1`, a one-line `FAIL reason=<reason> log=<local-path>` summary, and a detailed ignored local log under `.quail-tooling/`. The script does not restore, delete, or overwrite checkpoints; it does not perform Git or release operations. It needs normal Hyper-V access, existing SSH authentication/host-key trust, and an explicit `-VmUser`; no credentials are stored in the repository.

## Practical workflow reduction

| Workflow | Before M04.5 | With M04.5 | Approval and context effect | Residual manual/elevated work |
|---|---:|---:|---|
| Repository preflight | About 5–6 separate calls: branch, HEAD, status, origin/fetch, ref comparison, and tool checks. | 1 canonical call. | One supported command can be approved as a unit where an environment requires approval. Success returns one stable line instead of command-by-command output. | The agent still decides whether a reported non-current baseline may safely be synchronized; the script does not pull or change branches. |
| Quail-Lab bounded smoke | About 7–9 calls: Hyper-V address lookup, SSH probe, remote PowerShell, volume lookup, artifact copy, two hashes, smoke command, and evidence collection. | 1 canonical call. | Hyper-V/SSH/deploy operations are authorized and observed as one bounded procedure. Success returns one stable line; detailed SSH/SCP/remote output stays local. | Hyper-V access, SSH authentication and host-key trust, building/publishing a chosen artifact, and any milestone-specific destructive/elevated test remain explicit. |

Exact token counts were not inferred or claimed. The measured benefit is fewer separate calls, fewer repeated command-construction decisions, fewer individual approval surfaces in constrained environments, and substantially less routine success output returned to the implementation-agent context.

## Deliberately not automated

- host benchmark/evidence collection from the M04 observations, because it is not yet repeated enough to justify a third public entry point;
- directory artifact manifests and future installer/package layouts;
- M05/M06/M07 verification scenarios;
- Git synchronization, branch switching, commits, pushes, PR creation, checkpoint creation, restore/delete, release/tag operations, or any destructive/publication-sensitive action.

## Reusable observations for later milestones

The implemented preflight and bounded VM smoke are now canonical supported procedures. Future milestone handoffs should record any newly repeated deterministic workflow (for example a stable benchmark suite or a genuinely repeated multi-file deployment layout) and quantify its saved calls or context before extending tooling. A one-off convenience helper remains insufficient justification.
