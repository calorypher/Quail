# M04.5 — Developer Agent Tooling v1

## Goal

Reduce implementation-agent tool calls, repeated reasoning, approval friction, and unnecessary output by moving a small set of deterministic, repeatable Quail development procedures into local repository scripts.

M04.5 is a tooling milestone only. It must not change Quail product behavior or architecture. The tooling should be provider-neutral so that the same repository entry points can be used by Codex, Claude Code, or another implementation agent.

The design principle is minimal automation with high return: prefer a few canonical entry points that collapse several repeated Git/PowerShell/Hyper-V/SSH/deploy/verification steps into one deterministic operation, rather than a broad framework or many tiny helpers.

## Inputs from M04

`docs/milestones/M04-results.md` recorded repeated operational sequences that are candidates for automation:

- repository/Git preflight;
- host/VM synchronization and checkpoint guard checks;
- dynamic Quail-Lab IP discovery and SSH/PowerShell invocation;
- artifact deployment with hash verification;
- controlled Quail-Lab runtime verification;
- physical-host benchmark/evidence collection.

M04.5 must use these observations as evidence, but it must not implement every candidate merely because it was listed. Choose the smallest set of entry points that removes the most repeated agent work without creating a general-purpose framework.

## Scope

### 1. Canonical repository preflight

Add one repository-local PowerShell entry point, expected to be named `scripts/agent-preflight.ps1` unless implementation evidence justifies a clearer equivalent name.

It should cover the deterministic checks that implementation agents repeatedly perform before milestone work, including as applicable:

- discover the repository root relative to the script location rather than an absolute developer path;
- current branch;
- exact HEAD;
- clean/dirty worktree state;
- configured `origin` and relationship to `origin/main` after an ordinary fetch when safe;
- ahead/behind/diverged status sufficient to detect an unsuitable baseline;
- presence of required development tools used by the current Quail workflow, such as Git, .NET, PowerShell, SSH, and Hyper-V tooling where applicable;
- concise validation of the reusable Quail-Lab environment when requested or naturally cheap to include.

The script must return a stable compact summary and meaningful process exit code.

It must not perform destructive Git operations. Routine non-destructive synchronization may be performed only when explicitly part of the approved script contract and when failure cannot hide local work; otherwise the script should report the state and let the implementation workflow decide the next safe action.

### 2. Canonical Quail-Lab verification entry point

Add one main repository-local PowerShell entry point for routine Quail-Lab work, expected to be named `scripts/vm-verify.ps1` unless implementation evidence justifies a clearer equivalent name.

The entry point should replace the repeated sequence of manually discovering VM state/IP, establishing SSH, switching from the default remote `cmd.exe` shell to PowerShell when required, locating the disposable data volume, deploying an artifact, executing a routine verification scenario, and collecting evidence.

At minimum, it should be capable of:

- locating the intended Hyper-V VM through a stable project identifier such as the configured/default `Quail-Lab` name;
- discovering the current dynamic IP rather than requiring the model to know or persist it;
- verifying SSH reachability;
- invoking remote PowerShell explicitly where PowerShell cmdlets are required;
- positively identifying the disposable NTFS data volume by label `QUAIL_LAB_DATA` rather than assuming a drive letter;
- deploying a requested repository-relative build artifact or artifact directory when verification requires deployment;
- verifying artifact integrity using SHA-256 or an equivalently simple deterministic check;
- running a bounded routine verification operation selected through a simple script contract;
- collecting detailed output to a local log/evidence file;
- printing only a compact stable PASS/FAIL summary on the normal success path.

The first version does not need to encode all future milestone-specific verification logic. A simple bounded mode or command contract is sufficient if it proves that one entry point can perform a real current Quail-Lab smoke/regression workflow without repeated manual SSH/SCP/PowerShell orchestration.

If a milestone later introduces a new repeatable workflow, extend the canonical tooling only when real repetition demonstrates value. Do not predictively add M05/M06/M07-specific scenarios in M04.5.

### 3. Compact output and detailed failure evidence

Repository tooling should optimize what returns to the implementation-agent context.

Success behavior:

- stdout should be short, stable, and machine/agent-friendly;
- include only the key state needed for the next decision, for example branch/HEAD/clean/current, VM reachable, discovered volume label, artifact hash, verification result;
- do not echo long command output when the operation succeeded.

Failure behavior:

- return a non-zero process exit code;
- include a concise primary failure reason;
- preserve detailed diagnostics in a local log/evidence file;
- print the log path so the agent can inspect it only when needed;
- avoid exposing secrets or unnecessarily dumping private host paths/data into durable repository evidence.

Logs generated by routine local development tooling must not be committed by default. Use a repository-local ignored output directory or an appropriate local temporary directory.

### 4. Machine-independent repository tooling

Scripts committed to the repository must not encode developer-specific machine details.

Do not hard-code:

- developer usernames;
- absolute clone paths such as a specific `C:\Users\...\Quail` location;
- VM IP addresses;
- disposable-volume drive letters;
- secrets, tokens, passwords, or account-specific credentials;
- arbitrary local artifact paths outside the repository.

Prefer:

- `$PSScriptRoot` and paths derived from the repository layout;
- dynamic discovery;
- stable project identifiers where the lab contract intentionally defines one;
- explicit command-line parameters for values that legitimately vary;
- optional ignored local configuration only when a machine-specific value cannot reasonably be discovered or passed as an argument.

The scripts must be usable after cloning/copying the repository to a different filesystem path without source edits.

### 5. Provider-neutral agent workflow in `AGENTS.md`

Update `AGENTS.md` so repository workflow terminology does not depend on Codex as the implementation provider.

Use a neutral role such as `implementation agent` where the rule applies equally to Codex, Claude Code, or another agent.

Document that:

- the implementation agent is the default owner of routine non-destructive Git lifecycle work when it has access, including branch creation, fetch/pull where safe, clean-state verification, commits, pushes, and PR creation;
- the user should not be asked to perform routine Git commands manually when the agent can perform them safely;
- the implementation agent should perform routine non-destructive host/VM milestone preparation when access is available;
- canonical repository scripts must be used instead of manually reconstructing an equivalent supported procedure, unless the script itself is being debugged or the required case is outside its documented contract;
- existing explicit safety gates remain authoritative and unchanged for merge, branch deletion, force-push, destructive reset/clean, history-rewriting rebase, tags/releases, destructive checkpoint actions, and other gated operations.

Do not turn `AGENTS.md` into a provider-specific tool manual.

### 6. Measure practical workflow reduction

Record before/after evidence for the implemented entry points.

For each automated workflow, capture approximately:

- the prior number of separate commands/tool calls or agent interaction steps;
- the new number of entry-point calls;
- whether approvals were reduced;
- whether routine detailed output no longer returns to the model on success;
- any important residual manual/elevated step that remains unavoidable.

This is an engineering comparison, not a precise token-accounting benchmark. If practical, record the user's observed weekly Usage trend qualitatively, but do not invent token counts that cannot be measured reliably.

Create `docs/milestones/M04.5-results.md` with the final tooling decision and evidence.

### 7. Future scriptable-workflow observation rule

Establish a lightweight durable process for later milestones:

- final milestone handoffs should note newly observed repeatable/deterministic/scriptable operational sequences when they are materially useful;
- do not automatically implement tooling inside an unrelated product milestone;
- prefer adding tooling only after repetition/evidence shows a meaningful reduction in agent calls, approvals, context volume, or user manual work;
- avoid accumulating one-off helper scripts whose maintenance cost exceeds the saved work.

This rule should be recorded in `AGENTS.md` in concise form if it fits naturally with the milestone workflow section.

## Implementation shape

Prefer approximately two public/canonical script entry points for v1:

- repository/agent preflight;
- Quail-Lab routine verification/orchestration.

This is a directional preference, not a rigid file-count requirement. If implementation evidence shows that one additional small shared module or internal helper is materially cleaner, it is allowed. Conversely, if one entry point can safely cover more of the workflow without becoming a general framework, prefer the simpler public surface.

Private PowerShell functions or a small internal script module may be used to avoid duplicated implementation details. Do not expose a large set of tiny public helper scripts merely because the M04 observations listed several sub-steps.

## Test environment

### Physical host

The tooling is primarily executed from the physical Windows development host because Hyper-V and Quail-Lab are managed there.

M04.5 may perform ordinary non-destructive Git, Hyper-V discovery, SSH, build, deployment, and controlled lab verification operations.

The physical host remains not an unrestricted administrative sandbox. Do not perform destructive host filesystem/journal operations merely to test tooling.

### Quail-Lab

Use the existing reusable `Quail-Lab` VM and positively identified `QUAIL_LAB_DATA` disposable NTFS volume for real verification.

Do not assume:

- the VM's current IP address;
- the data volume's drive letter;
- that the remote SSH shell is PowerShell.

Do not delete or restore existing milestone checkpoints as part of routine tooling verification.

Creating a new M04.5-specific checkpoint is not required merely to test non-destructive tooling. If the implementation agent believes a new checkpoint is materially necessary, it must follow the existing project safety/workflow rules and avoid overwriting any existing checkpoint.

## Acceptance criteria

M04.5 is complete only when all applicable criteria below are satisfied:

1. At least one canonical repository preflight entry point exists and replaces several repeated manual/agent checks with one deterministic call.
2. At least one canonical Quail-Lab orchestration/verification entry point exists and replaces a meaningful multi-step SSH/PowerShell/deploy/verification sequence with one call.
3. Normal successful execution produces compact stable summaries rather than returning full logs to the model.
4. Detailed diagnostics are preserved locally and surfaced by path when a failure requires investigation.
5. Scripts derive repository paths from their own location or explicit parameters and work when the repository is located at a different path.
6. No committed script hard-codes developer-specific usernames, clone paths, VM IPs, disposable-volume drive letters, secrets, or tokens.
7. Dynamic Quail-Lab IP discovery and SSH verification work on the real reusable VM.
8. The disposable lab volume is identified by `QUAIL_LAB_DATA` and verified as NTFS rather than assumed by drive letter.
9. Artifact deployment includes deterministic integrity verification.
10. One real routine Quail-Lab verification scenario completes through the canonical entry point and retains failure evidence correctly.
11. The tooling does not perform or silently authorize destructive/publication-sensitive Git, checkpoint, release, or host operations.
12. `AGENTS.md` uses provider-neutral `implementation agent` terminology for general workflow rules and makes routine non-destructive Git/host/VM mechanics the agent's responsibility where access exists.
13. `AGENTS.md` directs agents to use supported canonical scripts rather than reconstructing equivalent procedures manually, with a narrow debugging/out-of-contract exception.
14. Later milestone handoffs are asked to record materially useful new scriptable workflow observations without automatically expanding the active milestone.
15. `docs/milestones/M04.5-results.md` documents implemented entry points, interfaces, exit/summary/log contracts, verification T01–T13, measured workflow reduction, limitations, and follow-up candidates.
16. No Quail product functionality, index/search semantics, application architecture, CI/CD, or release infrastructure is changed by this milestone.

## Out of scope

M04.5 must not implement:

- M05 metadata-filter functionality or any other Quail product feature;
- changes to file-index/search architecture;
- a cross-project or general agent framework;
- Codex-specific, Claude-specific, or provider-specific APIs;
- local LLM integration;
- CI/CD pipelines;
- full Git lifecycle automation framework;
- automatic PR merge;
- branch deletion;
- force-push;
- destructive reset/clean;
- history-rewriting rebase of published branches;
- automatic release tags or GitHub Releases;
- destructive checkpoint restore/delete/overwrite;
- secret storage in the repository;
- hard-coded developer-machine configuration;
- a large collection of public helper scripts without demonstrated need;
- speculative M05/M06/M07 verification automation before those workflows exist;
- exact token metering infrastructure.

## Stop conditions

Stop instead of expanding the milestone if any of the following becomes true:

- reliable operation would require committing credentials, secrets, or machine-private configuration;
- dynamic VM/IP discovery cannot be made reliable using straightforward supported Windows/Hyper-V/network information and would require brittle heuristic scanning;
- a proposed universal VM runner starts accumulating milestone-specific application logic or becoming a general remote-execution framework;
- the tooling requires a substantial PowerShell framework/module architecture merely to support the approved two-entry-point workflow;
- useful automation requires crossing an existing safety gate or making destructive actions implicit;
- a routine Git helper would need to hide, reset, stash, clean, or overwrite unrelated user work;
- testing path independence reveals unavoidable dependencies on a specific developer clone layout that cannot be replaced by simple parameters/discovery;
- completing the milestone would require changing Quail product behavior or architecture;
- measured workflow reduction is too small to justify the implementation complexity for a proposed entry point; omit that entry point and document the decision rather than building it anyway.

## Deliverables

Expected deliverables are:

- canonical repository-local PowerShell preflight tooling;
- canonical Quail-Lab orchestration/verification tooling;
- any minimal private/shared PowerShell support required by those entry points;
- `.gitignore` updates if required for local logs/evidence;
- provider-neutral workflow updates in `AGENTS.md`;
- `docs/milestones/M04.5-results.md`;
- automated or script-level verification where practical;
- real T01–T13 evidence;
- a branch and PR ready for independent QA.

## Completion boundary

Normal completion is a verified implementation branch plus an open PR ready for independent QA.

Do not merge the PR, delete branches, create/move tags, publish releases, perform destructive Git operations, or delete/restore/overwrite checkpoints without explicit user approval.
