# M04 — Basic search

## Goal

Add the first production file-name search capability over the persistent local NTFS namespace index established by M02 and maintained incrementally by M03.

M04 must prove that Quail can query a realistic persistent index quickly and predictably, with simple filters and measured latency, without introducing smart ranking, metadata filtering, GUI, service/IPC, or additional providers.

## Inputs from earlier milestones

M04 must preserve the verified behavior and constraints recorded in `docs/milestones/M01-results.md`, `docs/milestones/M02-results.md`, and `docs/milestones/M03-results.md`:

- the persistent local namespace index is SQLite-backed;
- namespace identity is stored in the canonical schema-v2 form established by M03;
- path reconstruction uses parent identifiers plus names rather than canonical full-path storage;
- incremental correctness and checkpoint semantics must remain intact;
- schema-v1 and incompatible schema-v2 states require safe rebuild rather than guessed migration;
- M03 intentionally keeps synchronization one-shot and does not add a service, watcher, polling loop, scheduler, or GUI;
- the current namespace model does not provide general NTFS hard-link multiplicity;
- the product remains Windows 11 x64 first, C#/.NET 10, and SQLite-based;
- repository artifacts are English-first;
- `Quail.Core` is still an interim project boundary rather than a permanent declaration of the final provider architecture.

## Architecture boundary for M04

M04 is the first milestone where a real file-search domain becomes active.

Before adding search APIs, inspect the current project structure and decide whether a small, concrete boundary is now justified between:

- NTFS/index persistence and synchronization implementation;
- file-search query/result concepts;
- shared application-level concepts that may later be reused by other providers.

The preferred outcome is the smallest structure that keeps search behavior testable and independent from CLI presentation and Windows UI technology.

Allowed outcomes include:

- leaving `Quail.Core` as the interim boundary if a split would be mostly cosmetic at M04 scale;
- introducing one small file-search-focused project/module or contracts if the separation is already concrete and reduces coupling.

Do not introduce:

- a dynamic provider/plugin framework;
- public extension SDKs;
- provider discovery/loading machinery;
- speculative abstractions for future application/browser/network providers;
- a large project split that is not required by the active search slice.

Record the architecture decision and rationale in `M04-results.md`.

## Scope

### 1. Search source

Search only the existing persistent local NTFS namespace index.

M04 does not add another index source, backend, filesystem scanner, network source, application provider, browser provider, content index, or cloud source.

The search implementation must not require reading file contents or traversing the live filesystem for ordinary queries.

### 2. Name matching

Add case-insensitive file and directory name search.

Required baseline behavior:

- matching is performed against the indexed entry name;
- ordinary substring/partial matching is supported;
- a query such as `report` can match a name such as `Quarterly Report.xlsx`;
- matching semantics are deterministic and documented;
- path text is not required to participate in matching unless evidence shows that doing so is necessary for the approved baseline; do not silently broaden the query model.

The implementation may normalize query input in a minimal predictable way, but M04 must not introduce fuzzy matching, typo correction, token scoring, phonetic matching, stemming, NLP, or smart ranking.

### 3. Result model

Introduce a small search result model sufficient for the file-search slice.

Each result must expose at least:

- canonical file identifier or another stable internal identity needed by the current architecture;
- entry name;
- reconstructed or reconstructable full path;
- whether the entry is a file or directory;
- extension information where relevant to filtering/output.

Do not expose SQLite-specific implementation details as the intended long-term public search contract when a small neutral model is sufficient.

### 4. File/directory filter

Support explicit filtering to:

- files only;
- directories only;
- both, which is the default unless the chosen syntax clearly states otherwise.

The filter must operate in the persistent query rather than fetching a large superset and filtering entirely in memory when SQLite can apply it directly.

### 5. Extension filter

Support a simple extension filter.

Required behavior:

- `ext:pdf` or an equivalently simple documented syntax filters files by extension;
- matching is case-insensitive;
- the user should not need to include the leading dot;
- directories do not match an extension filter;
- multiple-extension grammar is not required unless it falls out naturally without parser complexity.

M04 does not add size, timestamps, attributes, or other M05 metadata filters.

### 6. Simple query syntax

Add a small predictable CLI query syntax.

Preferred shape:

```text
quail search <database-path> <query> [--type file|dir|any] [--ext pdf] [--limit 50]
```

Equivalent syntax is acceptable if it remains simple and unambiguous.

Requirements:

- one plain-text name query;
- file/directory filtering;
- extension filtering;
- result limit;
- invalid combinations fail with concise English diagnostics;
- no general expression language;
- no boolean query parser;
- no nested grammar;
- no quoted-field mini-language unless required by normal shell argument handling.

The CLI remains a thin diagnostic/product-development surface. Search behavior belongs below CLI parsing.

### 7. Result limit and deterministic ordering

Queries must support an explicit maximum result count and a safe default.

Use a deterministic ordering that is simple enough to explain and test.

M04 does not attempt relevance ranking comparable to Spotlight, Alfred, or KRunner.

A preferred baseline is an order based on simple exactness/name properties plus a stable deterministic tie-breaker only if those rules remain obviously non-smart and inexpensive. Pure lexical ordering is acceptable if it satisfies the milestone more cleanly.

Whichever rule is chosen:

- document it;
- test it;
- do not make ordering depend on nondeterministic SQLite row order;
- do not add usage history, recency scoring, path-preference scoring, machine learning, fuzzy-distance scoring, or cross-provider ranking.

### 8. Search implementation decision

Do not assume FTS5, trigram indexing, or plain `LIKE` before measurement.

Start with the simplest SQLite approach that can implement the required semantics correctly.

At minimum:

1. implement or prototype a plain SQLite baseline appropriate for case-insensitive substring name search;
2. measure realistic query latency against a representative physical-host index;
3. inspect query plans/storage impact where useful;
4. only if the baseline is not adequate for the product target, evaluate one focused SQLite-native alternative such as FTS5 with a suitable tokenizer or another SQLite-supported indexing strategy;
5. choose the simpler mechanism when measured behavior is already sufficient.

Do not add a second search engine, external daemon, Lucene-style dependency, custom native extension, or bespoke trigram engine in M04.

If a SQLite-native alternative materially complicates incremental maintenance, storage, rebuild behavior, or correctness, include that maintenance cost in the decision rather than comparing query latency alone.

### 9. Search-index maintenance

Any auxiliary search structure introduced by M04 must remain consistent with the namespace state.

If search uses only the existing namespace table, no additional maintenance path is required.

If an auxiliary SQLite table/index/FTS structure is added:

- initial build/rebuild must populate it consistently;
- incremental M03 mutations must keep it synchronized in the same durable SQLite transaction or through an equivalently crash-consistent mechanism;
- failure before commit must not leave namespace and search state at different logical frontiers;
- safe rebuild semantics must remain intact;
- schema/version compatibility must be explicit.

Do not weaken M03 checkpoint guarantees to improve search latency.

### 10. Latency measurements

Measure realistic search latency on the physical host using its real persistent Quail index.

Use the physical host because M04 risk is realistic query performance at larger index size rather than destructive NTFS behavior.

Measure at least:

- a query with many matches;
- a selective query with few matches;
- a query with no matches;
- file-only filtering;
- directory-only filtering;
- extension filtering;
- repeated warm-cache queries;
- at least one cold-ish/process-reopen measurement if practical without artificial system-wide cache flushing.

Prefer process-level elapsed-time measurement around the search operation rather than fragile microbenchmarks.

Record:

- index record count;
- database size;
- search mechanism evaluated;
- query text/category without recording private filenames unnecessarily;
- result limit;
- representative latency distribution such as median and a reasonable high percentile or max over a bounded run count;
- whether measurements were warm or process-reopened/cold-ish;
- relevant storage/index-size overhead if an auxiliary structure is introduced.

Do not perform destructive host storage operations or unrestricted administrative experimentation.

### 11. Performance target

M04 should establish an evidence-based target rather than optimize for benchmark records.

Acceptance requires that common warm-cache searches on the representative physical-host index feel effectively immediate for a keyboard launcher.

As a working milestone target, aim for:

- median warm search latency comfortably below 50 ms for typical bounded queries on the current physical-host index;
- no common required scenario routinely exceeding 100 ms solely in the search core under normal warm conditions.

These are engineering targets, not immutable product guarantees. If the simplest correct SQLite approach narrowly misses them, measure and compare before adding complexity.

If realistic evidence shows that meeting an acceptable launcher-search latency requires a materially different persistence/search architecture, stop and report the decision instead of building a large unapproved subsystem.

## Test environment

### Physical host

The physical host is the primary M04 performance environment.

Before M04 performance work:

- repository must be on clean current `main` containing the M03 merge and approved M04 specification;
- build and automated tests must pass;
- create or rebuild a current schema-v2 index through the production path if the existing local benchmark database is stale or incompatible;
- do not obtain unrestricted administrator execution on the host;
- do not perform destructive USN-journal or storage experiments.

A representative full local NTFS index may be used because M02 already established acceptable initial-index behavior and M03 established safe incremental semantics.

Do not commit runtime databases or private path dumps.

### Quail-Lab

Use `Quail-Lab` for functional smoke/regression testing where controlled files and directories are useful.

Before M04 lab work:

- host and VM repositories must both be on clean current `main` containing the M03 merge and approved M04 specification;
- verify the disposable data volume by label `QUAIL_LAB_DATA`, filesystem NTFS, health, and current drive letter;
- do not assume VM IP or drive letter;
- create `M04-clean` from the intended clean baseline before milestone runtime work materially changes reusable lab state;
- do not delete or overwrite `M01-clean`, `M02-clean`, or `M03-clean`.

SSH login starts in `cmd.exe`; explicitly invoke `powershell -NoProfile` when PowerShell cmdlets are required.

No destructive journal churn is required for M04.

## Acceptance criteria

M04 is complete only when all applicable criteria below are satisfied with durable evidence.

1. A production search API queries the persistent current schema-v2 namespace index without live filesystem traversal.
2. Search is case-insensitive and supports predictable partial/substring matching by entry name.
3. File-only, directory-only, and default/any filtering are implemented and tested.
4. A simple case-insensitive extension filter is implemented and tested.
5. CLI search syntax is small, English-language, predictable, and documented through usage/help behavior.
6. Result count is bounded by a safe default and explicit limit.
7. Result ordering is deterministic and documented without introducing smart ranking.
8. Search refuses absent, incomplete, incompatible, or rebuild-required index state instead of presenting it as current.
9. Incremental create/rename/delete changes become visible to search through the existing M03 persistence path without requiring full rebuild.
10. Any auxiliary SQLite search structure, if introduced, is maintained crash-consistently with namespace mutations and safe rebuilds.
11. Automated tests cover T01–T09 as applicable.
12. Quail-Lab functional evidence covers T10 on real NTFS.
13. Physical-host evidence covers T11 with realistic index size and query categories.
14. The search implementation choice is based on measurement; plain SQLite is retained if sufficient, and a more complex SQLite-native mechanism is adopted only with clear evidence.
15. `docs/milestones/M04-results.md` records the search semantics, ordering, syntax, implementation decision, latency measurements, storage impact, architecture boundary decision, limitations, and verification results.
16. M04 does not implement M05 metadata filters, smart ranking, GUI, service/IPC, background monitoring, other providers, network/content indexing, or plugin infrastructure.

A build passing or one fast query alone is not completion.

## Out of scope

M04 must not implement:

- fuzzy matching;
- typo correction;
- smart/relevance ranking;
- usage-history scoring;
- recency/path-preference ranking;
- cross-provider ranking;
- M05 size/modification-time/attribute filters;
- content indexing or content search;
- application search;
- browser history/bookmarks;
- calculator/conversions;
- web search provider;
- network/cloud filesystem search;
- production Windows Service;
- IPC;
- long-running watcher/polling/scheduler/autostart;
- GUI/global hotkey/tray/settings;
- installer/updater;
- dynamic or third-party plugin framework;
- external search engine daemon;
- custom native SQLite extension;
- custom NTFS parser;
- native C++/Rust;
- speculative cross-platform abstraction;
- general hard-link representation redesign;
- broad provider-framework refactor unrelated to the active file-search slice.

## Stop conditions

Stop instead of expanding M04 if any of the following becomes true:

- the current schema cannot support correct basic file-name search without a material persistence redesign;
- a required search structure cannot be maintained crash-consistently with M03 checkpoint semantics using a small SQLite-native change;
- realistic physical-host measurements show that acceptable launcher latency requires a materially different database/search architecture;
- a proposed FTS/trigram approach requires substantial custom tokenizer/native-extension work;
- a project/module split grows into a generic provider/plugin framework rather than a small concrete file-search boundary;
- basic search correctness would require solving general NTFS hard-link multiplicity;
- M05 metadata work becomes necessary to satisfy M04;
- service/IPC/background monitoring becomes necessary for basic one-shot indexed search correctness;
- required physical-host or VM access is unavailable;
- the lab target is ambiguous or unrelated local changes are present;
- canonical repository documents conflict materially with the approved milestone;
- completing the milestone requires unrelated destructive host operations;
- another material architecture/correctness issue appears that is outside the approved scope.

When a stop condition is triggered, preserve evidence, explain the minimum decision required, and do not improvise a larger redesign.

M04 must produce:

- production basic file-name search over the current persistent index;
- simple file/directory and extension filters;
- bounded deterministic results;
- thin CLI search command;
- automated tests for required search semantics and current-state guards;
- Quail-Lab functional search evidence;
- physical-host latency evidence;
