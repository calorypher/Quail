# M05.5 — Developer Agent Tooling v2

## Goal

Extend the small provider-neutral development tooling introduced in M04.5 with three workflows that have now repeated enough to justify repository automation:

1. reliable Quail-Lab startup and SSH host-key handling across dynamic IP changes;
2. bounded deployment and integrity verification for more than one build artifact;
3. safe preparation of a new milestone baseline across the host repository and Quail-Lab.

M05.5 is a tooling milestone only. It must not change Quail product behavior, index/search semantics, application architecture, CI/CD, packaging, or release behavior.

The design principle remains the same as M04.5: a few high-value deterministic entry points with compact output, fail-closed behavior, and no general automation framework.

M05.5 is intentionally not a product milestone in `ROADMAP.md`. It is a technical interlude between M05 and M06.

## Evidence and motivation

M04.5 established `scripts/agent-preflight.ps1` and `scripts/vm-verify.ps1` and deliberately deferred additional automation until repetition justified it.

M05 provided that evidence:

- Quail-Lab had to be started and made SSH-ready as part of real milestone verification;
- a new dynamic VM address caused OpenSSH to request host-key trust again because the default trust identity was the changing IP address;
- manual acceptance was required even though the VM itself had not been replaced;
- T12 required deployment and SHA-256 verification of more than one artifact (`Quail.Cli.exe` plus the native SQLite library), exceeding the v1 single-file contract;
- milestone preparation has repeatedly required the same clean-main, host/VM synchronization, same-HEAD, checkpoint guard/create, and branch-creation sequence;
- physical-host build/benchmark collection repeated again, but its final stable reusable contract is still less clear than the workflows above and remains deferred.

The tooling must solve only the repeated problems above. Do not use M05.5 as an excuse to automate every development operation.

## Scope

### 1. Quail-Lab lifecycle in canonical tooling

Extend the canonical Quail-Lab tooling so callers no longer need to start `Quail-Lab` manually before routine verification or milestone preparation.

Required behavior:

- locate the VM by the configured/default stable name `Quail-Lab`;
- inspect its current Hyper-V state;
- if the VM is already `Running`, continue without changing its state;
- if the VM is `Off`, start it with the normal Hyper-V start operation;
- wait for a bounded configurable period for a usable dynamic IPv4 address and SSH reachability;
- poll locally without returning each retry to the implementation-agent context;
- on timeout, fail with a compact reason and preserve detailed diagnostics in `.quail-tooling/`;
- do not assume or persist a VM IP address;
- do not stop, reset, restore, or otherwise change a running VM merely to normalize its state;
- fail closed on ambiguous or unsafe Hyper-V states rather than improvising.

A simple timeout parameter is allowed. Keep the default suitable for normal Windows guest startup without creating a general VM lifecycle manager.

### 2. Stable SSH host identity across dynamic IP changes

Replace IP-address-based trust for canonical Quail-Lab SSH/SCP calls with a stable project-lab identity.

Preferred contract:

- use `HostKeyAlias` derived from the configured VM name, normally `Quail-Lab`;
- use a dedicated ignored `known_hosts` file under `.quail-tooling/` rather than the developer's global OpenSSH trust store;
- use `StrictHostKeyChecking=accept-new` or an equivalently narrow TOFU behavior for the first connection to a previously unknown lab identity;
- after first trust, a real host-key mismatch for that alias must fail and must not be auto-replaced, removed, or bypassed;
- use the same SSH trust options for SSH probes, remote commands, and SCP deployment;
- do not use `StrictHostKeyChecking=no`, a null known-hosts file, or another mechanism that disables host authentication;
- do not commit the learned host key or machine-local trust database to the repository.

The purpose is to make DHCP/IP changes transparent while retaining meaningful SSH host authentication.

### 3. Bounded multi-file artifact deployment

Extend `scripts/vm-verify.ps1` so one invocation can deploy and verify a small set of repository-relative files required by a verification scenario.

Keep backward compatibility with the existing single-file use where practical.

The implementation may use a repeated/array `-ArtifactPath` argument or an equivalently small interface.

Required behavior:

- accept one or more repository-relative leaf files;
- reject absolute paths and paths that resolve outside the repository;
- reject missing files;
- reject ambiguous remote-name collisions rather than silently overwriting one artifact with another;
- copy all requested artifacts to the bounded remote verification directory;
- verify SHA-256 for every deployed file;
- return one compact success summary containing at least artifact count and a deterministic integrity summary;
- preserve per-file details in the local tooling log rather than printing a long list on normal success;
- retain the existing healthy `QUAIL_LAB_DATA` discovery and bounded verification scenario behavior.

Do not build a package manager, installer deployment framework, recursive synchronization engine, or general manifest format in M05.5.

A directory deployment mode is allowed only if it is demonstrably simpler than a small file-list contract and remains bounded and deterministic.

### 4. Canonical milestone preparation entry point

Add one canonical repository-local PowerShell entry point for the repeated pre-milestone baseline workflow, expected to be named:

`scripts/prepare-milestone.ps1`

unless implementation evidence clearly supports a better name.

Its purpose is to collapse the routine safe sequence performed before implementation milestones into one fail-closed operation.

The script should accept explicit values for items that legitimately vary, expected to include at least:

- milestone/checkpoint identifier, for example `M06` / `M06-clean`;
- implementation branch name, for example `m06-usable-cli-core`;
- Quail-Lab SSH user;
- VM repository path, because that path is machine-local and must not be hard-coded into committed tooling;
- optional VM name and data-volume label using the existing project defaults.

#### Host repository baseline

The script must:

- derive the host repository root from its own repository location;
- require a clean worktree before changing branch/ref state;
- verify `origin`;
- fetch `origin` normally;
- move the local `main` forward only through an ordinary fast-forward when it is behind `origin/main`;
- reject local-main-ahead and diverged states rather than silently publishing, rebasing, resetting, or hiding work;
- never stash, clean, reset, force, or rewrite history;
- end the baseline phase with clean host `main` equal to `origin/main`.

If the invocation begins on another clean branch, switching to `main` is allowed as routine non-destructive preparation when it cannot discard work.

#### Quail-Lab repository baseline

Using the canonical VM/SSH behavior from this milestone, the script must:

- ensure Quail-Lab is running and SSH-ready;
- explicitly invoke remote PowerShell where PowerShell is required;
- require the configured remote repository to be clean before changing branch/ref state;
- switch the remote repository to `main` when safe;
- fetch `origin`;
- fast-forward remote `main` only when safe;
- reject remote-ahead/diverged/dirty states;
- confirm the host and VM repositories end at the same exact `main` commit.

The VM repository path must be supplied explicitly or through a simple ignored local configuration if implementation evidence shows that to be materially cleaner. Do not commit `C:\Projects\Quail` or another machine-specific absolute path as a source-code default.

#### Lab guard and checkpoint

Before creating a milestone checkpoint, the script must:

- positively identify exactly one healthy NTFS data volume by `QUAIL_LAB_DATA` or the requested stable label;
- confirm host and VM repositories are clean and on the same exact current `main`;
- derive or accept a unique checkpoint name such as `M06-clean`;
- check whether that checkpoint already exists;
- if it already exists, stop without deleting, restoring, renaming, or overwriting it;
- if it does not exist and all guards pass, create exactly one new checkpoint.

Creating a new uniquely named checkpoint after validating the clean baseline is an approved routine non-destructive preparation operation. Existing checkpoints remain protected by the normal safety gates.

#### Implementation branch

Only after the clean baseline and checkpoint creation succeed, the script may create and switch the host repository to the requested new milestone branch.

It must:

- create the branch from the exact validated `main` HEAD;
- reject an already existing conflicting branch rather than resetting or moving it;
- leave the VM repository on clean `main` unless a later milestone explicitly needs a different remote branch;
- print a compact final summary containing milestone/checkpoint, host main HEAD, VM main HEAD, checkpoint status, created branch, VM readiness, and data-volume label.

### 5. Shared implementation without a tooling framework

The new lifecycle/SSH behavior is needed by both `vm-verify.ps1` and `prepare-milestone.ps1`.

A small private PowerShell helper/module is allowed to avoid duplicating:

- VM state/start/wait logic;
- dynamic IP discovery;
- SSH option construction;
- remote PowerShell invocation;
- stable lab-volume discovery;
- compact logging helpers.

Prefer one small internal helper over copying significant logic between public scripts.

Do not expose a collection of public micro-scripts and do not create a generic remote-execution/agent framework.

The expected public entry points after M05.5 remain approximately:

- `scripts/agent-preflight.ps1`;
- `scripts/vm-verify.ps1`;
- `scripts/prepare-milestone.ps1`.

### 6. Compact output and local detailed logs

Retain the M04.5 output principle.

On success:

- one compact stable PASS line per public entry-point invocation;
- no SSH retry spam, per-file hash dump, Git command transcript, or Hyper-V polling transcript on stdout.

On failure:

- non-zero exit code;
- one concise primary reason;
- local detailed log path under ignored `.quail-tooling/`;
- no secret dumping.

### 7. Documentation

Update `AGENTS.md` only where needed to make the new canonical workflow durable.

Document concisely that:

- canonical Quail-Lab tooling owns normal VM startup/wait and stable SSH host-key handling;
- dynamic IP changes must not require manual trust when the pinned alias key is unchanged;
- a changed key remains a hard failure requiring investigation;
- `prepare-milestone.ps1` is the canonical supported preparation path when its contract applies;
- new uniquely named milestone checkpoints may be created automatically only after the documented clean/same-HEAD guards pass;
- existing checkpoint deletion/restore/overwrite remains explicitly gated.

Do not turn `AGENTS.md` into a PowerShell manual.

Create `docs/milestones/M05.5-results.md` with final interfaces, verification, workflow reduction, limitations, and deferred candidates.

## Deliberately deferred automation

Do not add physical-host benchmark automation in M05.5.

M04 and M05 show that host build/measurement collection is becoming repeatable, but M06 may change what release-quality measurements are useful. Record it again as a candidate if M06 repeats a stable bounded pattern.

Also defer:

- general fixture orchestration;
- general remote command execution;
- milestone-specific M06/M07 scenarios that do not yet exist;
- automatic merge or review handling;
- release/tag automation.

## Acceptance criteria

M05.5 is complete only when:

1. Canonical VM tooling can handle a normally `Off` or already `Running` Quail-Lab without requiring the user to start it manually.
2. VM startup and SSH wait are bounded and fail closed.
3. Canonical SSH/SCP uses a stable VM alias and a dedicated ignored known-hosts database.
4. First-use trust can be accepted automatically, but a later host-key mismatch remains a hard failure.
5. Dynamic IP changes no longer require manual host-key acceptance when the VM key is unchanged.
6. `vm-verify.ps1` can deploy and integrity-check at least two repository-relative artifacts in one bounded invocation.
7. The existing single-file smoke remains supported or has a minimally changed documented equivalent.
8. A canonical milestone-preparation entry point safely handles clean-main synchronization for host and VM, exact-HEAD equality, data-volume validation, checkpoint guard/create, and host milestone branch creation.
9. Host and remote dirty/ahead/diverged/conflicting states fail without hiding or rewriting user work.
10. Existing checkpoints are never restored, deleted, renamed, or overwritten by preparation tooling.
11. New checkpoints are created only when all clean/same-HEAD/lab guards pass and the requested name does not already exist.
12. No committed script hard-codes developer/machine-specific paths, usernames, current VM IPs, disposable drive letters, secrets, or learned host keys.
13. Success output remains compact and detailed logs remain local/ignored.
14. `AGENTS.md` records the new canonical workflow and preserves all existing safety gates.
15. `docs/milestones/M05.5-results.md` records T01–T18, final interfaces, security behavior, call reduction, limitations, and deferred candidates.
16. Quail product code, product behavior, index/search semantics, packaging, CI/CD, and release behavior are unchanged.
17. Existing automated Quail tests and Release build still pass after tooling/documentation changes.
18. A verified branch plus open PR is ready for independent QA; merge remains separately gated.

## Out of scope

M05.5 must not implement:

- M06 product functionality;
- changes to Quail indexing/search behavior;
- Windows Service/IPC work;
- background index lifecycle;
- host benchmark/performance automation;
- a general Hyper-V manager;
- a general SSH client/configuration manager;
- insecure SSH host-key bypass;
- general file synchronization or package deployment;
- general fixture/test orchestration;
- general Git workflow automation beyond the bounded preparation contract;
- automatic commits/pushes/PR creation inside `prepare-milestone.ps1`;
- PR merge;
- branch deletion;
- force-push;
- destructive reset/clean;
- history-rewriting rebase;
- checkpoint restore/delete/overwrite;
- automatic release tags or GitHub Releases;
- secrets or credentials in repository files;
- Codex-specific, Claude-specific, or other provider-specific integration;
- a general agent framework.

## Stop conditions

Stop instead of expanding scope if:

- reliable SSH handling would require disabling host authentication rather than pinning a stable lab identity;
- VM startup/wait requires a broad lifecycle manager or brittle network scanning;
- multi-file deployment starts becoming installer/package synchronization infrastructure;
- remote repository discovery would require hard-coded machine paths or broad filesystem searches instead of an explicit parameter/simple ignored config;
- milestone preparation cannot prove clean/same-HEAD state before checkpoint creation;
- a requested operation would need stash/reset/clean/force/rebase or another operation that can hide or rewrite unrelated work;
- checkpoint creation cannot be separated cleanly from gated restore/delete/overwrite behavior;
- testing would require destructive checkpoint operations or significant destructive host changes;
- useful implementation would require changing Quail product code or architecture;
- a proposed helper/module grows into a general orchestration framework;
- measured workflow reduction does not justify a proposed automation element.

## Completion boundary

Normal completion is a verified implementation branch plus an open PR ready for independent QA.

Do not merge the PR, delete branches, force-push, perform destructive reset/clean, rewrite published history, restore/delete/overwrite checkpoints, create/move release tags, publish releases, or perform significant destructive host operations without explicit user approval.

A first live use of `prepare-milestone.ps1` for M06 after M05.5 merge may provide additional operational evidence, but the PR must already be independently reviewable and must prove all safety guards before merge.
