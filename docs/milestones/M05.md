# M05 — Metadata Filters

## Goal

Extend Quail's persistent file-search index with reliable metadata required for practical size, modification-time, and basic-attribute filtering without weakening M03 crash consistency or M04 search latency.

M05 is split operationally into two phases to control implementation risk and agent cost:

- **M05-A — Metadata acquisition decision/spike**: a short evidence-driven decision about how size and modification time can be acquired and maintained correctly and at acceptable cost.
- **M05-B — Metadata filters implementation**: implementation of the approved metadata model and filters after the M05-A decision has been recorded.

The split is methodological only. M05 remains one product milestone and is complete only after M05-B passes the full acceptance criteria.

## Current constraints

The current persistent namespace model stores file identity, parent identity, name, attributes, USN, and record version. It does not yet persist file size or modification time.

M01 established MFT/USN namespace and change-stream feasibility, but it did not establish production-quality acquisition of file size or `LastWriteTime` semantics for all indexed records. M05 must not assume that a USN record timestamp is equivalent to the current file modification time.

Normal search must continue to use persistent index data. Do not add live filesystem traversal or per-result `FileInfo`/equivalent stat calls to the query path.

## M05-A — Metadata acquisition decision/spike

### Goal

Determine the smallest correct mechanism for acquiring and maintaining file size and modification time for Quail's persistent NTFS index, with representative correctness and cost evidence before implementing the full filter feature.

### Scope

Investigate and compare practical Windows/NTFS mechanisms available to the current C#/.NET architecture for obtaining:

- logical file size;
- last modification time with semantics suitable for user-visible filtering;
- any metadata refresh required after relevant USN changes.

The spike should answer at least:

1. What source provides the authoritative size value for normal files?
2. What source provides the modification timestamp Quail should expose/filter as `modified`?
3. Can the values be obtained cheaply during initial enumeration, or is a secondary metadata lookup required?
4. If a secondary lookup is required, what is its correctness behavior for inaccessible, deleted-racing, reparse, system, and otherwise unusual entries?
5. Which USN reasons or observed mutations require size/mtime refresh?
6. Can rename/move preserve metadata without unnecessary re-read?
7. What are the measured wall-time, CPU, I/O, failure-rate, and memory implications on Quail-Lab and a representative physical-host `C:` index?
8. Can enrichment remain streaming/batched and compatible with staged rebuild and crash-consistent incremental transactions?
9. Is metadata absence representable explicitly without silently inventing zero/epoch values?

Prefer official Windows APIs and the existing thin interop direction. Do not introduce a native C++/Rust component, filesystem crawler, background job framework, service/IPC, or broad metadata abstraction merely for the spike.

### Required evidence

Use controlled Quail-Lab files with known:

- zero-byte size;
- small non-zero size;
- larger size;
- explicitly controlled last-write timestamps where Windows permits;
- content/size changes without rename;
- timestamp-only changes where practical;
- rename/move without content modification;
- delete/race behavior.

Also perform a bounded representative physical-host measurement sufficient to estimate the incremental cost of the selected acquisition mechanism over the current persistent build path. Do not perform destructive host filesystem/journal operations.

Record results in `docs/milestones/M05-A-results.md`.

### Decision output

M05-A must end with one explicit result:

- **GO** — selected acquisition/maintenance mechanism is correct enough and affordable for M05-B;
- **GO WITH LIMITATIONS** — implement only a clearly defined subset and record the limitation;
- **NO-GO / STOP** — correct size/mtime acquisition at acceptable cost requires a material architecture expansion, in which case stop before M05-B.

The result must define the exact persistent semantics to be implemented in M05-B, including representation of unavailable metadata and which incremental changes trigger refresh.

### M05-A out of scope

Do not implement the complete user-facing metadata filter feature in M05-A. Small disposable probe/test code and narrowly scoped production-path instrumentation are allowed only as needed to establish the decision.

Do not add:

- service/IPC;
- background scheduler/job system;
- new provider/plugin framework;
- GUI;
- M06 CLI polish beyond evidence commands strictly needed for the spike;
- speculative metadata types beyond the approved M05 scope.

### M05-A completion boundary

M05-A ends when the decision evidence is recorded and independently reviewable. It does not need a separate public release. If code changes are required for the spike, keep them minimal and either retain them only if they are production-useful for M05-B or remove disposable-only instrumentation before the M05 implementation PR is finalized.

## M05-B — Metadata filters implementation

M05-B begins only after the M05-A decision is accepted.

### Scope

Implement the approved persistent metadata model and query filters.

Required user-facing search capabilities, subject to the M05-A decision:

- minimum file size;
- maximum file size;
- modification-time lower bound (`modified after` or equivalent);
- modification-time upper bound (`modified before` or equivalent);
- a minimal useful subset of existing basic file attributes, expected to be `hidden`, `read-only`, and `system` unless implementation evidence shows that one of these is not reliable/useful enough to expose.

The CLI syntax must be simple, deterministic, and documented. Prefer explicit units/ISO-style timestamps or another unambiguous representation. Do not introduce a general query language.

Metadata filters must compose with existing M04 capabilities:

- substring name query;
- file/directory filter;
- extension filter;
- bounded result limit;
- deterministic ordering.

Normal search remains persistent-index-only.

### Persistence and incremental correctness

The implementation must:

- persist size/mtime according to the exact M05-A semantics;
- represent unavailable/not-applicable metadata explicitly rather than conflating it with zero or epoch;
- populate metadata correctly during staged initial build/rebuild;
- preserve M03 build/checkpoint handoff semantics;
- refresh only the metadata required by relevant incremental changes;
- preserve valid metadata across rename/move when the underlying content metadata did not change;
- remove metadata atomically with deleted namespace entries;
- keep search auxiliary state and metadata state crash-consistent with the authoritative namespace transaction;
- reject or rebuild incompatible older schema/index state rather than guessing a migration when that is safer and simpler.

A schema version bump or explicit metadata-format marker is allowed if required by correctness.

### Architecture

Keep the current architecture simple.

A small concrete boundary between namespace change records and metadata enrichment is allowed if required by the approved acquisition method. Do not introduce:

- a generic enrichment framework;
- background work queues;
- provider/plugin infrastructure;
- service/IPC;
- speculative cross-platform filesystem abstractions.

Reassess `Quail.Core` only if the active M05 slice creates a real architectural pressure; do not split projects cosmetically.

## Acceptance criteria

M05 is complete only when:

1. M05-A records a reviewed evidence-based acquisition/maintenance decision.
2. Size and modification-time semantics are explicit and not inferred incorrectly from unrelated USN fields.
3. Normal search performs no live filesystem traversal/stat operations.
4. Minimum/maximum size filters work on persistent data.
5. Modification-time bounds work on persistent data with documented UTC semantics.
6. A minimal reliable subset of basic attributes is filterable.
7. Filters compose correctly with all M04 search controls.
8. Initial build/rebuild populates metadata according to the approved mechanism.
9. Incremental sync refreshes the required metadata correctly for real controlled mutations.
10. Rename/move/delete and rollback behavior preserve M03 crash consistency.
11. Metadata-unavailable states are explicit and safe.
12. Physical-host evidence quantifies initial-build overhead and metadata-filter query latency.
13. Complexity remains proportional to the requirement; no service, scheduler, plugin framework, or broad enrichment framework is introduced.
14. Full automated regression tests and Release CLI build pass.
15. `docs/milestones/M05-results.md` records final semantics, CLI syntax, persistence design, performance evidence, limitations, T01–T15, and reusable/scriptable workflow observations.
16. A verified branch and PR are ready for independent QA; merge remains separately gated.

## Performance guidance

Do not optimize before measuring.

M04 established a representative physical-host index of roughly 860k namespace records and warm FTS search-core medians generally below 50 ms, with a deliberately broad extension-filter case around 63 ms and all measured warm-core cases below 100 ms.

M05 should preserve that user-perceived search class. Metadata predicates may add some cost, but common warm core-search scenarios should not routinely exceed 100 ms without strong evidence and explicit review.

Initial-build metadata enrichment may cost materially more than M04's namespace-only/FTS build. Measure wall time, CPU, memory, database-size change, and failure counts before deciding whether the cost is acceptable. Do not hide an excessive per-file lookup cost behind complexity.

## Tooling workflow

Use the canonical M04.5 repository tooling where its contracts apply:

- `scripts/agent-preflight.ps1` for supported repository/environment preflight;
- `scripts/vm-verify.ps1` for supported Quail-Lab orchestration/verification.

Do not reconstruct equivalent supported procedures manually unless debugging the script or the required M05 case is outside its documented contract.

At M05-A and final M05 handoff, record newly observed repeatable deterministic procedures that may justify a later tooling extension. Do not implement unrelated tooling automatically inside M05.

## Out of scope

M05 must not add:

- fuzzy matching, typo correction, relevance ranking, or other M04 search expansion;
- content search/indexing;
- application/browser/utility providers;
- GUI;
- Windows Service or IPC;
- automatic background monitoring/scheduling beyond existing one-shot sync behavior;
- installer/update work;
- public plugin/extensibility infrastructure;
- network/cloud indexing;
- broad metadata fields without a demonstrated use case;
- speculative optimization unrelated to measured M05 bottlenecks.

## Stop conditions

Stop instead of expanding scope if:

- reliable size/mtime acquisition requires a material new service/background subsystem not approved by this milestone;
- representative host enrichment requires excessive per-file I/O/time or has an unacceptable unresolved failure rate;
- Windows semantics discovered during M05-A do not support the requested user-visible meaning without approximation;
- incremental correctness cannot be maintained without weakening M03 transaction/checkpoint guarantees;
- a proposed solution requires live filesystem stat/traversal in the normal search path;
- unrelated worktree changes, conflicting canonical requirements, or destructive operations would be required;
- completing M05 requires a material architecture expansion beyond the approved slice.

## Git and safety

Use normal implementation-agent workflow from `AGENTS.md`.

Routine non-destructive Git operations may be performed autonomously where access exists. Explicit approval remains required for merge, branch deletion, force-push, destructive reset/clean, history-rewriting rebase of a published branch, release tags/releases, destructive checkpoint operations, and other gated destructive actions.

## Completion boundary

The final M05 boundary is a verified implementation branch plus PR ready for independent QA.

M05-A is a decision gate inside the milestone. Do not proceed into M05-B if the M05-A result is NO-GO/STOP or if the evidence shows that implementation would require a material scope expansion.
