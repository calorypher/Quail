# M06 — Usable CLI and 0.1 Core

## Goal

Turn the verified NTFS file engine from M01–M05 into a coherent, usable Windows CLI/core slice that can operate on one or more local NTFS volume indexes, search them predictably, open a selected result through the Windows shell, and provide release-quality diagnostics and documentation.

M06 is the functional **0.1 core** boundary. It is not the final 0.1 distribution boundary: packaging remains M07, and M06 must not create a release tag or GitHub Release.

The milestone should consolidate and expose the capabilities already proven by earlier milestones rather than introduce another large subsystem.

## Inputs from completed milestones

M01–M05 established:

- official NTFS/MFT enumeration and USN journal feasibility;
- persistent per-volume SQLite indexes;
- staged rebuild and crash-consistent incremental checkpoints;
- restart catch-up and fail-closed continuity handling;
- persistent FTS5 trigram name search plus deterministic short-query fallback;
- type and extension filters;
- persistent nullable size and UTC modification-time metadata;
- hidden/read-only/system filters;
- representative physical-host search latency below 100 ms for measured warm core scenarios;
- a representative M05 physical-host index of 862,284 records, 248,844,288 bytes, with accepted initial-build wall time of 161.596 s.

M04.5/M05.5 established canonical repository and Quail-Lab tooling. Use those scripts where their contracts apply.

## Product boundary for M06

M06 should make the existing engine useful without prematurely implementing the later launcher/service lifecycle.

The intended model is:

- one independent SQLite index per indexed local NTFS volume;
- a thin aggregation layer for searching more than one index in one request;
- explicit CLI index paths rather than a new persistent configuration/catalog subsystem;
- one-shot `sync` remains explicit;
- no Windows Service, background scheduler, daemon, installer, tray process, or GUI.

Do not replace the per-volume database design with one global database in M06. Do not introduce a provider/plugin framework merely to support multi-index search.

## Scope

### 1. Coherent user-facing CLI

Refine the current diagnostic CLI into a small documented command surface suitable for the 0.1 core.

Required capabilities:

- build/rebuild an index for a local NTFS volume;
- sync an existing index once from the USN journal;
- show useful index/volume status;
- search one or more index databases;
- open a selected indexed file or directory through the normal Windows shell;
- help/usage;
- version information.

The final syntax should be explicit and predictable. Prefer a common explicit `--index <database-path>` convention, repeatable where multiple indexes are valid, rather than positional forms whose meaning changes by command. Because Quail has no public CLI compatibility commitment yet, M06 may simplify the pre-0.1 syntax instead of preserving awkward historical forms merely for compatibility.

Do not add a third-party CLI parsing framework unless the existing parser becomes materially harder to keep correct and tested than a mature small dependency would be. A straightforward in-repository parser remains preferred if adequate.

Test-only fault injection such as `--fail-after` must not appear as a normal documented user feature. It may remain available only through an explicit internal/test seam if still required by automated verification.

### 2. Multi-index / multi-volume search

A search request must be able to read one or more complete compatible per-volume indexes.

Required behavior:

- apply the same name/type/extension/size/time/attribute semantics to every index;
- normal search remains persistent-index-only and must not traverse/stat the live filesystem;
- reject an incompatible/incomplete/rebuild-required input index rather than silently returning a partial global result;
- apply one global result limit across all indexes;
- return deterministic global ordering;
- include enough source identity in each result to distinguish equal file IDs/names from different volumes/indexes;
- preserve bounded work: an index does not need to return more than the requested global result limit merely to compute a global top-N merge;
- single-index search remains a normal supported case.

The aggregation should live in a reusable core-level boundary if that is the natural minimal design, because the later launcher should not need to reimplement multi-index merge semantics. Do not create a generic provider framework.

### 3. Open indexed result

Add a user-facing operation that opens an indexed file or directory using the normal Windows shell association/navigation behavior.

Preferred contract:

- identify the source index explicitly;
- identify the indexed entry by canonical file ID or another stable identifier already present in search output;
- reconstruct the path from persisted namespace state;
- invoke the Windows shell using ordinary supported .NET/Windows behavior;
- report a concise operational failure if the indexed path no longer exists or cannot be opened.

Opening is an explicit user action and may of course access the live filesystem/shell. The restriction against live filesystem work applies to the normal search path.

Do not add an interactive result picker, shell replacement, file manager, preview pane, or persistent result-number state between processes.

### 4. Status and diagnostics

Make status output useful enough to understand each index without inspecting SQLite manually.

At minimum expose, in a stable concise form where available:

- index state;
- source volume/mount identity;
- record count;
- schema/search/metadata compatibility state or rebuild requirement;
- checkpoint/journal state needed to diagnose whether sync can continue;
- completed/build timestamp;
- database path/source identity when multiple indexes are shown.

Multiple indexes may be supplied to status if this remains simple and consistent with the common CLI contract.

Do not build a general diagnostics framework.

### 5. Exit/error behavior

Document and test a small stable exit-code/error contract sufficient to distinguish at least:

- success;
- invalid CLI/user input;
- operational/index/runtime failure.

Do not return partial success for a multi-index search when one requested index is invalid or unavailable unless the specification is explicitly revised with evidence. Fail-closed behavior is the default for the 0.1 core.

Normal errors should be concise and English-first. Detailed developer evidence belongs in tests/logging/tooling rather than noisy normal output.

### 6. 0.1-core documentation

Update README and/or a focused CLI/core document so a developer can perform a basic end-to-end workflow without reading milestone history.

Document:

- requirements and current Windows/NTFS scope;
- build/rebuild;
- one-shot sync;
- single- and multi-index search;
- filters;
- open-result usage;
- status;
- known privilege requirements;
- current limitations;
- the fact that background maintenance, service integration, GUI, and installer are not part of M06;
- that M07 remains the distribution/installer boundary.

Do not claim that M06 is a polished public release.

## Index storage characterization

M06 should characterize current on-disk index scaling as part of the 0.1-core evidence, but **must not optimize or compress the database speculatively**.

The M05 representative host result is 248,844,288 bytes for 862,284 records. Storage depends primarily on indexed entry count, name/token distribution, SQLite indexes, and FTS5 trigram data; it does not store file contents.

During final physical-host verification collect at least:

- record count;
- final database bytes;
- approximate bytes per indexed entry for that measurement;
- SQLite `page_size`, `page_count`, and `freelist_count`;
- a best-effort component breakdown (for example via SQLite `dbstat`) if available through the existing SQLite build without adding a new dependency.

The breakdown should, where practical, distinguish the authoritative namespace table/primary-key storage, parent/name index, FTS5 auxiliary storage, and other material structures.

If `dbstat` is unavailable, record that limitation and retain coarse measurements rather than adding a native extension or separate database tool merely for M06.

Use this evidence to decide whether a later bounded storage-optimization milestone/spike is justified. Generic transparent compression, a custom compressed VFS, compressed archives, or custom packed storage are out of scope for M06.

## Architecture constraints

Keep the current architecture small.

Allowed when naturally required:

- a small reusable multi-index aggregation type/service in `Quail.Core`;
- a small Windows-shell launch helper isolated from search/index semantics;
- modest CLI parser cleanup to make commands testable and predictable.

Do not add:

- provider/plugin discovery or public extensibility;
- dependency injection/application-host frameworks merely for CLI organization;
- a persistent catalog/config database;
- a Windows Service or IPC;
- a background scheduler/watcher;
- an installer/updater;
- a general command framework without demonstrated need;
- a new storage/search engine.

## Acceptance criteria

M06 is complete only when:

1. The CLI has a coherent documented command/option model including help and version output.
2. Existing build/rebuild/sync/status behavior remains correct and safely exposed.
3. One request can search one or more persistent per-volume indexes.
4. Multi-index search has deterministic global ordering, one global limit, and explicit source identity.
5. Multi-index search fails safely when a requested index is not usable; it does not silently hide missing sources.
6. All M04/M05 search/filter semantics remain available.
7. A selected indexed file or directory can be opened through the normal Windows shell using a stable explicit result identity.
8. Search itself performs no live filesystem traversal/stat calls.
9. User-input errors and operational failures have a small documented exit/error contract.
10. Real Quail-Lab verification proves the usable CLI/core flow.
11. Representative physical-host verification proves the final core still works on a real large index.
12. Warm search remains in the established responsive class or any regression is measured and explicitly reviewed.
13. Current database storage scaling/footprint is measured and documented without speculative compression/storage redesign.
14. Documentation provides a usable 0.1-core quick start and honest known limitations.
15. Existing automated regression tests and Release build pass.
16. Architecture remains proportional to the M06 slice.
17. `docs/milestones/M06-results.md` provides durable evidence and workflow observations.
18. A verified branch plus open PR is ready for independent QA; merge remains separately gated.

## Performance guidance

M06 should not repeat every exploratory benchmark from M04/M05 unless a regression appears.

Use targeted release-quality checks:

- preserve the established warm core search class;
- measure the aggregation overhead for more than one index;
- record process-level behavior where it materially affects CLI usability;
- retain the accepted M05 initial-build cost as the current baseline rather than reopening metadata optimization without new evidence;
- characterize disk footprint before proposing storage optimization.

If multi-index aggregation or CLI restructuring causes a material regression, investigate the concrete regression. Do not hide it behind caching, parallelism, a service, or new architecture without explicit review.

Use canonical repository tooling from M04.5/M05.5 where its contract applies:

- `scripts/agent-preflight.ps1`;
- `scripts/vm-verify.ps1`;

Host benchmark/evidence automation remains deferred unless M06 itself demonstrates a stable repeated contract worth a later tooling change. Do not add it inside M06 merely because measurements are required.

## Out of scope

M06 must not add:

- Windows Service or IPC;
- automatic/background index maintenance or scheduling;
- GUI, global hotkey, tray/settings UI;
- installer/update work;
- persistent source/catalog configuration subsystem;
- application/browser/calculator/web providers;
- public/dynamic plugin framework;
- content search/indexing;
- fuzzy matching/typo correction/ranking expansion;
- network/cloud indexing;
- Linux/macOS support;
- database compression, custom compressed VFS, custom packed storage, or a replacement storage engine;
- speculative initial-index parallelism optimization;
- CI/CD, tags, GitHub Release, or release assets.

## Stop conditions

Stop instead of expanding scope if:

- multi-index support appears to require replacing the per-volume database architecture or introducing a persistent catalog/service;
- opening results would require an unsafe shell invocation or broad privilege expansion;
- correct global search would require unbounded result materialization or a new search engine;
- a requested CLI cleanup grows into a framework migration with little user value;
- storage reduction would require compression/custom VFS/schema redesign before the footprint is characterized;
- a physical-host regression is substantial and unexplained;
- unrelated worktree changes, conflicting canonical requirements, or destructive operations would be required;
- completing the milestone would require a material architecture expansion beyond the approved 0.1-core slice.

## Git and safety

Follow `AGENTS.md` and canonical tooling.

Explicit approval remains required for merge, branch deletion, force-push, destructive reset/clean, published-history rebase, release tags/releases, destructive operations on existing checkpoints, and other gated destructive actions.

M06 ends at a verified implementation branch plus an open PR ready for independent QA.
