# M07 — Test/Developer Packaging and 0.1 Distribution

## Goal

Package the verified M06 Windows CLI/core as a reproducible, installable **Quail 0.1.0** test/developer distribution without expanding the product into a Windows Service, background indexer, GUI, or separate no-admin backend.

M07 is the packaging/distribution boundary for 0.1. It should make the existing CLI practical to install, reinstall/upgrade, verify, and uninstall on Windows 11 x64 while preserving the architecture and behavior already verified in M06.

The milestone packages what exists. It must not hide new application/service architecture inside installer work.

## Inputs from completed milestones

M01–M06 established:

- official Windows NTFS/MFT/USN enumeration and incremental-update behavior;
- persistent per-volume SQLite indexes;
- deterministic indexed search with metadata filters;
- one-shot build/rebuild/sync/status operations;
- deterministic multi-index search;
- explicit result identity and Windows shell-open support;
- a coherent CLI with stable success/input/operational exit-code classes;
- representative Quail-Lab and physical-host verification;
- canonical host/VM preparation and verification tooling.

M06 intentionally did **not** add a Windows Service, background scheduler, persistent source catalog, GUI, installer, or production no-admin indexing backend. M07 must preserve that boundary.

## Product boundary for M07

The 0.1 distribution model is deliberately narrow:

- Windows 11 x64 only;
- existing `Quail.Cli` application/core only;
- self-contained .NET 10 `win-x64` folder publish;
- one Inno Setup per-machine installer;
- installation under `C:\Program Files\Quail` using the normal 64-bit Program Files location;
- normal Windows elevation/UAC for installation and uninstall when required;
- installed CLI available from new command shells through the system `PATH`;
- persistent indexes remain outside the application directory and are not owned by the installer;
- no service, daemon, scheduler, GUI, updater, or per-user/no-admin installation mode.

The executable/component naming convention is:

- `Quail.Cli.exe` — current CLI and future diagnostic/automation CLI;
- `Quail.exe` — reserved for the future primary GUI launcher;
- `Quail.Service.exe` — reserved for a future Windows Service if/when that architecture is implemented;
- `Quail.Core.dll` — shared core library.

Do not rename the CLI to `Quail.exe`, `quail.exe`, or `Quail-cli.exe` in M07.

## Scope

### 1. Canonical 0.1.0 version contract

Define one canonical product/build version for this release: `0.1.0`.

Required behavior:

- assembly/product version metadata comes from one canonical MSBuild/repository source rather than unrelated duplicated literals;
- `Quail.Cli --version` derives its displayed product version from build/assembly metadata rather than the current hard-coded `0.1-core` string;
- the installer uses the same canonical `0.1.0` version;
- the final setup artifact is named `Quail-0.1.0-Setup.exe`;
- temporary version overrides used only for upgrade-path testing must not change the committed canonical version or produce release artifacts.

Do not introduce a general release/versioning framework.

### 2. Self-contained Windows x64 publish

Create a reproducible Release publish path for `Quail.Cli` targeting `win-x64` and including its own .NET runtime.

Required baseline:

- self-contained deployment;
- normal folder-based publish output;
- preserve the publish layout generated by .NET rather than manually reorganizing runtime/dependency files;
- no requirement for a separately installed .NET runtime on the target machine;
- no single-file bundling;
- no trimming;
- no ReadyToRun;
- no Native AOT.

Those additional deployment optimizations may be evaluated later only if evidence justifies them.

Generated publish output belongs under an ignored repository-local artifact directory such as `artifacts/publish/win-x64` and must not be committed.

### 3. Inno Setup installer

Use Inno Setup rather than a custom installer engine.

Add a small repository-owned installer definition, expected under a path such as `packaging/Quail.iss`.

The installer must:

- install the complete self-contained publish output to the conventional 64-bit per-machine `Program Files\Quail` location;
- require normal administrative approval appropriate for a per-machine installation;
- use one stable application identity/AppId so later versions can upgrade the same installation;
- create the normal Windows uninstall registration;
- support unattended/silent invocation where Inno Setup normally provides it, without treating silent mode as a UAC bypass;
- not create a Windows Service;
- not create scheduled tasks, startup entries, tray processes, or background processes;
- not create desktop or Start Menu shortcuts for the CLI unless runtime evidence demonstrates a concrete need and the milestone is explicitly revised;
- not install or modify user index databases.

The installer should package the publish output as produced instead of maintaining a hand-curated list of .NET runtime DLLs.

### 4. System PATH integration

The per-machine installer must make `Quail.Cli.exe` callable from a newly started command shell without a full path.

Required behavior:

- add the Quail install directory to the **system** `PATH` exactly once;
- preserve all unrelated existing `PATH` entries;
- reinstall/upgrade must not create duplicate Quail entries;
- uninstall must remove only the Quail-owned install-directory entry and preserve unrelated entries;
- environment-change behavior must be verified from a newly started process/shell.

Do not create a `quail.exe` shim or alias because that filename is reserved for the future GUI application on Windows.

### 5. Application and data layout

The installer owns application binaries under:

`C:\Program Files\Quail`

The current recommended per-user location for explicit CLI index databases is:

`%LOCALAPPDATA%\Quail\Indexes`

M07 does **not** change the existing explicit `--index <database-path>` CLI contract. The recommended data path is documentation/deployment guidance, not a new persistent source catalog or automatic default-index feature.

Required ownership rules:

- index databases, user settings, caches, logs, and other mutable user data must not be stored under `Program Files\Quail`;
- the installer must not create `%LOCALAPPDATA%\Quail\Indexes` merely to reserve the path;
- uninstall must not delete `%LOCALAPPDATA%\Quail` or explicit index databases outside the application directory;
- upgrade/reinstall may replace application files but must not depend on deleting user data.

A future service-owned machine-wide index may use `%PROGRAMDATA%\Quail` if later architecture requires it, but M07 must not create or freeze that layout.

### 6. Canonical installer build script

Add one bounded repository script, expected as `scripts/build-installer.ps1`, that produces the test/developer installer from a clean source tree.

The script should:

1. locate the repository deterministically from its own path rather than depend on the caller's current working directory;
2. build/publish `Quail.Cli` Release self-contained `win-x64` into the ignored artifact tree;
3. locate `ISCC.exe` through a documented explicit parameter and/or a small set of conventional supported installation paths;
4. fail clearly when Inno Setup is unavailable instead of downloading/installing software implicitly;
5. compile the repository-owned `.iss` definition;
6. place the setup executable under an ignored path such as `artifacts/installer`;
7. verify the expected `Quail-0.1.0-Setup.exe` exists;
8. compute and print its SHA-256;
9. return a clear nonzero failure if publish or installer compilation fails.

The script may clean/recreate only its own known generated artifact directories. It must not perform destructive Git operations or broad filesystem cleanup.

Do not add GitHub Actions/CI merely to build the M07 installer.

### 7. Install, reinstall/upgrade, and uninstall behavior

Verify the real installer lifecycle, not merely successful compilation.

Required behavior:

- clean installation succeeds on supported Windows 11 x64;
- installed `Quail.Cli.exe` reports `0.1.0` and help correctly;
- installation contents are sufficient to run without a separately installed .NET runtime dependency;
- reinstalling the same version is safe and does not duplicate system integration;
- the stable installer identity supports in-place upgrade behavior;
- an M07-only temporary earlier-version fixture may be built from the same source/package definition solely to verify replacement by canonical `0.1.0`; it must not be committed, tagged, or published;
- uninstall removes the installed application and Quail-owned PATH entry;
- uninstall preserves user/index data outside the install directory.

Do not add a custom repair/update engine.

### 8. Installed CLI smoke verification

The installed executable, not a `dotnet run` or bin-directory executable, must be used for deployment smoke tests.

At minimum verify:

- `Quail.Cli --version`;
- `Quail.Cli --help`;
- `status` against a compatible test/known index where available;
- `search` against a compatible test/known index;
- one controlled build/sync/search flow on Quail-Lab where the existing NTFS privilege requirements can be exercised safely.

M07 does not change the M06 privilege model: direct full-volume MFT/USN operations may still require an elevated CLI process because the production service boundary is not yet implemented. Documentation must state this clearly.

### 9. Documentation

Update the README and/or focused packaging documentation so another developer can:

- install the Inno Setup build prerequisite;
- build the 0.1.0 installer from the repository;
- understand where application files are installed;
- understand the recommended `%LOCALAPPDATA%\Quail\Indexes` location;
- understand that `--index` remains explicit;
- install/uninstall Quail;
- start a new shell and invoke `Quail.Cli` through PATH;
- understand current elevation requirements for full-volume build/sync;
- understand that there is no service, background maintenance, GUI, updater, or no-admin/per-user installer in 0.1;
- understand that 0.1 packaging is test/developer quality and unsigned unless later release work explicitly changes that.

Do not claim polished public-release readiness.

## Acceptance criteria

M07 is complete only when:

1. `0.1.0` is the canonical product version and `Quail.Cli --version` derives from build/assembly metadata.
2. A Release self-contained `win-x64` folder publish works without requiring a separately installed .NET runtime on the target deployment path.
3. The publish remains folder-based; M07 does not add single-file, trimming, ReadyToRun, or Native AOT.
4. One repository-owned Inno Setup definition packages the complete publish output.
5. One canonical repository script reproducibly builds `Quail-0.1.0-Setup.exe` and reports its SHA-256.
6. The installer performs a normal per-machine installation under `Program Files\Quail`.
7. `Quail.Cli.exe` remains the CLI filename; `Quail.exe` remains reserved for the future GUI launcher.
8. The installed directory is added once to system PATH, survives reinstall/upgrade correctly, and is removed safely on uninstall.
9. Index/user data remains outside Program Files; `%LOCALAPPDATA%\Quail\Indexes` is documented as the recommended current explicit-index location.
10. The installer does not own/delete user index data and uninstall preservation is tested.
11. Clean install, same-version reinstall, bounded in-place upgrade-path verification, and uninstall are proven on Quail-Lab.
12. Installed CLI behavior is smoke-tested on Quail-Lab using the existing privilege model.
13. A bounded physical-host install/use/uninstall or install/use/reinstall verification proves the package works outside the VM without damaging existing data.
14. Existing automated tests and Release build remain passing.
15. Documentation accurately describes build prerequisites, packaging, PATH, data layout, privilege requirements, and 0.1 limitations.
16. Architecture remains the M06 CLI/core plus packaging; no service/background/UI/no-admin backend is introduced.
17. `docs/milestones/M07-results.md` contains durable evidence including final artifact SHA-256 and size.
18. A verified branch plus open PR is ready for independent QA; merge remains separately gated.

## Release boundary after M07

M07 implementation/QA should produce a release-ready private/test artifact, but **must not** create or move a Git tag, publish a GitHub Release, replace release assets, or make the repository/public artifact public without separate explicit user approval.

After the M07 PR is independently reviewed and merged, the canonical `main` should be verified again. A `v0.1.0` tag and private GitHub Release may then be considered as a separate gated publication step using a fresh installer rebuilt from the verified merge commit.

Public distribution under the Quail name remains separately subject to the repository's name/trademark-clearance requirement and later code-signing/public-release decisions.

## Tooling workflow

Use canonical repository tooling from M04.5/M05.5 where its contract applies:

- `scripts/agent-preflight.ps1`;
- `scripts/vm-verify.ps1`;
- `scripts/prepare-milestone.ps1`.

Milestone preparation should create a new uniquely named `M07-clean` checkpoint only through the canonical preparation script and only after its normal guards pass. Do not restore/delete/rename/overwrite existing checkpoints.

The Inno Setup compiler is an external build prerequisite. The repository build script must discover/use it but must not install or update Inno Setup implicitly.

## Out of scope

M07 must not add:

- Windows Service or IPC;
- automatic/background index maintenance or scheduling;
- per-user/no-admin installer or a new user-mode filesystem indexing backend;
- GUI, global hotkey, tray/settings UI;
- automatic updater or update checker;
- code-signing infrastructure or certificate procurement;
- public release automation;
- MSIX, MSI/WiX, custom installer engine, or multiple competing installer formats;
- .NET single-file deployment;
- trimming, ReadyToRun, Native AOT, or deployment optimization experiments;
- persistent source/catalog configuration;
- implicit/default index discovery that replaces the explicit `--index` CLI contract;
- service-owned `%PROGRAMDATA%\Quail` state;
- application/browser/cloud/content providers;
- CI/CD solely for packaging;
- release tag/GitHub Release/publication without separate approval.

## Stop conditions

Stop instead of expanding scope if:

- correct packaging appears to require implementing a Windows Service, IPC, scheduler, or new filesystem backend;
- Inno Setup cannot package/run the normal self-contained publish without material application redesign;
- PATH integration cannot be made idempotent and safely removable without broadly rewriting environment state;
- uninstall/upgrade would require deleting or migrating user index data;
- the installer would need to elevate or run the CLI in the background during normal installation merely to fabricate application state;
- a physical-host or Quail-Lab packaging failure reveals a substantial existing M06 runtime defect rather than a packaging issue;
- a deployment optimization would require trimming/AOT/single-file/native work not approved for M07;
- unrelated worktree changes, canonical-source conflicts, unavailable required environment/tooling, or approval-gated destructive/publication operations are encountered;
- completing the milestone would require a material architecture expansion beyond packaging the verified M06 CLI/core.

Routine within-scope reversible failures should be diagnosed, fixed, rerun, and continued rather than treated as stop conditions. Long-running install/build/elevated operations must be treated as `RUNNING`, `SUCCEEDED`, `FAILED`, or `UNKNOWN` and polled to a terminal state instead of being classified as failure merely because a child process is still active.

## Git and safety

Follow `AGENTS.md` and canonical tooling.

Routine non-destructive Git and lab preparation may be automated within documented contracts. Explicit approval remains required for merge, branch deletion, force-push, destructive reset/clean, published-history rebase, release tags/releases, destructive operations on existing checkpoints, and other gated destructive actions.

Installing or updating Inno Setup on the physical host is an external machine change and is not an implicit side effect of the repository build script.

## Completion boundary

M07 ends at a verified implementation branch plus an open PR ready for independent QA.

Do not merge, create `v0.1.0`, publish a GitHub Release, or delete the milestone branch without the corresponding explicit user approval.
