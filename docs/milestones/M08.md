# M08 — UI framework spike: WinUI 3 vs Avalonia

## Goal

Choose the production UI framework for Quail 0.2 from an equivalent, measured Windows 11 launcher-shell spike. The outcome must explicitly recommend WinUI 3, Avalonia, or one narrowly defined missing experiment; it must not end with an indeterminate preference.

## Scope

Two isolated prototypes live under `spikes/m08/`: `winui/` and `avalonia/`. They use the common deterministic data in `shared/mock-results.json` and implement a transient, unelevated, frameless Quick Search overlay with a 680 x 360 logical-pixel target, five to six 44-pixel result rows, scrolling for approximately twenty results, live immediate filtering, keyboard selection, Enter test confirmation, Escape dismissal, `Ctrl+Alt+Space` global hotkey, cursor-monitor work-area placement, tray Show/Exit, light/dark/system theme behavior, and Windows Shell type icons.

The shared test protocol is [CONTRACT.md](../../spikes/m08/shared/CONTRACT.md). It requires `visible-ready` only after the overlay is visible, foreground, textbox-focused, and at a comparable rendered presentation point. The harness uses real `SendInput` for hotkey and keyboard tests.

## Methodology

Use pinned stable packages only, Release x64 builds, .NET 10, and an unelevated normal physical Windows desktop session. Do not compare deployment models in this milestone. Benchmark a cold process under normal OS cache conditions after five warmups and 30 measured runs. For resident behavior, run 100 hotkey/focus cycles, 50 keyboard-flow cycles, and 500 summon/hide cycles. Sample hidden idle memory and CPU after a settle period, preserving raw values in the M08 evidence directory.

Use the common M08 harness rather than manually recreating its supported measurement sequence. The physical host, rather than Quail-Lab/RDP, is the source of final GUI figures. Quail-Lab is restricted to bounded repository/build regression sanity.

## Acceptance criteria

Both candidates use the identical data and protocol; no candidate may use Quail.Core, SQLite, real indexing, settings, autostart, installer work, or a provider framework. Every non-blocked candidate supplies the required shell behavior and representative icon styling. Results record exact environment and package versions, raw measurements, failures, visual/DPI findings, complexity, deployment inputs, Linux assessment, limitations, manual remainder, and an explicit final recommendation. The branch must be clean, committed, pushed, and have an open PR to `main`; merge remains separate.

## Out of scope

M08 does not create production `Quail.exe`, real file search, SQLite integration, Quail.Core changes, persistent settings/single-instance/autostart, File Engine/Service/IPC/background indexing, Full Search, providers, updater, installer/deployment choice, MSIX, release work, Linux implementation, cross-platform abstractions, or AI features.

## Stop conditions

Stop rather than expanding scope if canonical host/lab preparation is unsafe; comparable behavior requires changing the contract for just one framework; required shell lifecycle depends on a large, paid, risky, unsupported, or preview-only layer; a true fundamental lifecycle blocker is reproducible; a real File Engine/M09/M10 change becomes necessary; benchmark instability cannot be investigated; or a separately gated destructive/publication action is needed. A candidate with a fundamental blocker is documented with concrete reproduction evidence rather than artificially benchmarked to parity.

## Completion boundary

M08 ends with verified prototypes, durable results, a clear recommendation, and an open PR ready for independent QA. Do not merge, delete branches, force-push, rewrite history, change existing checkpoints, create tags, or publish a release.
