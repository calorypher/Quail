# M09 — WinUI 3 deployment spike

## Goal

Select the deployment model for the future unpackaged `Quail.exe` WinUI 3 shell without building that production application. The decision compares the M08 WinUI fixture under two real Release x64 Inno Setup installations:

- **A — fully self-contained:** .NET and Windows App SDK are app-local;
- **B — framework-dependent + prerequisite bootstrap:** shared .NET Desktop Runtime, Windows App Runtime, and Visual C++ Redistributable are detected and, only when absent or insufficient, installed from pinned Microsoft sources.

## Fixed inputs

The fixture remains `spikes/m08/winui/` and is read-only for M09. It stays on .NET 10, Microsoft.WindowsAppSDK 2.4.0, `win-x64`, unpackaged `WindowsPackageType=None`, and its M08 visible-ready/hotkey/tray lifecycle. No Quail.Core, SQLite, File Engine, service, IPC, production `Quail.exe`, or UI framework comparison is in scope.

## Deployment contract

Variant A sets both `.NET SelfContained=true` and `WindowsAppSDKSelfContained=true`; the latter is required independently for a self-contained Windows App SDK app. Variant B is .NET framework-dependent and retains `WindowsPackageType=None`, which supplies the Windows App SDK bootstrap auto-initializer for an unpackaged executable.

The B fixture uses only Inno Setup code and Microsoft prerequisite installers. Before its application payload is installed it checks the x64 Windows Desktop Runtime, the complete Windows App Runtime 2.4 package set (Framework, Main, Singleton, and x64 DDLM), and VC++ x64 runtime. The .NET family is derived from the generated framework-dependent `runtimeconfig.json`; with the fixture's default roll-forward policy, a higher major runtime does not satisfy .NET 10. The selected VC++ prerequisite binary supplies the minimum registry version used for comparison.

The prerequisite acquisition script resolves redirects during the build, accepts only an approved Microsoft HTTPS host for each prerequisite, and writes the concrete resolved URL plus SHA-256 into the generated installer inputs. The installed setup therefore downloads a byte-stable Microsoft URL matching its embedded hash, not a moving `aka.ms` permalink. A missing prerequisite is downloaded only from that pinned official source, SHA-256 verified before execution, and a failure stops before Quail files are copied. Uninstall owns only the Quail fixture directory and never invokes a prerequisite uninstaller.

## Verification

The M09 result record must preserve T01–T13 from the approved milestone contract: core regression/build, artifact footprint, host startup and hidden-residency measurements, genuine clean-target installs, prerequisite-present and offline B behavior where safe, reinstall, bounded fixture upgrade, uninstall, servicing analysis, and a single recommendation. A clean target must be an actual Windows environment; hiding files or environment variables is not evidence.

`spikes/m09/` contains all M09-specific publish, installer, prerequisite, and measurement tooling. Generated output and downloaded binaries remain under ignored `artifacts/` and `.quail-tooling/`.

`M01-clean` is the approved pre-implementation/project Windows baseline for this spike. It has pre-existing `quailadmin` SSH/minimal automation and the observed SDK/runtime inventory, but no later Quail development state. It is not represented as an untouched retail/factory image. M09 uses its observed prerequisite inventory rather than removing inbox packages to manufacture a more artificial state.

## Stop conditions

Stop rather than substitute a simulated clean target, alter the M08 stack, uninstall host shared runtimes, restore/delete/replace checkpoints, use a third-party bootstrap framework, or extend this spike into M10/M13 work. The authorized Quail-Lab attempt confirmed a further guard: if a required Windows App Runtime can be removed only by uninstalling unrelated inbox applications that depend on it, stop rather than remove those applications. Merge, releases, tags, and branch deletion remain separately gated.
