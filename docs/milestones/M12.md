# M12 — Persistent index configuration and management

## Goal

Make the existing local NTFS index usable by ordinary Quail desktop users without manual database paths or terminal-driven routine index operations.

## Scope and architecture

M12 keeps the existing `WinUI -> small App orchestration -> Quail.Core` direction. The App reuses `NtfsVolume.Validate`, `IndexStore.Build`, `IndexStore.Sync`, `IndexStore.GetStatus`, and the M11 file-search path. It adds a normal top-level `Quail Indexes` window, a small persistent catalog, supported-volume discovery, and a narrow elevated worker hosted by the final `Quail.exe`.

The normal application remains unelevated. Before WinUI, single-instance, or shell startup, `Program.Main` recognizes an internal worker request. The worker accepts only build, rebuild, or refresh for a configured local fixed NTFS mount point, validates elevation and the stable volume identity, and derives the database path itself. It accepts no arbitrary index destination path and starts no GUI, tray icon, or hotkey. The worker returns a narrow exit code; the unelevated process reads the resulting Core status after the worker exits, so no elevated result file is written into user-controlled storage.

## Catalog

`%LOCALAPPDATA%\Quail\indexes.json` is a separate, versioned, inspectable JSON document. Writes use a temporary file and atomic replacement. An entry contains only stable volume identity, current mount point, derived managed database path, and its enabled-for-search flag. Catalog mutations are serialized and publish their new in-memory generation only after persistence succeeds; a failed write leaves disk, entries, and active search paths on the previous committed generation.

Managed databases live in `%PROGRAMDATA%\Quail\Indexes\`; filenames are deterministic SHA-256-derived safe names from the stable volume identity. The elevated worker creates and validates an inheritance-protected Administrators/SYSTEM-writable root, opens every directory without following reparse points, and retains non-delete-shared handles for the operation. It rejects reparse points at the database, SQLite sidecar, staging, previous, root, and parent locations before Core receives a path. A protected per-volume lock provides worker-level mutual exclusion. Pre-release M12 catalogs containing the earlier `%LOCALAPPDATA%\Quail\Indexes` development path are normalized to the protected path when loaded, but the old development database is not adopted or migrated. The catalog is not an index database.

Malformed catalog input is fail-safe: startup continues with no catalog search sources, the error is logged, and the manager shows a concise configuration error. Entries are deduplicated by stable volume identity. A mount whose current identity differs from its catalog identity is unavailable and is never built or synchronized.

## Freshness

`last_refreshed_utc` is optional, backward-compatible index metadata exposed through `IndexStatus`. Build and rebuild set it when the staged database is promoted. Every successful one-shot sync updates it in the same transaction as the final checkpoint, including a zero-record sync. Failed or rebuild-required sync does not update it. Existing compatible databases without the metadata remain searchable and report unknown freshness; this field does not change the schema compatibility contract.

For M12, a complete index refreshed within 24 hours is Ready. At 24 hours or older it remains searchable but the manager reports `Refresh recommended`; a missing timestamp reports `Last refresh unknown`. Rebuild-required has precedence. Quick Search presents a discrete footer notice for a stale or unknown active catalog index; it never schedules, triggers, or retries refresh.

## Search and lifecycle

Normal no-argument startup obtains enabled, compatible, complete catalog paths through an immutable in-memory source snapshot. Catalog actions update that snapshot so M11 Quick Search sees successful build, enable, disable, removal, mount loss, and rebuild-required status without restarting the resident application. A source-generation event invalidates any in-flight search before a new snapshot can publish results; the visible current query is rerun, including transitions to or from zero sources. Repeated `--index <path>` remains the explicit developer/test override: if supplied, it is the entire source list and is never written to the catalog.

The Index Manager is a single ordinary WinUI window. Closing it does not stop resident Quail; operation ownership remains in the resident App, and reopening the manager shows and blocks against a still-running operation. Tray Exit is blocked with a concise message while an index operation is running; otherwise it closes the manager together with the application. It exposes add/build/rebuild/refresh, status, enable/disable, and non-destructive remove. Refresh is a one-shot `IndexStore.Sync`; rebuild-required never triggers an automatic rebuild. Initial Build may enable the entry after a revision-checked catalog commit. Rebuild preserves the current explicit enabled state, and a concurrent explicit disable cannot be overwritten by operation completion.

## Out of scope

No Windows Service, IPC/RPC, generic elevated broker, background watcher, polling sync, arbitrary-folder/removable/network indexing, index-db deletion, installer migration, Full Search, ranking changes, new providers, updater, or UI-polish backlog is introduced.

## Acceptance and verification

Acceptance requires an atomic persistent catalog, identity-safe managed paths and discovery, responsive manager operations through explicit UAC, narrow headless worker validation, M11 search compatibility, and durable test/build/publish/lab evidence. The worker must be exercised from the final self-contained `Quail.exe`; Quail-Lab must perform a real privileged build and sync on its disposable NTFS data volume. Stop if fulfilling these boundaries requires a service, generic broker, Core schema redesign, unsafe lab conditions, material lifecycle regression, or a broad cross-user elevation design.

The supported lab scenario extends the existing `vm-verify.ps1` and uses `Invoke-QuailRemotePowerShell` for its bounded remote payload after normal lab preflight. It must not stage a guest runtime `.ps1`, alter ExecutionPolicy, bypass policy, or replace the canonical SSH/HostKeyAlias/trust-store path.
