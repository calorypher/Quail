# M13-A — Search performance diagnosis

## Goal

Determine where the observed end-to-end Quick Search latency is spent on the real production search path, using privacy-safe instrumentation and repeatable measurements, so the next M13 step can make an evidence-based decision about whether performance remediation is required and, if so, which layer should change.

The motivating observation is approximately 2.1–2.3 seconds from completion of the manually typed `desk` query to visible results on a complete physical-host index of approximately 888,708 records. This milestone must diagnose that delay rather than assume that Core search, ranking, icon loading, rendering, or request coordination is the cause.

M13-A is diagnostic. It does not optimize the search pipeline merely because a plausible optimization exists.

## Context

Earlier Core measurements on an approximately 850,000-entry fixture were materially lower than the observed GUI end-to-end delay. The final Search Ranking measurements included broad short-query medians in roughly the 170–210 ms range, broad FTS around 80–100 ms, and selective FTS in single-digit milliseconds on that fixture. Those figures are not a substitute for production GUI measurements, but they make an end-to-end decomposition necessary before changing Core.

`LatestFileSearchCoordinator` currently owns a single worker. Pending requests are coalesced into one replaceable latest slot, but an already running synchronous `_search()` invocation is not cancelled. Therefore a final typed query may wait behind an in-flight intermediate query. This is a measurement hypothesis, not an established root cause.

After Core completes, Quick Search still performs result mapping, UI-thread collection updates, selection/scroll work, freshness/status bookkeeping, rendering, and asynchronous Shell icon retrieval. These layers must be separated in the evidence where they materially contribute to latency.

## Scope

### Privacy-safe internal instrumentation

Add the smallest instrumentation needed to reconstruct an end-to-end timeline for a search generation or measurement run.

Use one monotonic timing basis, such as `Stopwatch`, for relative event timing within a run.

The trace must be able to distinguish, where applicable:

- input/TextChanged observation;
- query length and search generation/run identity;
- short-query defer scheduling/release for one- and two-character queries;
- request/enqueue time;
- worker dequeue and actual search start;
- queue wait;
- Core search end and Core duration;
- completion dispatch toward the UI thread;
- start and end of result mapping;
- result collection/UI apply work;
- freshness/status bookkeeping when it occurs on the result path;
- first render boundary at which the new result state is visible;
- icon retrieval/load timing separately from first visible textual results;
- result count;
- relevant index scale context such as record count and database size;
- process CPU and working set in a bounded form suitable for the measurement campaign;
- fresh-process-first-search versus warm-same-session context.

Instrumentation may remain as small internal diagnostic plumbing after M13-A when it is generally useful, privacy-safe, disabled or effectively zero-cost during normal use, and does not expose user content. Do not retain milestone-specific dead code or a broad diagnostics framework merely because instrumentation was needed here.

A permanent user-facing Diagnostics Mode, support bundle, Settings UI, retention policy, export workflow, remote support workflow, or similar product surface is outside M13-A. Such a feature may be evaluated later and should be able to reuse appropriate privacy-safe internal plumbing when doing so is justified.

### Privacy constraints

The M13-A trace and durable evidence must not record or persist:

- query text;
- file or directory names;
- filesystem paths;
- usernames;
- machine identifiers;
- other content-derived identifiers that would allow reconstruction of the searched data.

Allowed fields include bounded non-content metadata such as:

- query length;
- generation/run ID local to the process or trace;
- stage timings and durations;
- queue delay;
- result count;
- index record count;
- database size;
- process CPU/working set;
- fresh/warm/session classification.

No remote telemetry is introduced.

Existing test/QA pipes that emit content-bearing fields such as query text or result names must not be used as the durable M13-A performance trace format on real user data unless those content fields are removed from the measurement path or otherwise prevented from being recorded.

### Measurement matrix

Run the production Release search path against the complete physical-host index when available.

The minimum matrix must compare:

1. full query supplied at once;
2. normal character-by-character typing;
3. fresh-process first search;
4. warm same-session search.

Use at least one representative broad query of three or more characters whose typed form exercises intermediate queries, including the existing `des` -> `desk` class of scenario, and at least one more selective query of three or more characters. The exact query text is an operator input and must not be persisted in trace evidence.

For the primary conditions, collect enough valid repetitions to separate a repeatable effect from an isolated run. Five valid measured runs per condition after any explicitly documented warm-up is the default minimum unless the evidence demonstrates that a different bounded count is more appropriate.

Do not describe a normal first process search as a true OS cold-cache measurement unless the Windows filesystem/page cache has actually been controlled. Prefer the terms `fresh-process first search` and `warm same-session search`.

### Physical-host WinApp execution

Prefer WinApp CLI/UI Automation on the physical Windows host for the interactive measurement matrix when it can run in the same unlocked interactive desktop session as Quail.

Use a bounded feasibility check first:

- verify the supported WinApp CLI is available or install it through the approved official channel if needed;
- launch/find the Release Quail process in the interactive user session;
- locate the Quick Search query control through UI Automation;
- verify focus can be placed on the query control;
- verify a full-value/paste-equivalent case can be driven repeatably;
- verify real character-by-character input can be driven repeatably, preferably through supported key-input functionality so successive `TextChanged` events represent typed intermediate queries.

If physical-host WinApp works reliably, use it as the default executor for the repeatable typed/full-query matrix. The user should not interact with the mouse, keyboard, foreground window, desktop lock state, or focus during the bounded interactive batch.

Do not expand M13-A into a general GUI-automation project. If WinApp on the physical host encounters a concrete execution-model or reliability blocker after a short bounded attempt, document that blocker and use a small manual typed/full-query gate instead. Do not build an inter-session broker, persistent Scheduled Task bridge, PsExec-style mechanism, pixel-automation framework, UAC automation, or general-purpose Windows automation layer.

The earlier QA Automation feasibility result remains relevant: WinApp/UIA itself worked in an interactive VMConnect session; the deferred blocker was unattended SSH-to-interactive-desktop execution, not a demonstrated WinUI 3 or WinApp incompatibility.

## Required diagnostic questions

M13-A evidence must answer at least the following:

1. Does a final typed query spend material time waiting behind an already in-flight intermediate query?
2. How much of end-to-end latency is Core search time versus queue wait?
3. How much time is spent after Core before the new textual results are first visibly rendered?
4. Are mapping, result collection updates, selection/scroll work, or freshness/status bookkeeping individually material contributors?
5. Does Shell icon retrieval delay first visible results, or does it only enrich rows after textual results are already visible?
6. How different are full-query-at-once and typed character-by-character behavior?
7. How different are fresh-process-first-search and warm-same-session behavior?
8. Is the approximately 2.1–2.3 second observation reproducible on the current Release implementation and complete large index?

## Out of scope

Do not implement performance remediation in this milestone solely because the trace reveals an obvious candidate.

Specifically outside scope unless required only to make the instrumentation correct and non-distorting:

- cancellation of an in-flight Core search;
- changing global debounce behavior or the existing one/two-character defer policy;
- changing ranking semantics;
- changing SQL candidate retrieval strategy;
- changing the index schema or persistent ranking metadata;
- redesigning icon caching/loading policy;
- UI polish or presentation changes;
- packaging, prerequisite bootstrap, installer, reinstall, uninstall, or 0.1 -> 0.2 upgrade work;
- Windows Service or continuous USN maintenance changes;
- permanent user-facing diagnostics UI or support-bundle workflow;
- remote telemetry;
- a general GUI automation framework.

If a correctness bug must be fixed merely to obtain valid measurements, keep that change minimal, document why measurement was impossible without it, and do not use the exception to broaden the milestone into remediation.

## Acceptance criteria

M13-A is complete when all of the following are true:

1. A repeatable privacy-safe trace can reconstruct the relevant end-to-end search timeline without persisting query text, names, paths, usernames, machine IDs, or equivalent user content.
2. The production Release path has been measured for full-query-at-once versus character-by-character input and fresh-process-first-search versus warm-same-session behavior on the physical host's complete large index when available.
3. The typed-query evidence shows each search generation that actually starts Core work and is sufficient to determine whether the final query waits behind an in-flight intermediate search.
4. Queue wait, Core duration, and post-Core/UI time are separated.
5. Mapping, result apply/collection work, relevant status/freshness bookkeeping, first visible render, and icon loading are separated sufficiently to identify any material contributor.
6. At least one representative broad >=3-character query and one more selective >=3-character query are covered by the bounded matrix.
7. Each primary condition has at least five valid measured repetitions unless the results document and justify another bounded count.
8. A representative slow run has no unexplained timing gap greater than 100 ms. If such a gap remains, the milestone is not conclusive and the missing boundary must be identified explicitly.
9. Normal Release regression tests and the relevant Release application build pass after instrumentation changes.
10. Durable evidence records the methodology, aggregate measurements, limitations, and root-cause classification without private search content.
11. The final result makes exactly one evidence-based disposition:
    - `remediation required`, with the responsible layer(s) and measured reason identified;
    - `no performance remediation required`, with evidence explaining why the observed latency is acceptable/not reproducible; or
    - `diagnosis inconclusive`, with the exact missing evidence or blocker identified.

There is no arbitrary M13-A requirement to reduce search latency below a preselected number. Remediation targets belong to the follow-up step after the bottleneck is established.

## Verification

At minimum:

- run the normal full Release regression suite relevant to the current repository state;
- build `Quail.App` in Release for `win-x64`;
- add focused automated tests for the instrumentation/timing behavior where direct tests provide meaningful confidence;
- verify that normal operation with diagnostics disabled or inactive does not emit private search content through the M13-A trace;
- execute the physical-host measurement matrix through WinApp when its bounded interactive feasibility check passes;
- otherwise execute the smallest manual physical-host typed/full-query matrix needed to complete the same timing evidence;
- use synthetic/fixture measurements only as supporting control evidence, not as a substitute for the physical-host production-path result;
- retain durable, privacy-safe evidence under `docs/milestones/evidence/M13-A/` or an equivalently clear repository location;
- record final conclusions in `docs/milestones/M13-A-results.md`.

Successful compilation, one fast trace, or reproducing the old video timing alone is not sufficient completion evidence.

## Stop conditions

Stop rather than broadening the task if any of the following occurs:

- valid instrumentation would require a material redesign of the production search architecture;
- the observed problem cannot be reproduced on either the physical large index or a representative controlled fixture and there is insufficient evidence to classify it;
- obtaining the measurements would require deleting, rewriting, rebuilding, or otherwise destructively changing user data beyond an already-approved normal operation;
- the required physical-host interactive test would require an unsafe or persistent automation bridge, elevated input injection, UAC automation, or another material security-boundary change;
- the diagnosis reveals a remediation that materially expands scope into architecture, schema, packaging, or another separately planned area;
- repository requirements conflict with this specification;
- unrelated worktree changes or environment state make the evidence unreliable.

When a root cause becomes obvious early, finish only the bounded measurements needed to confirm it and characterize its contribution. Do not implement the fix automatically in M13-A.

## Deliverables and completion boundary

The milestone should leave:

- the minimum useful instrumentation required by the accepted design;
- privacy-safe measurement evidence;
- `docs/milestones/M13-A-results.md` with methodology, aggregates, limitations, and disposition;
- any narrowly justified automated tests or measurement helper scripts;
- a verified implementation branch and pull request ready for independent QA.

The implementation agent should note whether retained internal instrumentation is generally reusable for a future explicit user-triggered diagnostics feature, but must not design or implement that product feature in M13-A.
