# M13-B — Short-query responsiveness remediation

## Goal

Remove the M13-A finding in which a stale one- or two-character Quick Search fallback can occupy the single synchronous search worker and delay a newer three-or-more-character query for seconds. Preserve Core search, SQLite schema, candidate retrieval, ranking, result limits, and CLI semantics.

## Scope

- Keep one- and two-character Quick Search support, but start it only after 1,000 ms of uninterrupted input.
- Start Quick Search queries of three or more characters immediately.
- Use two explicitly bounded, latest-wins execution lanes: one short-query lane and one interactive lane. Each lane has at most one running Core search and one replaceable pending request; the mechanism therefore runs at most two Core searches concurrently.
- Ensure a running short search cannot delay interactive work and that a stale short completion cannot update the current UI.
- Retain and minimally extend the opt-in, privacy-safe M13-A trace only as needed to identify the lane.
- Add focused scheduling, stale-completion, bounded-pending, disposal, and existing-coalescing regression coverage.
- Measure standalone one- and two-character fallbacks and the bounded M13-B physical-host scenarios without altering the real index.

## Out of scope

No SQLite schema or candidate-SQL redesign, one/two-gram index, native SQLite interruption, Core async rewrite, general cancellation framework, ranking/search semantic change, UI redesign, debounce setting, packaging, M13-C, or M13-D work.

## Acceptance criteria

1. Empty input cancels the pending short defer and stale completions cannot restore results.
2. One- and two-character input waits a trailing 1,000 ms; every intervening input resets that wait.
3. Normal fast `1 -> 2 -> 3 -> 4` typing starts no short Core search; three-or-more-character input starts immediately.
4. A running short fallback does not block an interactive search, and its stale completion is discarded.
5. Concurrency remains bounded to one running search in each of the two lanes.
6. Core and CLI one/two-character semantics and all existing ranking semantics remain unchanged.
7. Release tests and the warning-free `Quail.App` `win-x64` Release build pass.
8. Privacy-safe physical-host evidence demonstrates the remediation, including standalone short-query behavior and a forced in-flight short-to-interactive case when feasible.

## Verification

Run focused automated tests, the complete Release regression suite, the Release `win-x64` application build, then use the existing M13-A WinApp CLI/UIA route for the bounded physical-host matrix only after the user confirms that the desktop is unlocked and will remain undisturbed. Retain aggregate, non-content-bearing evidence under `docs/milestones/evidence/M13-B/` and record results in `M13-B-results.md`.

## Stop conditions

Stop for a decision rather than expanding scope if two concurrent read searches cause SQLite correctness/locking issues; isolating the lanes requires a material Core redesign; interactive work remains materially blocked by resource contention requiring native cancellation; schema, ranking, or query semantics would need to change; or physical evidence would require destructive index changes.
