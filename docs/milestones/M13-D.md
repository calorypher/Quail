# M13-D — Technical release-candidate validation

## Goal

Freeze one exact Quail 0.2 technical release candidate from the post-M13-C
mainline and determine whether the complete installed product is sufficiently
correct, stable, responsive, and lightweight to proceed to the M14 public
release-readiness audit.

The only permitted dispositions are:

- `technical RC ready for M14`;
- `remediation required`; or
- `RC decision required`.

A successful build alone is not a passing disposition.

## Scope

- Record this approved specification before the candidate freeze.
- Run focused Windows App Runtime detector fixtures, the full Release regression
  suite, warning-free Release App and CLI builds, production installer build,
  payload guards, version checks, and committed-prerequisite pin checks.
- Freeze and preserve one exact production installer, with source commit,
  installer and installed executable hashes, payload manifest/tree identity,
  payload count/bytes, and prerequisite-pin identity.
- Install that exact verified candidate in Quail-Lab and validate the normal
  installed-product lifecycle: resident startup, single instance, hotkey,
  focus, dismiss, tray actions, Settings, Index Manager, persisted catalog,
  normal search/open/error states, and clean Exit.
- Perform one controlled, real privileged Refresh on a Quail-Lab index using
  the exact installed candidate. The unelevated resident App must remain
  healthy after the elevated worker exits and the controlled result must become
  searchable.
- Use the existing M10 lifecycle harness and its `visible-ready` boundary for
  resident warm-up, 100 hotkey samples, 50 keyboard/focus flows, 500
  summon/Escape cycles, resource checkpoints, and final Exit.
- Measure 30 production starts after required conditioning and record the
  comparable startup boundary and p50/p95/max.
- Sample hidden idle resources for at least 120 seconds: working set, private
  bytes, CPU, handles, USER objects, and GDI objects.
- On the physical host, use the exact installed product with the existing
  privacy-safe M13 trace/UIA route against the existing complete index. Verify
  broad typed search, a selective control, and a bounded forced in-flight short
  query spot check without rebuilding the host index.
- On the physical host, after explicit interactive-session confirmation, run a
  bounded installed-product GUI smoke including hotkey/focus, compact/expanded
  behavior, a real indexed result, navigation/open, Settings, Index Manager,
  tray actions, restart, and orphan-process check. Check cross-DPI behavior
  only if a mixed-DPI topology is currently available.
- Preserve aggregate durable evidence under `docs/milestones/evidence/M13-D/`
  and record the final assessment in `docs/milestones/M13-D-results.md`.

## Candidate freeze and integrity

M13-C's final installer is retained as packaging evidence only:

- source `c6ceba94605a3cbfd85972d9be945e7a181ca470`;
- 23,664,414 bytes;
- SHA-256 `a621be3eeb85019f422dd9e763a90e0fb0836ff19b13a3aad42e2f59c49c2e2f`.

M13-D must create a new candidate from the current validated mainline after
adding this specification. It must be copied, together with its manifest, to
an ignored stable path such as `artifacts/rc/0.2.0/<candidate-short-sha>/` and
must never be overwritten by a later build. Every environment verifies the
installer SHA-256 before and after copy/transfer and records installed
`C:\Program Files\Quail\Quail.exe` and `Quail.Cli.exe` identities.

If production code, project configuration, packaging, or runtime behavior
changes after freeze, the previous candidate is invalid. A new exact candidate
must be frozen and the affected verification matrix rerun; cross-cutting
changes require the full campaign. Documentation-only results/evidence commits
do not require a rebuild.

## Acceptance criteria

`technical RC ready for M14` requires one unambiguous candidate identity,
passing automated/build gates, successful Quail-Lab installed-product and
protected Refresh checks, successful physical-host installed smoke, reliable
hotkey/focus lifecycle, no 500-cycle leak trend, practically idle CPU, an
explicit acceptable memory assessment against the approximately 200 MiB Quail
0.2 release criterion,
no material M13-B search responsiveness regression, matching candidate identity
in every environment, and no unresolved release-blocking defect.

For the installed candidate, hotkey-to-`visible-ready` targets are p50 <= 50
ms and p95 <= 100 ms, with 100/100 valid summons and no focus failure.
Startup targets are p50 <= 500 ms and p95 <= 750 ms after five conditioning
runs; an unexplained valid run above 1000 ms is a finding. Hidden idle CPU
target is average <= 0.05% with no sustained activity. For Quail 0.2, stable
physical hidden-idle working set at or below approximately 200 MiB meets the
release criterion when CPU and resource stability also pass. Approximately 100
MiB remains the long-term lightweight aspiration. The decision follows the
M13-D 167.6 MiB / 165.1 MiB physical observation, the approximately 174.5 MiB
/ 170.8 MiB M08 minimal WinUI reference baseline, and the absence of a
monotonic leak trend; it does not claim that the historical 100 MiB target was
met.

Physical broad typing (four or more characters) requires at least ten valid
warm runs with median input-to-first-text-render <= 250 ms, p95 <= 500 ms,
interactive-lane queue wait < 100 ms in every valid run, and no stale-short
stall. A selective control requires at least five warm runs. The forced
in-flight short spot check requires at least five valid trials confirming
independent interactive work, stale-result suppression, queue wait < 100 ms,
and no stale render.

## Out of scope

No new product features, Full Search, recents, pinned results, Windows Service,
continuous USN maintenance, updater, MSI/MSIX, winget, Store, code signing,
trimming, Native AOT, public-repository audit, licensing/notices, trademark
work, release tag, GitHub Release, visibility change, or branch deletion.

The complete M13-C destructive prerequisite/install/upgrade matrix is not
repeated unless the exact candidate changes its application payload contract.
The M12 adversarial protected-storage matrix is not repeated unless the
production path changes.

## Stop conditions

Stop and record `RC decision required` or `remediation required` rather than
expanding scope if memory materially exceeds the product target without a
simple local cause, a lifecycle leak requires redesign, hotkey/focus requires a
window-model change, search needs Core/schema/ranking changes, installer
validation needs a deployment-architecture change, the protected boundary
needs security redesign, physical-host work would be destructive, system
runtimes would need removal, new general automation would be required,
unrelated worktree changes appear, or canonical requirements conflict.

## Completion boundary

Commit the specification, results, and aggregate evidence (plus any narrowly
scoped defect fix and regression test), push the verification branch, and open
a pull request to `main`. Do not merge, delete branches, create a tag, publish
a release, or change repository visibility. The handoff reports exact source
and artifact identities, measurement results, limitations, disposition, and
whether M14 may begin after independent QA and merge.
