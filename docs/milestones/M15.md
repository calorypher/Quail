# M15 — Core / FileSystem Boundary Extraction

## Status

**Approved for implementation.**

This milestone is the first implementation milestone of Quail 0.3. It is a behavior-preserving architectural extraction, not a feature, performance, ranking, storage-redesign, or provider-framework milestone.

## Goal

Turn `Quail.Core` into the actual application/search core used by the product and move the existing filesystem/NTFS implementation behind a clear filesystem-specific module.

The expected production module is `src/Quail.FileSystem/Quail.FileSystem.csproj` unless implementation evidence gives a concrete, simple reason for an equally narrow alternative name.

The intended semantic dependency direction for normal search is:

```text
Quail.App
    -> Quail.Core
        -> Quail.FileSystem
```

Filesystem-specific administrative surfaces may depend directly on `Quail.FileSystem` where appropriate, including the CLI, elevated Build/Rebuild/Refresh paths, and filesystem index-management glue. Do not create a dependency cycle to achieve this split.

## Scope

### FileSystem extraction

Move filesystem-specific responsibilities out of `Quail.Core`, including where applicable:

- `IndexStore` and filesystem SQLite persistence;
- filesystem index schema and FTS implementation;
- NTFS/MFT enumeration and USN journal handling;
- volume validation/discovery primitives;
- filesystem metadata acquisition;
- native filesystem identity, including `NativeFileId`;
- build/rebuild/sync/status implementation;
- journal/checkpoint types and lifecycle;
- path reconstruction;
- filesystem-specific candidate retrieval and multi-index search implementation;
- filesystem-specific ranking implementation when that is the smallest behavior-preserving placement;
- filesystem-specific open/action implementation;
- helpers that exist only to support the filesystem source.

Do not intentionally change these behaviors merely because the code is moving. After M15, `Quail.Core` must not remain the filesystem engine under a different folder structure.

### Minimal Core search boundary

Create only the minimal application/search contracts required by current product surfaces and the already approved Quail 0.3 direction.

Core may expose the search request/query, GUI-usable result information, currently supported filter/metadata information, and an opaque identity/action sufficient to operate on a selected result.

The exact type names and internal structure are implementation decisions. Do not design a future provider SDK.

Normal GUI-facing contracts must not expose:

- `IndexStore`;
- `NativeFileId`;
- SQLite types;
- database paths as the public search-result source identity;
- NTFS volume/journal/checkpoint internals;
- filesystem-native search-result wrappers.

The GUI may receive ordinary product information already required by current behavior, such as display name, path/context, file/directory kind, extension/type, logical size, modified timestamp, and existing attribute-derived metadata.

Opening a normal search result must use an opaque Core-level identity/action from the App's perspective. Preserve source-native NTFS identity internally; do not reduce filesystem identity to the current path merely to fit the Core model.

### Application migration

Migrate the normal Quick Search path to the Core-level boundary. Normal application search must no longer construct `IndexStore`, consume `IndexedFileSearchResult`, carry `NativeFileId` in presentation models, use an index database path as a public `SourceIdentity`, or directly invoke filesystem-native opening logic.

Preserve existing asynchronous search scheduling, coalescing, cancellation, stale-result protection, short-query deferral, result/window lifecycle, keyboard behavior, and opening behavior. Do not redesign Quick Search UX.

### Filesystem administration and CLI

Preserve current filesystem administrative behavior. The CLI remains explicitly filesystem-oriented and may depend directly on `Quail.FileSystem`.

Preserve the user-visible behavior of build, rebuild, sync/refresh, status, search, and open commands, along with GUI index management, configured-index catalog behavior, Build/Rebuild/Refresh, status reporting, and the existing elevated-operation flow.

Mechanical namespace and type changes caused by the extraction are acceptable.

### Search and ranking invariants

Preserve current search semantics and ranking behavior. Do not intentionally change:

- literal case-insensitive indexed-name substring semantics;
- short-query fallback behavior;
- FTS/trigram behavior for applicable queries;
- current candidate windows;
- exact/prefix/token-prefix/substring text tiers;
- current location/path-aware ranking;
- deterministic ordering and tie-breaking;
- global result limits;
- current metadata filters;
- current multi-index behavior.

The accepted limitation where more than the candidate limit within the same text tier can hide a more useful path-aware result remains owned by M18. Do not fix it in M15.

### Index storage compatibility

Backward-compatible reuse of Quail 0.2 filesystem index databases is not a hard requirement. The filesystem index is derived data and may be rebuilt when necessary.

Do not change the schema or storage format merely to make the architectural split cleaner, and do not introduce migration machinery solely to preserve a disposable derived index.

Preserve user configuration, configured/indexed-volume catalog state, and protected-storage location where applicable. Preserve the existing storage and identity design unless a small change is directly required by the extraction.

If the existing Quail 0.2 index format remains compatible, it should continue working normally. If the simplest correct M15 implementation requires a narrowly justified incompatible schema or format change, a one-time rebuild is acceptable. Quail must detect the incompatible state safely and require or clearly communicate rebuild rather than silently trusting, partially consuming, or corrupting the incompatible index. Complex backward migration is not required.

A simple schema/version incompatibility that safely results in `Rebuild required` is not itself a stop condition.

### Privilege and security invariants

Preserve the existing Quail 0.2 privilege/security boundary, including:

- same-account UAC elevation;
- the narrow elevated worker responsibility;
- protected `%PROGRAMDATA%` index storage;
- current ACL/trust assumptions;
- reparse-point protections and protected handle/path validation;
- per-volume/operation locking;
- SQLite quiescent lifecycle used by elevated mutations;
- safe return to the unelevated application;
- installer privilege model.

Mechanical namespace or assembly changes are expected. Do not introduce a new privileged IPC mechanism, Windows Service, generic elevated agent, broader worker command surface, background-maintenance responsibility, or updater responsibility.

### Dependency and packaging consequences

After extraction, `Quail.Core` should not depend on `Microsoft.Data.Sqlite` unless a concrete non-filesystem Core requirement remains.

Do not perform dependency cleanup for aesthetic reasons beyond what is directly justified by the new boundary.

Because adding `Quail.FileSystem` changes the production assembly/dependency graph, inspect and update canonical build, publish, installer, payload, and dependency guards as required so the new assembly and its runtime dependencies are actually shipped. Do not redesign the installer.

### Tests and durable evidence

Adapt or add tests only as needed to prove the new boundary and behavior preservation. A cosmetic mass rename or reorganization of the existing test project is not required.

Provide appropriate automated coverage for:

- Core-level request/result projection;
- opaque GUI-facing result identity/open behavior;
- normal App search no longer depending on native filesystem identifiers;
- existing search/ranking semantics;
- multi-index/global-limit behavior;
- CLI behavior;
- build/sync/status behavior;
- schema incompatibility/rebuild detection if M15 introduces it;
- existing-index behavior if the format remains unchanged;
- relevant existing security/storage regressions.

Record milestone results in `docs/milestones/M15-results.md` and add focused evidence under `docs/milestones/evidence/M15/` only where durable evidence is useful.

## Explicitly out of scope

Do not introduce or implement:

- a public provider SDK or generalized `IProvider` framework for hypothetical providers;
- provider registry/discovery, dynamic plugin loading, provider version negotiation, generalized capability or lifecycle frameworks;
- a universal object/source database;
- browser, cloud, mail, calendar, or application providers;
- cross-source ranking or a generic source synchronization framework;
- M16 performance investigation or targets;
- M17 search optimization;
- M18 ranking changes or the known same-tier recall fix;
- M19 maintenance/service architecture work;
- M20 continuous background maintenance;
- Full Search UI or new filters;
- Created-time acquisition or filesystem history;
- browser history/bookmarks;
- service/IPC architecture;
- later startup/settings work;
- unrelated UI polish or refactoring;
- speculative cross-platform abstractions;
- new installer features.

There is currently one real source. The first heterogeneous source should later validate which abstractions are genuinely shared. A concrete Core-to-FileSystem boundary is sufficient for M15.

## Acceptance criteria

M15 passes only when all of the following are true:

1. `Quail.FileSystem` exists as a separate production module, unless a documented equally narrow alternative was justified.
2. `Quail.Core` no longer owns NTFS/MFT/USN implementation, filesystem SQLite persistence, checkpoint/build/sync internals, native filesystem identity implementation, or filesystem shell-open implementation.
3. `Quail.Core` no longer requires `Microsoft.Data.Sqlite` unless a concrete non-filesystem Core use remains and is documented.
4. Normal App-to-Core search does not expose `IndexStore`, `NativeFileId`, filesystem result wrappers, or database paths as result source identity.
5. Native NTFS identity remains preserved internally rather than being replaced by path identity.
6. Quick Search preserves current query semantics, result behavior/order/global limit, keyboard/open behavior, and scheduling/lifecycle behavior.
7. CLI user-visible contracts remain usable.
8. GUI filesystem administration and status remain usable with the existing privilege/protected-storage boundary.
9. If the 0.2 index format remains compatible, existing healthy indexes remain usable. If a narrowly justified incompatible format is introduced, the old format is safely detected as rebuild-required and a rebuild produces a healthy usable index without migration machinery.
10. There are no intentional ranking, query, privilege, installer, or unrelated storage-behavior changes.
11. The complete existing automated test suite passes after necessary adaptation.
12. Release builds for App and CLI pass without new warnings.
13. Canonical build/publish/package verification proves `Quail.FileSystem` and required dependencies are shipped correctly.
14. Representative Quail-Lab smoke verifies production App startup, Quick Search, result opening, CLI status/search/open, safe-lab Build/Rebuild/Refresh, a controlled change becoming visible after Refresh, and no regression in unelevated reads of the protected ProgramData index after elevated worker completion.
15. Static architecture review confirms the intended boundary and absence of speculative provider/plugin/capability machinery or dependency cycles.
16. Changed production code remains readable and complies with `AGENTS.md` formatting expectations.

M15 does not require repeating the full M13-D physical-host validation campaign by default. Use the physical host only if Quail-Lab cannot exercise a required boundary, an environment-specific defect appears, or the implementation unexpectedly changes a host-sensitive integration boundary.

## Verification

Verification must include:

- explicit static dependency/boundary inspection and focused code searches;
- the complete automated test suite plus focused new boundary tests;
- Release builds for App and CLI;
- canonical publish/build/installer/payload checks affected by the new production assembly;
- index compatibility verification appropriate to the chosen implementation: either use of an existing 0.2-format index without rebuild, or safe detection of incompatibility followed by a successful rebuild;
- representative Quail-Lab runtime verification as described above;
- final diff/scope/readability inspection.

The final handoff must include exact branch and HEAD, clean worktree status, the resulting dependency structure, implementation summary, tests/builds/package verification, index-compatibility decision and evidence, Quail-Lab evidence, security-boundary confirmation, limitations/deviations, and the PR link/number.

## Stop conditions

Stop and report instead of materially expanding scope if the extraction requires:

- material redesign of the storage model;
- complex index migration machinery;
- changes to privilege/UAC semantics;
- changes to protected-storage trust/ACL architecture;
- new privileged IPC or a Windows Service/background-maintenance architecture;
- a broad provider SDK, lifecycle, or capability framework;
- search-engine or ranking redesign;
- material Quick Search UX changes;
- material deviation from the approved `App -> Core -> FileSystem` direction;
- a high-impact security or integrity defect whose proper fix materially exceeds M15;
- conflicting canonical repository requirements or unrelated worktree changes that cannot safely coexist with the milestone.

Routine compile errors, namespace/project-reference work, focused test adaptation, packaging inclusion of the new required assembly, refactor regressions, and a simple safe index-version bump requiring rebuild when genuinely justified are ordinary in-scope implementation work.

After all acceptance criteria pass and the branch plus PR are ready for independent QA, stop. Do not proceed into M16.
