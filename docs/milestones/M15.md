# M15 — Core / FileSystem Boundary Extraction

## Status

**Approved for implementation, with source-neutral dependency direction clarified during QA.**

This milestone is the first implementation milestone of Quail 0.3. It is a behavior-preserving architectural extraction, not a feature, performance, ranking, storage-redesign, runtime-plugin-loading, or provider-framework milestone.

## Goal

Turn `Quail.Core` into the actual source-neutral application/search core used by the product and move the existing filesystem/NTFS implementation into a clear filesystem-specific module.

The expected production module is `src/Quail.FileSystem/Quail.FileSystem.csproj` unless implementation evidence gives a concrete, simple reason for an equally narrow alternative name.

The required compile-time dependency direction is:

```text
Quail.App ---------> Quail.Core
                         ^
                         |
Quail.FileSystem -------+

later:
Quail.Browser ----------+
Quail.Mail -------------+
Quail.Cloud ------------+
```

`Quail.Core` must not reference `Quail.FileSystem` or another concrete source. Concrete sources implement minimal Core-owned search contracts and depend on Core, not the reverse.

`Quail.App -> Quail.FileSystem` may remain temporarily where it is the simplest static composition path or where App hosts explicitly filesystem-specific administration/UAC UI. Those direct references must be isolated from the normal Quick Search/search-coordinator/presentation pipeline so that later optional source loading is a composition change rather than another broad search-stack refactor.

The long-term direction is physical source optionality: a first-party source module such as `Quail.FileSystem.dll` should eventually be omittable from a deployment, removing that source's results, source-specific actions, indexing/synchronization behavior, and source-specific settings without breaking the rest of Quail. M15 does not implement runtime module loading; it establishes the dependency direction needed to make that future change small.

## Scope

### FileSystem extraction

Move filesystem-specific responsibilities out of `Quail.Core`, including where applicable:

- `IndexStore` and filesystem SQLite persistence;
- filesystem index schema and FTS implementation;
- NTFS/MFT enumeration and USN journal handling;
- volume validation/discovery primitives;
- filesystem metadata acquisition;
- native filesystem identity, including `NativeFileId`;
- build/rebuild/sync/status implementation;
- journal/checkpoint types and lifecycle;
- path reconstruction;
- filesystem-specific candidate retrieval and multi-index search implementation;
- filesystem-specific ranking implementation when that is the smallest behavior-preserving placement;
- filesystem-specific open/action implementation;
- helpers that exist only to support the filesystem source.

Do not intentionally change these behaviors merely because the code is moving. After M15, `Quail.Core` must not remain the filesystem engine under a different folder structure.

### Minimal Core search boundary

Create only the minimal source-neutral application/search contracts required by current product surfaces and the already approved Quail 0.3 direction.

A small internal contract such as `ISearchSource`, or an equally narrow dependency-inversion mechanism, is explicitly allowed when needed to let Core orchestrate concrete search sources without referencing them. It should cover only demonstrated needs such as:

- accepting the current search request;
- returning Core-level results suitable for normal presentation;
- retaining/routing an opaque result action to the source that owns it;
- allowing Core to aggregate results from registered sources.

Do not add provider lifecycle, discovery, version negotiation, capability matrices, authentication abstractions, synchronization frameworks, or runtime plugin loading in M15.

Normal GUI/Core contracts must not expose:

- `IndexStore`;
- `NativeFileId`;
- SQLite types;
- database paths as the general result identity;
- NTFS volume/journal/checkpoint internals;
- filesystem-native search-result wrappers.

The normal Core result model also must not require every future result to be a file. Filesystem concepts such as `FullPath`, `IsDirectory`, logical size, NTFS attributes, or filesystem timestamps may exist in filesystem-specific data/adapters where needed, but they must not define the mandatory ontology of every Core search result merely because FileSystem is currently the only production source.

Core should expose only the presentation/action information genuinely required by current search surfaces. Do not invent a universal metadata bag or final heterogeneous object model in M15; later real sources and M22 Full Search should extend the model only when demonstrated requirements appear.

Opening or otherwise activating a normal result must use an opaque Core-level action from the App's perspective. Preserve source-native NTFS identity inside `Quail.FileSystem`; do not reduce filesystem identity to the current path merely to fit the Core model.

### Source-neutral application search path

Migrate the normal Quick Search path to source-neutral Core contracts. Normal application search must no longer construct `IndexStore`, consume filesystem result wrappers, carry `NativeFileId` in presentation models, use an index database path as general source identity, or directly invoke filesystem-native opening logic.

Normal search-flow types in App/Core should use source-neutral names unless the type genuinely handles only filesystem behavior. In particular, file-specific names such as `FileSearchApplicationService`, `FileSearchService`, `LatestFileSearchCoordinator`, `FileSearchPresentation`, or equivalents should not remain on the generic search orchestration/presentation path merely because FileSystem is the first source.

Preserve existing asynchronous search scheduling, coalescing, cancellation/stale-result protection, short-query deferral, result/window lifecycle, keyboard behavior, and opening behavior. Do not redesign Quick Search UX.

A focused test using one or more non-filesystem fake search sources should prove that Core search orchestration can run without constructing filesystem objects and does not structurally assume that FileSystem is the only possible source.

### Filesystem administration and CLI

Preserve current filesystem administrative behavior. The CLI remains explicitly filesystem-oriented and may depend directly on `Quail.FileSystem`.

Filesystem-specific administration may continue to have an App frontend. App may host UI, UAC invocation, and static composition, but NTFS, filesystem persistence, protected-storage implementation, filesystem security validation, and filesystem-specific search/index logic belong to `Quail.FileSystem` rather than generic Core or the normal App search pipeline.

Preserve the user-visible behavior of build, rebuild, sync/refresh, status, search, and open commands, along with GUI index management, configured-index catalog behavior, Build/Rebuild/Refresh, status reporting, and the existing elevated-operation flow.

Mechanical namespace and type changes caused by the extraction are acceptable.

Do not generalize filesystem index health/record counts/database size into mandatory capabilities of every future source. If normal search needs a small source-neutral availability signal, add only the minimum demonstrated semantics; filesystem administration/diagnostics remain filesystem-specific.

### Search and ranking invariants

Preserve current search semantics and ranking behavior. Do not intentionally change:

- literal case-insensitive indexed-name substring semantics;
- short-query fallback behavior;
- FTS/trigram behavior for applicable queries;
- current candidate windows;
- exact/prefix/token-prefix/substring text tiers;
- current location/path-aware ranking;
- deterministic ordering and tie-breaking;
- global result limits;
- current metadata filters;
- current multi-index behavior.

The accepted limitation where more than the candidate limit within the same text tier can hide a more useful path-aware result remains owned by M18. Do not fix it in M15.

### Index storage compatibility

Backward-compatible reuse of Quail 0.2 filesystem index databases is not a hard requirement. The filesystem index is derived data and may be rebuilt when necessary.

Do not change the schema or storage format merely to make the architectural split cleaner, and do not introduce migration machinery solely to preserve a disposable derived index.

Preserve user configuration, configured/indexed-volume catalog state, and protected-storage location where applicable. Preserve the existing storage and identity design unless a small change is directly required by the extraction.

If the existing Quail 0.2 index format remains compatible, it should continue working normally. If the simplest correct M15 implementation requires a narrowly justified incompatible schema or format change, a one-time rebuild is acceptable. Quail must detect the incompatible state safely and require or clearly communicate rebuild rather than silently trusting, partially consuming, or corrupting the incompatible index. Complex backward migration is not required.

A simple schema/version incompatibility that safely results in `Rebuild required` is not itself a stop condition.

### Privilege and security invariants

Preserve the existing Quail 0.2 privilege/security boundary, including:

- same-account UAC elevation;
- the narrow elevated worker responsibility;
- protected `%PROGRAMDATA%` index storage;
- current ACL/trust assumptions;
- reparse-point protections and protected handle/path validation;
- per-volume/operation locking;
- SQLite quiescent lifecycle used by elevated mutations;
- safe return to the unelevated application;
- installer privilege model.

Mechanical namespace or assembly changes are expected. Do not introduce a new privileged IPC mechanism, Windows Service, generic elevated agent, broader worker command surface, background-maintenance responsibility, or updater responsibility.

### Dependency and packaging consequences

After extraction:

- `Quail.Core` must not reference `Quail.FileSystem` or `Microsoft.Data.Sqlite` merely to support the filesystem source;
- `Quail.FileSystem` should reference `Quail.Core` for the minimal source/search contracts it implements;
- `Quail.App` may reference both Core and FileSystem only for static composition and explicitly filesystem-specific administration during M15;
- the normal search/coordinator/presentation path must remain Core-facing and source-neutral.

Do not add a new bootstrap assembly, reflection loader, plugin directory, source manifest, or dynamic module-discovery mechanism solely to prove physical optionality now.

Because adding `Quail.FileSystem` changes the production assembly/dependency graph, inspect and update canonical build, publish, installer, payload, and dependency guards as required so the current 0.3 development application still ships the filesystem module and its runtime dependencies. Do not redesign the installer.

### Tests and durable evidence

Adapt or add tests only as needed to prove the new boundary and behavior preservation. A cosmetic mass rename or reorganization of the existing test project is not required.

Provide appropriate automated coverage for:

- Core-level request/result projection and source aggregation;
- Core search with a non-filesystem fake source and no filesystem construction;
- opaque GUI-facing result action routing;
- normal App search no longer depending on native filesystem identifiers or file-specific orchestration names;
- static dependency direction: Core has no concrete-source dependency, FileSystem depends on Core;
- existing search/ranking semantics;
- multi-index/global-limit behavior;
- CLI behavior;
- build/sync/status behavior;
- schema incompatibility/rebuild detection if M15 introduces it;
- existing-index behavior if the format remains unchanged;
- relevant existing security/storage regressions.

Record milestone results in `docs/milestones/M15-results.md` and add focused evidence under `docs/milestones/evidence/M15/` only where durable evidence is useful. The results document must report the actual final dependency graph and must not claim `Core -> FileSystem` as the accepted architecture.

## Explicitly out of scope

Do not introduce or implement:

- a public provider SDK or generalized public `IProvider` framework;
- provider discovery, dynamic plugin/module loading, provider version negotiation, generalized capability or lifecycle frameworks;
- physical optional-source packaging/loading in M15;
- a universal object/source database;
- browser, cloud, mail, calendar, or application providers;
- a final heterogeneous object/metadata model;
- final cross-source ranking or a generic source synchronization framework;
- M16 performance investigation or targets;
- M17 search optimization;
- M18 ranking changes or the known same-tier recall fix;
- M19 maintenance/service architecture work;
- M20 continuous background maintenance;
- Full Search UI or new filters;
- Created-time acquisition or filesystem history;
- browser history/bookmarks;
- service/IPC architecture;
- later startup/settings work;
- unrelated UI polish or refactoring;
- speculative cross-platform abstractions;
- new installer features.

A minimal internal Core-owned search-source contract is not a provider framework; it is the dependency-inversion seam required by the approved architecture. Broader provider contracts should still wait until multiple real source implementations demonstrate common requirements.

## Acceptance criteria

M15 passes only when all of the following are true:

1. `Quail.FileSystem` exists as a separate production module, unless a documented equally narrow alternative was justified.
2. `Quail.Core` no longer owns NTFS/MFT/USN implementation, filesystem SQLite persistence, checkpoint/build/sync internals, native filesystem identity implementation, or filesystem shell-open implementation.
3. `Quail.Core` has no project/code dependency on `Quail.FileSystem` or another concrete source and no filesystem-driven `Microsoft.Data.Sqlite` dependency.
4. `Quail.FileSystem` depends on Core-owned minimal search contracts rather than Core depending on FileSystem.
5. Core search orchestration can be instantiated and exercised with a non-filesystem fake source without creating filesystem objects.
6. Normal App search/coordinator/presentation code uses source-neutral Core contracts and source-neutral names unless a component genuinely handles only filesystem behavior.
7. Normal App-to-Core search does not expose `IndexStore`, `NativeFileId`, filesystem result wrappers, database paths as general result identity, or mandatory file-shaped result semantics.
8. Native NTFS identity remains preserved inside the filesystem source rather than being replaced by path identity.
9. Direct `Quail.App -> Quail.FileSystem` references, if retained, are isolated to static composition and explicitly filesystem-specific administration/UAC paths rather than the normal generic search flow.
10. Quick Search preserves current query semantics, result behavior/order/global limit, keyboard/open behavior, and scheduling/lifecycle behavior.
11. CLI user-visible contracts remain usable.
12. GUI filesystem administration and status remain usable with the existing privilege/protected-storage boundary.
13. If the 0.2 index format remains compatible, existing healthy indexes remain usable. If a narrowly justified incompatible format is introduced, the old format is safely detected as rebuild-required and a rebuild produces a healthy usable index without migration machinery.
14. There are no intentional ranking, query, privilege, installer, or unrelated storage-behavior changes.
15. The complete existing automated test suite passes after necessary adaptation.
16. Release builds for App and CLI pass without new warnings.
17. Canonical build/publish/package verification proves `Quail.FileSystem` and required dependencies are shipped correctly for the current static-composition build.
18. Representative Quail-Lab smoke verifies production App startup, Quick Search, result opening, CLI status/search/open, safe-lab Build/Rebuild/Refresh, a controlled change becoming visible after Refresh, and no regression in unelevated reads of the protected ProgramData index after elevated worker completion.
19. Static architecture review confirms the dependency-inverted Core/source boundary and absence of speculative provider/plugin/capability machinery or dependency cycles.
20. Changed production code remains readable and complies with `AGENTS.md` formatting expectations.

M15 does **not** require a successful runtime test with `Quail.FileSystem.dll` deleted. Physical source optionality is a long-term invariant enabled by this dependency direction, not an M15 loading/packaging feature.

M15 does not require repeating the full M13-D physical-host validation campaign by default. Use the physical host only if Quail-Lab cannot exercise a required boundary, an environment-specific defect appears, or the implementation unexpectedly changes a host-sensitive integration boundary.

## Verification

Verification must include:

- explicit static dependency/boundary inspection and focused code searches;
- a focused fake-source Core test proving source neutrality without runtime plugin machinery;
- the complete automated test suite plus focused new boundary tests;
- Release builds for App and CLI;
- canonical publish/build/installer/payload checks affected by the new production assembly;
- index compatibility verification appropriate to the chosen implementation: either use of an existing 0.2-format index without rebuild, or safe detection of incompatibility followed by a successful rebuild;
- representative Quail-Lab runtime verification as described above;
- final diff/scope/readability inspection.

The final handoff must include exact branch and HEAD, clean worktree status, the resulting compile-time dependency structure, implementation summary, tests/builds/package verification, index-compatibility decision and evidence, Quail-Lab evidence, security-boundary confirmation, limitations/deviations, and the PR link/number.

## Stop conditions

Stop and report instead of materially expanding scope if the extraction requires:

- material redesign of the storage model;
- complex index migration machinery;
- changes to privilege/UAC semantics;
- changes to protected-storage trust/ACL architecture;
- new privileged IPC or a Windows Service/background-maintenance architecture;
- a public/broad provider SDK, discovery system, lifecycle framework, capability framework, or dynamic module loader;
- search-engine or ranking redesign;
- material Quick Search UX changes;
- a new bootstrap architecture merely to make `Quail.FileSystem.dll` physically optional during M15;
- a high-impact security or integrity defect whose proper fix materially exceeds M15;
- conflicting canonical repository requirements or unrelated worktree changes that cannot safely coexist with the milestone.

A minimal Core-owned `ISearchSource`-like seam, dependency inversion, source-neutral renaming of the normal search path, routine compile/project-reference work, focused test adaptation, packaging inclusion of the currently required filesystem assembly, refactor regressions, and a simple safe index-version bump requiring rebuild when genuinely justified are ordinary in-scope implementation work.

After all acceptance criteria pass and the branch plus PR are ready for independent QA, stop. Do not proceed into M16.
