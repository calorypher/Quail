# M16 — Search Performance Investigation & Target

## Status

Approved for implementation.

## Goal

Measure why Quail is slower than Everything in representative daily filesystem-search workflows, establish a small durable benchmark procedure, identify the primary bottlenecks with evidence, and define explicit performance targets and recommended work for M17.

M16 is an investigation milestone. It must not turn into a search-engine optimization or architecture-rewrite milestone.

## Canonical context

Before work starts, read:

- `AGENTS.md`;
- `README.md`;
- `ROADMAP.md`;
- `docs/0.3-direction.md`;
- `docs/verification-playbook.md`;
- this file.

The M15 source-neutral boundary is the current architecture baseline. M16 must preserve it.

## Execution structure

M16 is executed in two bounded phases on the same milestone branch/session where practical:

1. **M16-A — benchmark procedure and harness**
   - inspect existing performance instrumentation and established procedures;
   - define the representative query/scenario set;
   - add only the minimum durable script/instrumentation required to run the benchmark repeatably;
   - perform only small validation runs needed to prove that the harness and scenarios work;
   - stop for independent QA before the full baseline campaign.

2. **M16-B — baseline measurements and conclusions**
   - run the approved benchmark campaign once;
   - perform only narrowly justified follow-up measurements needed to explain an ambiguity;
   - identify measured bottlenecks;
   - define M17 targets and recommended work;
   - establish the small regression set that M17 and M18 should reuse.

M16-A and M16-B are phases of one roadmap milestone, not separate roadmap milestones.

## Scope

Use the developer's physical Windows PC and real representative Quail indexes as the primary performance environment unless a concrete reason requires another environment.

Define a small representative benchmark set, expected to be roughly 8–12 scenarios rather than an exhaustive query matrix. It should cover the relevant classes below where they can be measured reliably:

- ordinary filename query;
- exact or strong-prefix-like daily-use query;
- broad-result query;
- one-character query;
- two-character query;
- warm repeated query;
- fresh-process / cold-start search behavior;
- rapid query changes representative of typing in Quick Search.

Use real queries/corpus characteristics where practical. The benchmark set should be stable enough to reuse in M17 and as a regression guardrail in M18.

Compare Quail with Everything on the same machine and representative corpus where the comparison is semantically meaningful. Everything is a practical UX/performance reference, not a requirement to reproduce its implementation.

Measure end-to-end Quick Search behavior as the primary product metric. Database-only or Core-only timing is supporting evidence, not the final product target.

Reuse existing `SearchPerformanceTrace` and other established instrumentation first. Add instrumentation only when existing evidence cannot distinguish a material bottleneck.

When useful, separate costs such as:

- filesystem search/candidate retrieval;
- ranking;
- Core orchestration;
- App mapping/presentation;
- UI dispatch/rendering;
- shell-icon enrichment.

Do not instrument every theoretical stage. Add measurement only when it can answer a concrete performance question.

Create or refine a small canonical repository script/harness when that materially prevents future Codex sessions from rediscovering the same commands, environment setup, parsing, or workaround. Prefer a one-command repeatable procedure with machine-readable output plus a concise summary.

Record enough environment context to make later comparisons meaningful, without attempting laboratory-grade hardware benchmarking. Relevant context may include Quail commit/build, index/corpus scale, scenario/query identity, session kind, and measurement timestamp.

## Measurement budget

Performance verification has a strict time/model-budget constraint.

During M16-A:

- use single or very small focused runs to develop and validate the harness;
- do not run the full campaign repeatedly while editing scripts;
- do not increase iteration counts merely because automation makes it possible.

During M16-B:

- run the approved baseline campaign once on the final harness;
- use the minimum number of repetitions needed to distinguish normal run-to-run noise from a material difference;
- prefer a small fixed repetition count and robust summaries such as median plus a useful tail measurement when justified;
- do not run dozens or hundreds of repetitions without a concrete noise/intermittency hypothesis.

If initial measurements are too noisy to support a conclusion without a substantial increase in iteration count or experimental complexity, stop and report the limitation/recommendation before spending material additional budget.

After an applicable PASS or usable baseline exists, later M17/M18 work should reuse it. A new Codex session or milestone number is not justification for rediscovering the benchmark procedure or rerunning the full M16 investigation.

M18 should run the established small performance regression set against its final ranking candidate, not repeat M16's investigation campaign.

## Manual vs agent-owned verification

Prefer manual user verification for simple directly observable UX facts such as whether Quick Search visibly feels delayed or whether a normal interaction behaves correctly.

Prefer scripts/automated measurement for timing, repeated samples, trace capture, aggregation, and comparison.

Do not spend Codex budget automating ordinary desktop interactions solely to replace a quick user observation. Do not use WinApp, VMConnect, SendInput, Quail-Lab GUI automation, or a new desktop harness unless the active measurement genuinely requires it.

Do not use Quail-Lab for performance baselining unless a concrete performance question requires the VM. The physical host is the intended environment for the daily-use performance target.

## Deliverables

M16 must leave durable repository evidence, expected to include:

- the canonical benchmark procedure/harness;
- the approved scenario/query set;
- a machine-readable baseline result where practical;
- `docs/milestones/M16-results.md` summarizing environment, procedure, measurements, observed bottlenecks, limitations, M17 targets, and recommended work;
- explicit identification of the small regression subset that M17/M18 should reuse;
- any newly settled environment/procedure facts added to `docs/verification-playbook.md` only when they are general and reusable beyond M16.

Do not copy large raw logs into documentation when a compact result artifact plus summary is sufficient.

## Out of scope

- search-engine optimization or algorithm changes;
- ranking/relevance changes;
- candidate-recall fixes planned for M18;
- storage/schema redesign;
- M15 architecture changes;
- continuous index maintenance;
- Full Search;
- UI polish unrelated to measurement instrumentation;
- installer/deployment changes;
- provider/plugin/runtime-loading work;
- a general benchmarking framework;
- exhaustive query/corpus/cache-state matrices;
- synthetic benchmarking whose only purpose is producing a larger dataset;
- repeated M15 security, package, installer, hotkey, lifecycle, or Quail-Lab campaigns.

A tiny code change that is strictly necessary to expose or collect a required measurement may be allowed, but it must not intentionally improve search performance or alter product semantics.

## Acceptance criteria

M16 is complete when all of the following are true:

1. A repeatable, documented benchmark procedure exists and can be invoked without rediscovering environment-specific steps.
2. A small representative query/scenario set is defined and suitable for reuse.
3. Quail's practical performance gap to Everything is quantified for the representative workflows where comparison is meaningful.
4. End-to-end Quick Search latency is measured, not only isolated database timing.
5. The primary measured bottleneck or bottlenecks are identified with sufficient evidence to guide M17.
6. M17 receives explicit performance targets and a recommended bounded implementation scope.
7. A small performance regression set is identified for final M17 verification and M18 ranking guardrails.
8. Measurement repetitions and follow-up experiments remain proportionate to observed noise and unanswered questions.
9. No intentional search/ranking optimization, architecture redesign, or unrelated product work is introduced.
10. Any material measurement limitation is documented rather than hidden by excessive retries or experimental expansion.

## Verification

### M16-A

Before handoff for independent QA:

- focused automated/script validation sufficient to show the benchmark harness works;
- demonstrate representative output for a small subset of scenarios;
- static review that instrumentation/harness changes do not alter search/ranking semantics;
- required builds/tests only for changed production/test/script boundaries;
- no full baseline campaign.

Independent QA should review scenario quality, measurement validity, repeatability, cost, and whether the harness is likely to be reusable without rediscovery.

### M16-B

After M16-A approval:

- run the approved baseline campaign once;
- run only narrowly justified follow-up measurements for concrete ambiguities;
- summarize results and targets;
- perform focused checks that final documentation/artifacts correspond to the measured commit/environment.

Do not rerun unrelated historical verification. Reuse applicable M15 build/package/security/runtime evidence unless M16 changes those boundaries, which it should normally not do.

## Stop conditions

Stop and return to roadmap/project review instead of expanding scope if:

- measurements indicate the current search/storage architecture is fundamentally incapable of the 0.3 performance goal without a material redesign;
- reliable comparison requires a substantially broader performance lab or benchmarking framework than this milestone authorizes;
- the benchmark is too noisy to support decisions without materially larger experimental cost;
- required Everything comparison cannot be made meaningfully and the missing comparison materially affects the M17 decision;
- a proposed instrumentation change would significantly alter production behavior or architecture;
- investigation reveals a material conflict with the M15 source-neutral architecture.

Do not silently begin M17 implementation from M16.
