# M17-S — Short-Query Search Structure Spike

## Status

**APPROVED feasibility and measurement contract.**

M17-S is a bounded spike inserted after M17 triggered its short-query storage stop condition. It evaluates correctness-preserving structures for one- and two-character search. It does not ship a production implementation.

Canonical inputs:

- `AGENTS.md`
- `README.md`

## Goal

Determine whether a small, correctness-preserving search structure can plausibly meet the approved M17 one- and two-character median latency target of `<= 150 ms` without weakening candidate recall/relevance or imposing disproportionate memory, persistent-storage, startup, build/rebuild, incremental-maintenance, consistency, or long-term maintenance cost.

The milestone must end with evidence sufficient for the Quail 0.3 execution thread to choose a bounded production direction, revise the in-version technical plan, or revise the short-query product/target behavior if no bounded solution is credible.

## Established evidence

Treat these findings as settled inputs rather than rediscovering them:

- the correctness-safe existing short-query path is too slow for the approved M17 target;
- a one-character exact-candidate lookup with no exact match measured about `1.46 s` on the physical C: index;
- existing FTS5 trigram search does not index one- or two-character terms;
- the invalidated M17 candidate achieved approximately `40.9 ms` one-character and `43.4 ms` two-character latency by using a bounded pre-ranking `rowid` candidate window, but that strategy could omit later exact/prefix candidates and is therefore unacceptable;
- permanent M17 regressions for later exact matches (`a` and `ks`) are correctness guards for replacement approaches;
- the approved M17 short-query target remains median `<= 150 ms`, with per-sample guardrail `<= 250 ms`.

Do not treat the invalidated performance campaign as M17 acceptance evidence.

## Candidate classes

Do not assume a specific implementation before measurement. First assess candidate credibility cheaply, then prototype only the most promising bounded approaches.

The minimum classes to consider are:

1. **Persistent auxiliary short-query structure**
   - a compact persistent lookup/index dedicated to correct one- and two-character candidate retrieval;
   - no specific schema, tokenization, or table design is pre-approved.

2. **Memory-resident derived structure**
   - built from the existing persistent filesystem index at startup, load time, or lazily;
   - must account for stabilized RAM and readiness/startup cost.

3. **SQLite-native bounded alternative**
   - another representation or lookup strategy that remains inside the current storage technology where practical;
   - it must preserve full relevant candidate recall and must not be another arbitrary pre-ranking candidate window.

4. **Another equally bounded candidate**
   - may be added only when current measurements or storage semantics provide a concrete reason to evaluate it.

Do not evaluate a broad replacement search engine, unrelated database technologies, or speculative frameworks merely to expand the comparison set.

## Correctness contract

Every viable candidate must preserve:

- literal case-insensitive indexed-name substring semantics;
- complete candidate recall required by the current ranking/relevance behavior;
- current exact/prefix/token-prefix/substring relevance behavior without pre-ranking truncation that can hide a better result;
- deterministic result behavior;
- supported search filters and result-limit semantics;
- correct multi-index behavior where the candidate would affect it;
- the M15 source-neutral Core/FileSystem dependency direction.

The permanent `a` and `ks` later-exact-match regressions must pass for any candidate that reaches detailed evaluation.

A candidate is not viable if its latency gain comes from reducing recall or relevance.

## Latency evaluation

Do not run the full M16 8×3 campaign for every prototype.

For each promising candidate, measure a small representative short-query set containing at least:

- one-character query with an exact match;
- one-character query without an exact match;
- two-character query with an exact match;
- two-character query without an exact match;
- a common/broad one- or two-character substring case with many candidates;
- a regression-shaped case in which a better result occurs later in the indexed data.

Measurements should exercise the real candidate retrieval and ranking path as closely as practical. A microbenchmark of the auxiliary data structure may support diagnosis but is not sufficient feasibility evidence by itself.

A candidate should demonstrate credible margin to the M17 `<= 150 ms` end-to-end product target. A design that only approaches `150 ms` in an isolated structure microbenchmark is not strong evidence of production feasibility.

Use the minimum repeats necessary to distinguish candidate classes. Do not create a high-iteration statistical campaign without a concrete need.

## Footprint evaluation

For each finalist, record enough evidence to compare:

- additional persistent bytes;
- percentage growth relative to the current filesystem database where applicable;
- approximate added bytes per indexed object where meaningful;
- additional stabilized RAM;
- notable temporary/runtime allocation or duplicated-name storage if material.

Do not invent an arbitrary spike-specific MB limit. Interpret the result against Quail's lightweight-operation direction, including the long-term aspiration of roughly `100 MB` idle working set for the complete application.

## Startup and cold-load implications

Measure or estimate startup/cold-readiness impact when the design makes it relevant.

For a memory-resident candidate, measure the cost of constructing or loading the structure and when Quick Search becomes ready.

For a persistent candidate, measure cold-open/load cost only when it is materially different from the existing SQLite index path.

Do not broaden M17-S into general application-startup optimization.

## Build and rebuild cost

M17-S does not optimize the existing full rebuild path, but it must quantify the marginal cost of each finalist sufficiently for the M17 and M17.5 decisions.

For a persistent candidate, measure or credibly estimate:

- time to build the auxiliary structure;
- additional persistent bytes;
- contribution to a representative build/rebuild, or an isolated build cost from which that contribution can be judged.

For a memory-resident candidate, measure:

- structure-construction/load time;
- temporary and final memory demand;
- whether construction would have to repeat after every process start or index change.

Do not attempt to fix the existing minutes-scale rebuild gap in this milestone. M17.5 owns full rebuild investigation after M17 is resolved.

## Incremental maintenance evaluation

M17-S does not implement continuous maintenance, but every finalist must have a credible bounded maintenance path for:

- insert/create;
- rename/update;
- delete;
- rebuild/recovery.

Use a small prototype or focused measurement where necessary to estimate mutation cost. Reject approaches that require a broad new maintenance architecture solely to keep the short-query structure correct.

The evaluation must be useful as an input to later M19/M20 work without designing the Windows Service or continuous-maintenance boundary now.

## Consistency and recovery

For persistent or otherwise durable auxiliary state, determine at least:

- whether the structure is authoritative or derived;
- how it remains transactionally consistent with the existing filesystem index, or how inconsistency would be detected;
- whether it can be rebuilt deterministically from `namespace_entries` or another existing authoritative state;
- how it interacts conceptually with staging build/sync/recovery boundaries;
- whether crash/recovery semantics introduce a new trusted partial state.

Do not redesign Quail's durability, privilege, staging, or service architecture inside M17-S.

## Concurrency

Concurrency is not a required solution for M17-S.

A candidate may use or test bounded parallel build/load work only when its structure naturally permits it and focused measurement shows that the concurrency question materially affects feasibility.

Follow `docs/concurrency-direction.md`:

- no unbounded worker pools or task creation;
- no thread-per-provider/index architecture;
- no assumption that FileSystem owns all logical processors;
- no generic scheduler/resource-governance framework;
- preserve deterministic results, integrity, and interactive responsiveness.

## Spike artifacts

M17-S should leave durable, non-sensitive decision evidence in the repository.

Expected artifacts:

- this contract: `docs/milestones/M17-S.md`;
- results: `docs/milestones/M17-S-results.md`;
- small reusable prototype/benchmark code only where needed for repeatable measurements, clearly separated from production search behavior;
- compact JSON/CSV measurement evidence only when it materially improves reproducibility or reviewability.

Prototype code must not be wired into production Quick Search, production index build/sync, or PR #10.

## Out of scope

- production implementation of the selected short-query structure;
- modifying or continuing PR #10 during the spike;
- removing the production one-second short-query defer;
- M18 ranking/relevance redesign;
- full build/rebuild optimization or M17.5 implementation;
- M19/M20 continuous maintenance or Windows Service implementation;
- generic caching/indexing/provider frameworks;
- broad search/storage engine replacement;
- unrelated concurrency work;
- heterogeneous-source work;
- installer, package, UI, release, or localization work;
- benchmark-specific shortcuts that weaken recall or relevance.

## Acceptance criteria

M17-S is ready for independent QA when:

1. the existing correctness-safe short-query limitation is reproduced or explicitly reused as the baseline;
2. the most credible bounded alternatives have been compared with measured or otherwise concrete evidence rather than architecture preference alone;
3. either:
   - at least one candidate preserves correctness/full candidate recall, has a plausible path to the M17 `<= 150 ms` target, has explicit footprint and startup/load consequences, has quantified build/rebuild contribution, has a credible incremental-maintenance and recovery path, and does not require broad architecture replacement; or
   - the evidence shows that no credible bounded candidate satisfies those conditions;
4. the final results clearly identify:
   - the preferred direction, if one exists;
   - the strongest runner-up;
   - rejected candidates and the reasons for rejection;
   - the expected M17 contract amendment or in-version decision consequence;
5. no candidate is shipped as production behavior.

## Verification

Follow `docs/verification-playbook.md` and optimize verification for the decision, not for historical coverage.

Expected verification:

- focused correctness tests, including the permanent one- and two-character regressions;
- deterministic prototype/search benchmarks;
- representative physical-host measurements when corpus scale is necessary to judge feasibility;
- storage/RAM/build/load/mutation measurements appropriate to each finalist;
- build/test only for changed prototype or test projects as needed;
- `git diff --check` before handoff.

Do not run manual UI smoke, installer/package verification, Quail-Lab campaigns, or the full M16 8×3 campaign unless a specific candidate cannot be judged without that evidence.

Reuse valid M16/M17 evidence for unchanged boundaries rather than recreating it.

## Stop conditions

Stop evaluating an individual candidate when evidence shows any of the following:

- correctness requires candidate truncation or weakened relevance/recall;
- representative latency remains materially outside the M17 budget with no bounded credible path to improvement;
- storage or RAM footprint is clearly disproportionate to the benefit;
- startup/load cost undermines the intended immediate-search experience;
- incremental maintenance requires a broad new architecture;
- consistency/recovery would require changing Quail's durability or privilege model merely to support the candidate;
- the candidate requires work outside the approved Quail 0.3 release boundary.

Rejecting one candidate does not stop the entire spike. Continue to the remaining credible bounded options while the acceptance question remains unanswered.

If all credible bounded options fail, stop the spike with that evidence rather than forcing an implementation.

## Completion boundary

The implementation-agent boundary is:

- a dedicated clean M17-S branch;
- committed and pushed spike artifacts and measurement evidence;
- a separate PR ready for independent QA;
- a clear technical recommendation or explicit conclusion that no bounded candidate is credible.

Do not merge the M17-S PR, modify/merge PR #10, delete branches, force-push, tag, publish a release, begin production short-query implementation, or begin M17.5 without the next approved workflow step.

After independent QA, the Quail 0.3 execution thread owns the in-version decision. It may amend M17 and resume PR #10, choose another bounded implementation path, revise the in-version target/product behavior, or adapt the milestone plan while the approved 0.3 release goal and boundary remain intact.
