# M17.5 — Index Build/Rebuild Performance Investigation & Target

## Status

**COMPLETE — independent QA passed; PR #15 merged to `main` as `1439c3e67e206a5f1e4279073802a7696786ea11`.**

M17.5 established a current-host physical baseline for a production-like `C:\`
rebuild, attributed wall time to practical phases, and ran one diagnostic-only
experiment selected from that baseline. It does not ship a production optimization.

## Method and validity

The valid campaign ran one warm-up and three measured `C:\` rebuilds at
`9f502b24a432c3a257f5aea67ee0db409f6453bf`, with a clean source tree, .NET
SDK 10.0.400, Windows 10.0.26200.0, a dedicated generated database under
`%PROGRAMDATA%\Quail\Benchmarks\M17.5`, `IndexStore.Build`,
`DeleteWhenQuiescent`, `synchronous=FULL`, WAL checkpoint/finalization,
staging publication, full metadata acquisition, FTS, and `compact-short-query-v3`.
It never opened or replaced either configured production index.

Every final database reported `Complete` and passed `EnsureSearchReady`. The
compact evidence omits host volume identity, label, paths, usernames, and file names.

The first campaign at `artifacts/m17.5/physical-20260905/` is invalidated but
retained. Callback-duration ticks were mistakenly passed as a stopwatch start
timestamp, producing a negative MFT phase. Commit `9f502b2` corrected the
conversion and added a regression test. The retry campaign is the only baseline.

`mftEnumerationReadParse` is `FSCTL_ENUM_USN_DATA` read/parse minus synchronous
sink time, excluding metadata and row writes. `metadataAcquisition`,
`namespaceAndFtsWrites`, and `bulkTransactionCommits` cover initial
enumeration/root insertion; any catch-up work is inside `journalHandoff`.
`checkpointFinalization` includes final checkpoint metadata, WAL checkpoint,
and delete-journal transition. `residual` is outer Build/control overhead.

## Bounded diagnostic-only experiment

The baseline selected one experiment: retain real `C:\` enumeration, full
metadata, short-query build, `synchronous=FULL`, WAL, checkpoint, and staging,
but omit FTS schema/triggers. The database is deliberately `RebuildRequired`
and not search-ready or production-comparable.

| Mode | Records | DB bytes | Wall s | Namespace write phase s | DB status |
|---|---:|---:|---:|---:|---|
| Canonical median | 479,305 | 243,634,176 | 82.161 | 36.738 | Complete/search-ready |
| Diagnostic no-FTS (one run) | 479,329 | 192,204,800 | 51.876 | 11.550 | RebuildRequired/not search-ready |

The diagnostic was 30.285 s (36.86%) faster and its row-write phase was
25.189 s (68.56%) lower. Its corpus changed slightly and it is one sample, so
the total delta is not a production saving claim. It is direct evidence that
per-row FTS trigger maintenance is the first production hypothesis to test.
The smaller diagnostic DB is not a production footprint comparison.

No metadata worker-pool or transaction-size experiment was run: neither is
needed to establish the highest-value next hypothesis, and adding them would
not change the decision.

## Bottlenecks and opportunities

| Rank | Opportunity | Evidence-based potential | Risk and cost |
|---:|---|---|---|
| 1 | Bulk-build existing FTS after authoritative namespace insertion | Highest. Diagnostic removes 25.189 s from write phase; production must pay a final FTS build, so net gain requires measurement. | Medium implementation/integrity risk; preserve schema, semantics, staging, recovery, and complete FTS before publication. |
| 2 | Bounded metadata pipeline (1/2/4/8) with one writer | Medium but unquantified: metadata is 23.554 s (28.67%). | Medium complexity/resource risk; writer serialization and handle contention may erase gain. |
| 3 | Re-evaluate fixed 2,048-row transaction size | Low-to-medium: commits are 7.484 s (9.11%). | Low code complexity; retain `synchronous=FULL` and failure semantics. |
| 4 | Narrowly optimize rooted namespace normalization | Low-to-medium: 5.105 s (6.21%). | Medium correctness risk around root/path invariants. |
| 5 | Profile compact short-query construction substage | Low: 8.186 s (9.96%). | Medium correctness/maintenance risk; do not redesign it before FTS work. |

MFT read/parse, journal handoff, checkpoint/finalization, and staging promotion
are not credible first targets.

## Target and execution decision

**Evidence-based production target range: 60–70 seconds median** on this
current-host corpus with complete production lifecycle and derived state. That
is a 15–27% reduction from 82.161 s. The 51.876 s no-FTS measurement is
diagnostic lower-bound context, not a valid target, because production must
construct and validate FTS.

**Decision A — add a bounded production optimization milestone before M18/M19.**

Working milestone: **M17.6 — FTS Bulk-Build Optimization**. Scope: replace the
measured per-row FTS cost with correctness-preserving bulk construction of the
same final FTS schema/state; add focused lifecycle/integrity tests; run one
final production-like campaign. Do not weaken durability or staging, change
search/ranking, introduce concurrent SQLite writers, create a generic scheduler,
or absorb M19/M20. A metadata pipeline is follow-up only if this cannot reach target.
