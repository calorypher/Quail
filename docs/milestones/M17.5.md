# M17.5 — Index Build/Rebuild Performance Investigation & Target

## Status

**ACTIVE — investigation contract approved on 2026-09-04.**

M17.5 is a bounded measurement and decision milestone. It does not implement the production rebuild optimization itself. Its purpose is to explain the current full-build/rebuild cost on the actual post-M17 filesystem index shape, derive an evidence-based target/range, and decide whether Quail 0.3 needs a separate bounded production optimization milestone before M18/M19.

## Goal

Determine why a full Quail filesystem index build/rebuild takes on the order of minutes at the relevant corpus scale, quantify the dominant costs on the actual post-M17 storage/search design, and end with an explicit Quail 0.3 decision:

1. add a separate bounded production build/rebuild optimization milestone before M18/M19; or
2. defer production rebuild optimization and continue to M18 with an explicit evidence-based rationale.

Everything remains a practical reference point, not a parity target. The historical comparison is approximately three minutes for an older Quail corpus of roughly 0.86 million records versus roughly 2.6–2.7 seconds observed in a 30 FPS Everything recording for roughly 0.93 million indexed objects. The datasets, metadata, durability model, storage format, and architecture are not equivalent.

## Current corpus and comparison policy

The pre-reinstall physical C: corpus used during M16/M17 is no longer the current host corpus. The accepted final M17 evidence records the current production C: index at 462,868 namespace rows, while the preserved comparable pre-reinstall C: corpus contains 850,675 rooted rows after normalization.

Therefore:

- establish a new canonical physical-host M17.5 baseline against the current real `C:\` NTFS corpus;
- do not represent the current C: corpus as directly identical to the older M16/M17 corpus;
- retain the historical roughly-three-minute Quail result and Everything video observation as scale/context only;
- the preserved/frozen pre-reinstall DB may be used for bounded replay or microbenchmark diagnostics where appropriate, but it does not substitute for real MFT enumeration and metadata acquisition on live NTFS;
- do not rerun frozen evidence merely to reproduce already-settled M17 results.

## Scope

### 1. Canonical physical full-build/rebuild benchmark

Create the smallest durable benchmark harness needed to perform a production-like full build/rebuild on the current physical C: volume without modifying the configured production index.

The canonical benchmark should:

- run from an elevated PowerShell/process because real NTFS enumeration and protected-style host access require it;
- index the real current `C:\` volume;
- write only to a dedicated generated benchmark database, preferably under a clearly isolated location such as `%PROGRAMDATA%\Quail\Benchmarks\M17.5\`;
- never point at or replace the configured production C: or D: index;
- use the real `IndexStore` production build path and `IndexStoreJournalLifecycle.DeleteWhenQuiescent` or an exactly equivalent production-like durability/staging path;
- preserve `synchronous=FULL`, the existing staging publication model, WAL/checkpoint behavior, authoritative namespace behavior, and accepted `compact-short-query-v3` build path;
- perform one warm-up rebuild followed by three measured rebuilds against the same benchmark destination;
- preserve raw measurement evidence under `artifacts/m17.5/<run>/` or an equivalently clear milestone-owned location;
- leave the generated benchmark DB in place at handoff unless the user explicitly authorizes deletion. Do not add automatic destructive cleanup outside the repository.

The benchmark output must record enough environment state to make the result interpretable, including at least:

- captured UTC time;
- exact Git HEAD;
- source dirty/clean status;
- .NET version;
- Windows version;
- physical volume/mount identity in non-sensitive form;
- measured run number and warm-up/measured classification;
- actual indexed record count;
- final database bytes;
- end-to-end elapsed time;
- process CPU time;
- peak working set;
- metadata-acquisition attempts/successes/failures/failure-code summary;
- phase timings described below.

Do not store usernames, user-profile paths, query text, or other unnecessary sensitive host data in committed compact evidence.

### 2. Phase attribution

Instrument the existing build path narrowly enough to attribute the practical majority of wall-clock time. The phase model should avoid double-counting or clearly document inclusive/exclusive timing when strict disjoint timing is not practical.

At minimum distinguish or account for:

1. **setup/schema** — staging DB creation/open, journal mode/synchronous setup, schema and initial metadata;
2. **MFT enumeration/read/parse** — `FSCTL_ENUM_USN_DATA` and record parsing, excluding downstream sink work where technically practical;
3. **metadata acquisition** — per-record `OpenFileById` / `GetFileInformationByHandleEx` work;
4. **namespace + FTS writes** — base-row upserts including the current FTS trigger work attributable to those writes;
5. **bulk transaction commits** — current periodic commits during initial row insertion where separable;
6. **journal handoff** — post-enumeration journal query/read/apply work needed to publish a current index;
7. **namespace normalization** — `RemoveUnrootedNamespaceEntries`;
8. **short-query build** — full accepted `compact-short-query-v3` construction;
9. **checkpoint/finalization** — WAL checkpoint and journal-mode finalization;
10. **promotion/publication** — staging replacement/move of the generated benchmark database;
11. **residual/unattributed** — wall-clock time not otherwise accounted for.

The investigation must not infer a stage cost from the current aggregate `BuildMetrics` if that metric includes callback/sink execution. Instrument the actual boundaries needed to distinguish MFT enumeration from downstream metadata/SQLite work.

The major measured phases should account for the practical majority of end-to-end elapsed time. Any substantial residual must be investigated or explicitly explained.

### 3. Storage and resource baseline

For the canonical current-C physical corpus record:

- final rooted namespace/object count;
- final DB bytes;
- approximate bytes per indexed object;
- process CPU time and CPU/wall ratio;
- peak working set;
- stabilized memory after build only if it is inexpensive and meaningful to measure;
- accepted short-query structure contribution where measurable with the available runtime;
- FTS/base/derived storage breakdown where the bundled SQLite/runtime exposes reliable data;
- null/unavailable storage submetrics must remain null rather than being replaced with invented estimates.

Retain the final M17 footprint/build evidence as prior context. In particular, the preserved ~850k-row disposable final-v3 direct compact construction took about 14.7 seconds. M17.5 must measure the short-query build contribution inside the actual current physical full-build path rather than treating that historical microbenchmark as the new whole-build baseline.

### 4. Bottleneck identification

Use the phase data to determine which current mechanisms dominate. Candidate hypotheses include, but are not limited to:

- per-record metadata acquisition;
- serial MFT/enumeration or parsing;
- SQLite base-row writes;
- per-row FTS trigger maintenance;
- transaction sizing/commit overhead;
- short-query construction;
- journal handoff;
- WAL checkpoint/finalization;
- staging publication;
- CPU underutilization caused by a serial stage;
- I/O saturation or contention.

Do not pre-select a culprit before the phase evidence exists.

### 5. Bounded diagnostic experiments

After the canonical baseline exists, perform only the smallest experiments needed to rank realistic optimization opportunities. The investigation may add bounded diagnostic-only seams or disposable helper modes; they must not become production behavior merely because they benchmark faster.

Examples, conditional on measured evidence:

- if metadata acquisition dominates, measure bounded acquisition scaling such as 1/2/4/8 workers without changing the authoritative writer semantics;
- if SQLite/FTS writes dominate, compare the current path with one or two bounded bulk-build hypotheses on disposable benchmark data, while preserving final correctness and without silently changing production schema/durability;
- if transaction commits dominate, test a bounded transaction-sizing hypothesis while retaining `synchronous=FULL` and the accepted durability model;
- if short-query construction is material, subdivide its cost enough to identify the dominant substage;
- if one serial stage dominates, measure a reader/worker/writer pipeline only if that experiment directly tests the observed bottleneck.

Concurrency experiments must follow `docs/concurrency-direction.md`:

- worker counts and queue depths must be bounded;
- no assumption that all logical processors should be used;
- no concurrent SQLite writers merely for theoretical parallelism;
- measure wall time and CPU utilization/scaling rather than treating high CPU percentage as success;
- preserve deterministic correctness and integrity.

Do not create a generic scheduler, worker framework, provider resource manager, or permanent parallel indexing architecture during M17.5.

## Out of scope

- implementing the final production build/rebuild optimization before the M17.5 decision is recorded;
- changing interactive Search implementation or ranking semantics;
- rerunning the final M16/M17 8x3 search campaign for an unchanged search path;
- weakening `synchronous=FULL`, staging publication, protected-storage assumptions, index integrity, or crash/recovery semantics to obtain benchmark wins;
- changing schema/storage architecture beyond small diagnostic-only experiments needed to measure a concrete hypothesis;
- introducing multiple concurrent writers to one SQLite DB without direct measured justification;
- continuous-maintenance / Windows Service architecture (M19/M20);
- generic scheduler/resource-governance infrastructure;
- installer/package/release work;
- refactoring `LatestSearchCoordinator` or the post-0.3 replaceable-frontend boundary;
- broad cleanup or unrelated modernization.

## Acceptance criteria

M17.5 is ready for independent QA when all of the following are true:

- a repeatable canonical current-host C: full-build/rebuild harness exists;
- one warm-up plus three measured production-like rebuilds complete successfully on the physical host, or a concrete environment blocker is recorded before claiming acceptance;
- all measured runs identify the exact HEAD/environment and use a dedicated non-production benchmark DB;
- the phase breakdown explains the practical majority of end-to-end elapsed time, with residual explicitly quantified;
- dominant bottlenecks are identified from measurements rather than inferred from total runtime;
- storage/object-count/bytes-per-object plus CPU/wall/peak-memory baseline are recorded;
- the accepted M17 short-query structure's full-build contribution is explicitly measured;
- any bounded diagnostic experiment is tied to a measured bottleneck and records enough evidence to judge likely production benefit;
- realistic optimization opportunities are ranked by expected wall-clock gain, implementation risk, integrity/durability risk, complexity, and maintenance cost;
- an evidence-based target or target range for a possible production optimization is recorded;
- the milestone ends with one explicit Quail 0.3 execution decision: add a bounded production optimization milestone before M18/M19, or continue to M18 with rebuild optimization deferred;
- no production optimization is silently shipped as part of the investigation;
- no search/ranking, M19/M20 service, generic scheduler, or cross-version architecture scope is absorbed.

## Verification

Follow `docs/verification-playbook.md` and use the smallest verification set that protects the changed measurement boundaries.

Expected verification shape:

- focused automated tests for new timing/metrics aggregation and any deterministic diagnostic seams;
- Release build of affected projects and the new benchmark/helper path;
- one canonical physical campaign: one warm-up plus three measured rebuilds;
- JSON parse/schema checks and independent recomputation/cross-check of phase sums, total elapsed, record counts, DB bytes, and summary values;
- focused integrity/status check on the generated benchmark DB after the final measured run;
- `git diff --check` before handoff;
- no M16/M17 interactive-search performance rerun unless M17.5 unexpectedly changes Search production code, in which case stop and explain why the milestone boundary was crossed before deciding how to verify it.

Do not run repeated physical campaigns after the canonical three measured runs merely for confidence. If an infrastructure-only failure occurs, diagnose it once, make one obvious bounded correction, and rerun only the affected attempt/campaign as allowed by the verification playbook. Preserve failed evidence rather than overwriting it.

## Implementation method

Use a new milestone branch from current `main`, expected to be `codex/m17-5-index-build-performance` unless repository state requires another clear name.

Work in this order:

1. verify branch/HEAD/worktree/remotes and read all canonical inputs;
2. inspect the actual current build path and existing metrics before designing instrumentation;
3. add the minimum deterministic phase instrumentation and canonical harness;
4. prove instrumentation correctness with focused tests/builds before running the expensive physical campaign;
5. run one warm-up and three measured current-C rebuilds to the dedicated benchmark DB;
6. analyze the baseline and identify the dominant stage(s);
7. run only bounded diagnostics that answer the highest-value measured hypotheses;
8. derive an evidence-based optimization target/range and rank opportunities;
9. record the explicit in-version decision;
10. commit/push and prepare a PR ready for independent QA.

Do not begin implementing the recommended production optimization in the same milestone. The Quail 0.3 execution thread will create/reorder the next production milestone if the evidence selects that path.

## Stop conditions

Stop and report evidence instead of expanding M17.5 if any of the following becomes necessary:

- touching or replacing the configured production C:/D: index for benchmark execution;
- destructive cleanup outside the repository without explicit user approval;
- weakening durability, staging, integrity, or protected-storage guarantees merely to improve timings;
- changing interactive search or ranking behavior;
- broad schema/storage redesign rather than bounded measurement;
- a generic scheduler/resource-governance framework;
- continuous-maintenance/service architecture;
- substantial production optimization before the investigation decision;
- a benchmark or instrumentation design whose overhead materially distorts the stage being measured and cannot be corrected narrowly;
- an environment limitation that prevents representative physical MFT/metadata measurement after the verification playbook's bounded retry budget;
- evidence requiring a major cross-version architecture/product/methodology decision or a change to the Quail 0.3 release boundary.

If evidence recommends a production optimization that remains inside the approved 0.3 boundary, record that recommendation and stop at the M17.5 completion boundary. The Quail 0.3 execution thread may then add/split/reorder a bounded implementation milestone without returning to the parent roadmap thread.

## Completion boundary

M17.5 ends at a verified branch + PR with accepted investigation evidence and an explicit Quail 0.3 execution decision. It does not end with production rebuild optimization, merge, branch deletion, tag, or release.

Merge still requires explicit user approval after independent QA.
