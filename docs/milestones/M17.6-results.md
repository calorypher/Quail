# M17.6 Results — FTS Bulk-Build Optimization

## Status

**READY FOR INDEPENDENT QA — TARGET PASS; merge pending.**

M17.6 implemented the bounded M17.5 Decision A: full Build/Rebuild no longer
maintains FTS row by row while ingesting the namespace. The final published
index retains the existing `fts5-trigram-v1` table, tokenizer, query semantics,
and production incremental-maintenance triggers. No Search, ranking, metadata,
transaction-size, normalization, short-query, or concurrency change was made.

## Production implementation

At implementation commit `be76a2cfe990140727a678d61db930761cac0c76`, the
staged build creates the authoritative namespace and external-content FTS5
table without FTS maintenance triggers. Enumeration and journal handoff mutate
only `namespace_entries` during that interval.

The final ordering is deliberate:

1. complete namespace insertion and journal handoff;
2. run `RemoveUnrootedNamespaceEntries`, so the authoritative namespace is
   final and rooted;
3. issue SQLite FTS5's `rebuild` command to populate `search_entries` from
   that final namespace;
4. create the existing insert, delete, and update triggers used by Sync;
5. verify trigger presence, exact `namespace_entries`/FTS docsize row-count
   coverage, and FTS5 `integrity-check` before building the compact short-query
   structure and marking staging `complete`.

This makes journal-handoff changes part of the bulk input rather than a later
delta. The only mutation path after trigger creation is normal published Sync.
The full integrity command requires writable SQLite access; the build validates
it before promotion. Read-only callers retain structural trigger/count
validation, preserving protected-storage read behavior.

The new direct FTS path is visible separately: 11.570 seconds authoritative
namespace writes plus 8.928 seconds bulk FTS construction, versus 36.738
seconds for M17.5's per-row namespace-plus-trigger phase. The corpus changed
only slightly (479,305 to 479,481 median rooted records); metadata and commit
time also improved, but the measured FTS-path reduction is the direct evidence
for this milestone's hypothesis.

DB median grew by 839,680 bytes (0.34%); median peak working set fell by
3,887,104 bytes (3.7 MiB). CPU and wall both declined by about 20.7 seconds,
while CPU/wall remained approximately 0.959. SQLite storage sub-breakdowns
remain unavailable and are intentionally null in the compact baseline.
