# M17.6 — FTS Bulk-Build Optimization

## Status

**ACTIVE — production optimization contract approved after M17.5 Decision A.**

M17.6 is a bounded production optimization milestone. It owns only the highest-value hypothesis selected by M17.5: replace per-row FTS trigger maintenance during full build/rebuild with a correctness-preserving bulk construction of the same final FTS state.

## Goal

Reduce production-like full filesystem rebuild time on the current physical `C:\` corpus from the M17.5 median of 82.161 s into an evidence-based target range of **60–70 s median**, while preserving the final production schema, FTS search semantics, metadata, durability, staging/publication, compact short-query state, journal handoff, integrity, and lifecycle behavior.

The target is not Everything parity. The M17.5 no-FTS diagnostic at 51.876 s is a lower-bound diagnostic only, because that database was intentionally `RebuildRequired` and not search-ready.

## Evidence basis

M17.5 canonical median on the current physical C: corpus:

- rooted records: 479,305;
- DB bytes: 243,634,176;
- wall: 82.161 s;
- CPU: 78.766 s;
- CPU/wall: 0.959;
- peak working set: 605.1 MiB.

Median phase costs:

- namespace + FTS writes: 36.738 s (44.72%);
- metadata acquisition: 23.554 s (28.67%);
- short-query build: 8.186 s (9.96%);
- bulk transaction commits: 7.484 s (9.11%);
- namespace normalization: 5.105 s (6.21%).

The bounded diagnostic that omitted FTS schema/triggers reduced the namespace-write phase to 11.550 s and total wall time to 51.876 s. This does not establish a production saving, but it identifies per-row FTS maintenance as the first production hypothesis to test.

## Scope

### 1. Bulk-build the existing FTS state

Change only the full Build/Rebuild path so authoritative `namespace_entries` insertion does not pay the current per-row FTS trigger maintenance cost.

The preferred shape is:

1. create/populate authoritative namespace state without incremental FTS trigger work;
2. complete required namespace normalization before publication;
3. construct the same final `search_entries` FTS5 state in a bounded bulk step;
4. establish the same production trigger/schema state required for subsequent incremental sync;
5. validate that the resulting index is fully search-ready before staging publication.

An equivalent smaller implementation is allowed if measurements and SQLite behavior justify it.

Do not change the logical FTS schema/tokenizer/search semantics unless evidence proves the current schema cannot be bulk-built correctly; if that becomes necessary, stop rather than silently broadening the milestone.

### 2. Preserve normal incremental maintenance

After a successful Build/Rebuild, ordinary explicit incremental `Sync` behavior must continue to maintain FTS correctly through the accepted production path.

M17.6 does not optimize sync throughput unless a narrowly required compatibility change is unavoidable for the bulk-build implementation.

### 3. Preserve other build phases

Keep unchanged unless a direct compatibility requirement exists:

- MFT enumeration;
- metadata acquisition;
- current transaction sizing;
- `compact-short-query-v3` construction;
- rooted namespace normalization;
- journal handoff;
- `synchronous=FULL`;
- WAL/checkpoint behavior;
- staging publication;
- protected storage assumptions.

Do not combine this milestone with metadata-worker, transaction-size, normalization, short-query, or general concurrency optimization.

## Performance target

Canonical acceptance target on the same current-host methodology used by M17.5:

- production-like median full rebuild: **60–70 s**;
- all measured final DBs must be `Complete` and search-ready;
- no sample may achieve the target by omitting required production state or weakening durability/integrity.

The target is a range, not a requirement to optimize toward exactly 60 s. If a clean, low-risk implementation lands below 60 s while preserving all semantics, that is acceptable. Do not add complexity merely to chase a lower number after acceptance is met.

If the smallest correct FTS bulk-build implementation cannot reach 70 s median, analyze the result before broadening scope. A miss does not automatically authorize metadata concurrency or another optimization.

## Correctness and integrity requirements

The final Build/Rebuild output must preserve:

- the exact production FTS5 schema and trigram case-insensitive filename search behavior expected by current Search;
- complete FTS coverage for all authoritative rooted namespace rows that should be searchable;
- no stale or extra FTS rows;
- current schema/version metadata and search-ready validation;
- `compact-short-query-v3` generation/state;
- deterministic namespace state and rooted-parent invariants;
- journal checkpoint continuity;
- current incremental create/update/rename/delete FTS maintenance after publication;
- crash/failure behavior: an incomplete bulk-build must never publish as a trusted complete searchable index.

Add focused regression coverage for at least:

- bulk-built FTS search equivalence on deterministic fixtures;
- exact row/FTS coverage or equivalent integrity check;
- build followed by incremental create/rename/delete/update behavior;
- failure before FTS completion leaves no trusted published index;
- rebuild over an existing benchmark/test index preserves staging replacement semantics;
- current search readiness checks accept the final valid index and reject deliberately incomplete FTS state.

## Verification method

Follow `docs/verification-playbook.md`.

During implementation:

1. use deterministic fixtures/tests first;
2. use the existing M17.5 phase instrumentation/harness for focused physical measurement;
3. iterate only on the FTS bulk-build path;
4. run one final production-like physical campaign only after correctness is green.

Do not rerun the M16/M17 interactive-search 8x3 campaign unless production Search/ranking code unexpectedly changes. If such a change appears necessary, stop because the milestone boundary has been crossed.

## Canonical physical campaign

Final campaign:

- full metadata;

## Acceptance criteria

M17.6 is ready for independent QA when:

- full Build/Rebuild no longer maintains FTS through the expensive per-row path, or an equivalent measured implementation removes the same bottleneck;
- the final published DB contains complete valid production FTS state;
- Search semantics/schema remain unchanged;
- incremental sync maintains FTS correctly after the bulk-built index is published;
- focused correctness, lifecycle, staging/failure and FTS integrity tests pass;
- affected Release builds pass;
- final physical campaign is one warm-up + three measured runs;
- median production-like rebuild is within 60–70 s, or a justified stop decision is recorded if the smallest correct implementation misses the target;
- phase evidence demonstrates where the recovered time came from;
- no durability/integrity/search/ranking guarantees are weakened;
- no metadata pipeline, generic scheduler, concurrent SQLite writer architecture, M18 ranking work, or M19/M20 service work is absorbed.

## Stop conditions

Stop and return evidence instead of expanding scope if:

- correct bulk construction requires changing FTS search semantics or schema materially;
- the final FTS state cannot be proven equivalent/complete with a bounded implementation;
- meeting the target appears to require metadata concurrency, transaction redesign, broad pipeline architecture, or another independent optimization;
- durability/staging/integrity would need to be weakened;
- production Search/ranking must change;
- benchmark work would touch configured production indexes;
- an unrelated repo conflict/change appears;
- physical evidence remains invalid after the verification playbook's bounded retry allowance;
- evidence implies a release-boundary or major cross-version decision.

A target miss that remains inside the 0.3 boundary returns to the Quail 0.3 execution thread for the next bounded decision; it does not authorize scope expansion automatically.
