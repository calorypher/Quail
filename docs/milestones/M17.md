## Goal

Make representative filesystem Quick Search effectively immediate by fixing the measured M16 short-query, broad-result, and relevant queue/Core hot paths while preserving correctness, ranking/relevance semantics, deterministic ordering, the M15 source-neutral boundary, and the established M16 benchmark methodology.

## Evidence and amendment decision

M16 established these physical-host medians:

- `ordinary-name`: 28.047 ms
- `strong-prefix`: 26.581 ms
- `broad-result`: 281.509 ms
- `one-character`: 3,006.749 ms
- `two-character`: 2,008.437 ms
- `warm-repeated`: 112.191 ms
- `fresh-process-first-search`: 90.089 ms
- `rapid-typing` final input: 57.456 ms
- `rapid-typing` prescribed burst: 529.727 ms

The existing one/two-character UI path deliberately includes a one-second defer introduced as a temporary mitigation for the expensive underlying search path. It is not target UX. M17 should remove the need for that workaround by making the underlying path fast enough.

The first M17 performance candidate met every timing target but was invalidated because a bounded `rowid` window could exclude later better candidates before ranking. That strategy remains prohibited. Permanent regression guards cover the discovered one- and two-character late-exact cases.

On the correctness-safe pre-M17 storage model, a full one-character candidate lookup with no exact match measured about 1.46 seconds. Existing FTS5 trigram search does not index one- or two-character terms. This triggered M17-S.

M17-S outcome A established a credible bounded direction on the physical C: corpus:

- 851,841 indexed entries;
- 35,093,907 distinct one/two-character postings;
- sparse-label compact SQLite representation: 84,164,608 additional bytes, about 31.0% of the 271,421,440-byte source DB and 2.398 bytes/posting;
- compact rank-map load: about 4.26 MB and 14.2 ms;
- focused complete-retrieval/ranking paths: approximately 5–21 ms, including a broad one-character shape;
- full candidate recall and late-exact guards passed;
- whole-list BLOB mutation was rejected because representative deletes implied about 9.9 MB P50 and 25.7 MB P95 payload rewrites.

The approved one/two-character target therefore remains unchanged. M17 is explicitly amended to authorize a filesystem-owned derived compact short-query structure within the existing SQLite/staging lifecycle.

## Scope

M17 may change only the measured interactive-search path and the smallest adjacent storage/build/sync behavior required by the approved compact short-query structure.

### 1. One- and two-character search

Implement a production compact structure for literal case-insensitive one- and two-character indexed-name substring search.

The approved direction is:

- `namespace_entries` remains authoritative;
- the derived structure belongs to `Quail.FileSystem` and remains an internal filesystem-source implementation detail;
- store the derived state in the existing SQLite index/staging lifecycle rather than introducing a custom durable store;
- use compact posting streams for `(term, text class)` or an equivalent bounded representation;
- use sparse insertion-stable static-rank labels and chunked delta-varint posting payloads, or a directly equivalent implementation that preserves the M17-S measured properties;
- include a source-generation/version marker so mismatched derived state is never silently trusted;
- preserve full candidate recall before the existing ranking semantics are applied;
- remove the large fixed one-second defer once the production path is fast enough.

Production guardrails:

- do not use an arbitrary `rowid`, posting-count, or per-class candidate cutoff;
- do not encode lexicographic rank precedence using magic numeric multipliers or assumed corpus-size ranges; compare `(location, text class, static rank)` or equivalent keys explicitly;
- rank labels must have safe headroom for realistic index growth; use a 64-bit or equivalently overflow-safe representation rather than depending on the spike's small `int` range;
- persisted derived ordering must not become incorrect if build/sync later runs under a different process identity. User-dependent ranking semantics such as current-user location must remain correct for the searching user; persist context-independent rank inputs or explicitly validate/key any user-dependent state rather than baking an arbitrary build identity into authoritative order;
- whole-list BLOB replacement for ordinary create/rename/delete maintenance is prohibited; updates must be bounded to affected chunks plus bounded metadata/relabel work;
- an exhausted sparse-label gap may use bounded local relabeling or a clear rebuild/recovery path, but not an unbounded global rewrite in the ordinary mutation path.

### 2. Build, sync, consistency, and recovery required by the short-query structure

M17 now explicitly owns the minimum production lifecycle work needed to keep the compact structure correct:

- build the derived structure as part of staged index construction before publication;
- keep create/update/rename/delete changes consistent with `namespace_entries` through the existing SQLite transaction model;
- update only affected term/class chunks and required rank-label metadata during incremental sync;
- detect a missing, stale, malformed, or generation-mismatched compact structure and never return results from it as if it were valid;
- allow deterministic rebuild from authoritative `namespace_entries`;
- preserve existing durability, protected-storage, staging, and publication semantics.

A broad migration framework is not required. If pre-M17 development indexes cannot safely acquire the derived structure in place with a small bounded change, an explicit rebuild-required transition is acceptable provided it is safe and clearly represented by the existing index lifecycle rather than silently producing incomplete search.

M17 must measure the marginal production footprint, compact-state load/open cost where material, and the direct build contribution of the chosen implementation. It does not optimize the overall minutes-scale rebuild; M17.5 remains the owner of that investigation and any later production rebuild optimization.

### 3. Broad-result search

Reduce the measured `broad-result` latency, focusing on measured Core candidate retrieval/search cost and queue wait.

Do not optimize mapping, result apply, source-status, icon work, or another stage unless current profiling shows it has become material after an in-scope change.

### 4. Warm-repeated scheduling

Improve queue/scheduling behavior affecting `warm-repeated` only as far as required by the target and regression guardrails.

Do not introduce a generic scheduler framework.

### 5. Multi-index concurrency as a measured hypothesis

The filesystem source currently searches configured indexes sequentially. M17 may evaluate bounded concurrent search of independent indexes if focused measurement shows a real latency benefit.

Concurrency must follow `docs/concurrency-direction.md`:

- no thread-per-index/provider requirement;
- no unbounded task creation;
- no assumption that FileSystem owns all logical processors;
- preserve deterministic merged ordering and correctness;
- avoid speculative shared scheduling/resource-governance infrastructure.

If parallel multi-index search does not materially help the measured scenarios, do not retain complexity merely because parallelism is possible.

### 6. Cancellation / supersession

The existing generation model may be extended so obsolete work is cancelled or superseded deeper in the active search path only where doing so prevents meaningful measured wasted work.

Do not broaden general Core/provider contracts unless a demonstrated M17 requirement makes the smaller solution insufficient.

## Performance targets and guardrails

Use the existing M16 physical-host harness and its `inputToFirstTextMilliseconds` boundary.

| Scenario class | M17 median target | Per-sample guardrail |
| --- | ---: | ---: |
| `ordinary-name`, `strong-prefix` | <= 50 ms | <= 100 ms |
| `one-character`, `two-character` | <= 150 ms | <= 250 ms |
| `broad-result` | <= 150 ms | <= 250 ms |
| `warm-repeated` | <= 100 ms | <= 150 ms |
| `fresh-process-first-search` | <= 125 ms | <= 150 ms |
| `rapid-typing` final input | <= 75 ms | <= 125 ms |
| `rapid-typing` prescribed burst | <= 600 ms | <= 700 ms |

The goal is a practical immediate-search experience, not exact Everything parity.

## Correctness constraints

M17 must preserve:

- literal case-insensitive indexed-name substring semantics;
- full candidate recall required by the existing ranker;
- current exact/prefix/token-prefix/substring relevance semantics;
- current location/path-depth/path-length/name/path/identity ordering semantics;
- current result limits and supported filters;
- correct deterministic merged ordering across configured filesystem indexes;
- opening the intended indexed result;
- the M15 source-neutral Core/FileSystem dependency direction;
- index integrity and existing durability/staging semantics.

The permanent one- and two-character late-exact regressions are mandatory. Add focused tests for compact-stream ordering, generation mismatch, affected mutation paths, bounded chunk updates, and any new recovery/rebuild-required behavior introduced by the implementation.

Do not weaken relevance or candidate recall to improve benchmark numbers.

## Footprint and lifecycle expectations

The M17-S sparse-label prototype is the reference scale, not an exact production byte target. Production storage should remain materially in the same bounded class rather than drifting toward the rejected dense-table representation.

Record on the representative physical-host corpus:

- source DB bytes;
- compact derived bytes and percentage growth;
- approximate bytes/posting or bytes/indexed-entry where useful;
- any stabilized runtime memory attributable to the structure;
- compact-state open/load cost where material;
- marginal direct-build cost of the production structure;
- focused mutation/write-amplification evidence for representative create/rename/delete or equivalent operations.

A material footprint/build regression relative to the M17-S direction requires explanation and may trigger a stop if it makes the bounded approach no longer proportionate. Do not optimize the full rebuild merely to improve these figures; that remains M17.5.

## Out of scope

- full index build/rebuild performance optimization or M17.5 work;
- production index-build parallelism unless a narrow measured need is unavoidable for the approved structure;
- a custom durable short-query file/store outside the existing SQLite/staging lifecycle;
- whole-list posting BLOB mutation as the production maintenance strategy;
- broad search/storage architecture replacement beyond the approved derived compact structure;
- ranking/relevance v2 (M18);
- continuous background maintenance or Windows Service work (M19/M20);
- generic scheduler/resource-governance framework;
- heterogeneous-source fan-out architecture beyond the current source-neutral boundary;
- unrelated Quick Search visual/UI polish;
- installer/package/release work.

## Implementation method

Resume M17 on the existing `codex/m17-search-performance` branch and PR #10 after integrating current `main` without history rewriting. Preserve useful correctness-safe M17 work already on that branch; do not resurrect the invalid bounded-`rowid` candidate strategy.

Use M17-S as design evidence, not copy-paste production code. The spike's dense intermediate, one-BLOB-per-list layout, numeric multiplier merge key, and 32-bit sparse-label representation are explicitly non-production details.

During implementation:

1. integrate current `main` into the existing M17 branch using a normal non-history-rewriting merge when needed;
2. implement the smallest production compact structure consistent with this amendment;
3. establish focused correctness and lifecycle tests before relying on performance numbers;
4. measure the short-query path on the physical corpus and iterate only on failing hot paths;
5. finish remaining broad-result and warm-repeated work already identified by M16/M17 evidence;
6. run the final representative campaign only on the final candidate.

Do not run the full 8-scenario campaign after every change.

## Acceptance criteria

M17 is ready for independent QA when:

- the final candidate meets every M16 median target and per-sample guardrail in one final 8-scenario x 3 physical-host campaign, unless an environment limitation requires user-owned execution of the unchanged harness;
- one- and two-character search uses the correctness-preserving compact derived path and no longer depends on seconds-scale delay or blocking;
- the compact path preserves full recall and ranking semantics, including the permanent late-exact regressions;
- build and existing explicit sync operations keep the compact structure consistent with authoritative state;
- stale/mismatched derived state cannot silently produce trusted incomplete results;
- production footprint, load cost, build contribution, and focused mutation cost are recorded and remain proportionate to the bounded M17-S direction;
- `broad-result` and `warm-repeated` meet their budgets;
- ordinary, fresh-process, and rapid-typing scenarios remain within their regression guardrails;
- focused correctness/lifecycle tests pass;
- affected Release builds pass;
- no M17.5, M18, M19/M20, generic scheduler, or broader architecture scope was silently absorbed.

## Stop conditions

Stop and record evidence instead of expanding M17 if meeting the amended contract requires any of the following:

- replacement of the overall search/storage architecture beyond the approved compact derived structure;
- a custom durable store or new privilege/service boundary;
- a broad migration/versioning framework;
- weakening index integrity, durability, protected-storage, or recovery guarantees;
- weakening candidate recall or ranking semantics;
- a general scheduler/resource-governance framework;
- M17.5 rebuild optimization as a prerequisite merely to make the short-query structure viable;
- M18 ranking/relevance redesign;
- a footprint, build-cost, or mutation-cost result showing the M17-S direction is no longer proportionate in production;
- inability to preserve current-user ranking semantics without making derived state dependent on an unsafe or unstable build identity;
- another material change outside the approved Quail 0.3 boundary.

A stop condition inside the 0.3 boundary is handled by the Quail 0.3 execution thread under the current execution-authority model; parent-roadmap escalation is required only for a release-boundary or cross-version decision.
