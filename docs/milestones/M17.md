# M17 — Search Engine Performance

## Status

**BLOCKED by roadmap stop condition. Do not merge PR #10.**

M17 implements the smallest evidence-based changes needed to remove the interactive-search bottlenecks measured by M16. It does not include full index build/rebuild performance, ranking/relevance redesign, continuous maintenance, or a general scheduling framework.

Post-candidate QA proved that the current storage/search model cannot yet satisfy the approved 1–2-character latency target with a correctness-preserving bounded read-path change. The roadmap now inserts M17-S, a bounded short-query search-structure spike, before M17 may resume. M17 itself is not broadened until that spike produces evidence and the roadmap explicitly approves the resulting contract change, if any.

## Goal

Make representative filesystem Quick Search effectively immediate by fixing the measured M16 short-query, broad-result, and relevant queue/Core hot paths while preserving correctness, ranking/relevance semantics, deterministic ordering, the M15 source-neutral boundary, and the established M16 benchmark methodology.

## Measured starting point

M16 established these physical-host medians:

- `ordinary-name`: 28.047 ms
- `strong-prefix`: 26.581 ms
- `broad-result`: 281.509 ms
- `one-character`: 3,006.749 ms
- `two-character`: 2,008.437 ms
- `warm-repeated`: 112.191 ms
- `fresh-process-first-search`: 90.089 ms
- `rapid-typing` final input: 57.456 ms
- `rapid-typing` prescribed burst: 529.727 ms

The current one/two-character UI path deliberately includes a one-second defer introduced as a temporary mitigation for the expensive underlying short-query search path. It is not a target UX policy. M17 should remove the need for that workaround by making the underlying path fast enough; merely shortening or deleting the timer without addressing the actual Core/search cost is not sufficient.

## Roadmap stop-condition evidence

The first M17 performance candidate met every M16 performance target, including approximately 40.9 ms for one-character and 43.4 ms for two-character queries, but post-candidate QA found that its bounded `rowid` candidate window could exclude later exact or prefix candidates before the unchanged ranker saw them. The candidate therefore violated M17's explicit recall/relevance constraint and is not acceptance evidence.

The unsafe short-query strategy and zero-delay policy were reverted, and permanent focused regression tests now cover the discovered one- and two-character exact-match cases.

On the correctness-safe existing model, a full exact-candidate lookup for a one-character query with no exact match measured about 1.46 seconds on the physical C: index. Existing FTS5 trigram search does not index terms shorter than three characters. The evidence therefore does not provide a credible small read-path route to the approved `<= 150 ms` median target while preserving full candidate recall.

This directly triggers the existing stop condition for a material persistent schema/index redesign or new durable short-query structure. Do not hide the problem behind another arbitrary bounded window or by weakening ranking/relevance semantics.

The approved M16 short-query target remains unchanged for now. M17-S will determine whether a bounded dedicated structure or another material but contained search/storage approach can meet latency, correctness, footprint, build/rebuild, and maintenance constraints. If not, the target or product behavior returns to roadmap review explicitly.

PR #10 remains open and blocked. Its safe regression tests, measurements, and correctness-preserving changes may remain useful if M17 is later resumed under an amended contract, but the PR must not be merged in its current state.

## Scope

M17 may change only the measured interactive-search path and the smallest adjacent behavior required to meet the M16 targets.

### 1. One- and two-character search

Investigate and optimize the current short-query path, including:

- the temporary one-second defer;
- the non-trigram candidate/search path used for names shorter than three characters;
- Core-search cost and unnecessary work before the first useful top results are available;
- obsolete short-query work when superseded by newer input, if avoiding that work materially improves the measured interaction.

The end state should not retain a large fixed delay merely to hide an expensive implementation.

Until M17-S completes and the roadmap explicitly amends this contract, do not introduce a new persistent short-query index, memory-resident replacement structure, or other material search/storage design inside M17.

### 2. Broad-result search

Reduce the measured `broad-result` latency, focusing on the measured queue wait and Core candidate retrieval/search cost.

Do not optimize mapping, result apply, source-status, icon work, or another stage unless current profiling shows that it has become material after an in-scope change.

### 3. Warm-repeated scheduling

Improve queue/scheduling behavior affecting `warm-repeated` only as far as required by the target and regression guardrails.

Do not introduce a generic scheduler framework.

### 4. Multi-index concurrency as a measured hypothesis

The current filesystem source searches configured indexes sequentially. M17 may evaluate bounded concurrent search of independent indexes if focused measurement shows a real latency benefit for the M16 scenarios.

Concurrency must follow `docs/concurrency-direction.md`:

- no thread-per-index/provider requirement;
- no unbounded task creation;
- no assumption that FileSystem owns all logical processors;
- preserve deterministic merged ordering and correctness;
- avoid speculative shared scheduling/resource-governance infrastructure.

If parallel multi-index search does not materially help the measured scenarios, do not retain complexity merely because parallelism is possible.

### 5. Cancellation / supersession

The existing generation model may be extended so obsolete work is cancelled or superseded deeper in the active search path only where doing so prevents meaningful measured wasted work.

Do not broaden general Core/provider contracts unless a demonstrated M17 requirement makes the smaller solution insufficient.

## Performance targets and guardrails

Use the existing M16 physical-host harness and its `inputToFirstTextMilliseconds` boundary.

| Scenario class | M17 median target | Per-sample guardrail |
| --- | ---: | ---: |
| `ordinary-name`, `strong-prefix` | <= 50 ms | <= 100 ms |
| `one-character`, `two-character` | <= 150 ms | <= 250 ms |
| `broad-result` | <= 150 ms | <= 250 ms |
| `warm-repeated` | <= 100 ms | <= 150 ms |
| `fresh-process-first-search` | <= 125 ms | <= 150 ms |
| `rapid-typing` final input | <= 75 ms | <= 125 ms |
| `rapid-typing` prescribed burst | <= 600 ms | <= 700 ms |

The goal is a practical immediate-search experience, not exact Everything parity.

## Correctness constraints

M17 must preserve:

- literal case-insensitive indexed-name substring search semantics;
- current result limit behavior and supported filters;
- current deterministic ranking/relevance behavior;
- correct merged ordering across configured filesystem indexes;
- opening the intended indexed result;
- the M15 source-neutral Core/FileSystem dependency direction;
- index integrity and existing build/sync semantics unless a small read-path-only change necessarily touches shared code.

Do not weaken relevance or candidate recall simply to improve benchmark numbers.

## Out of scope

- full index build/rebuild performance or M17.5 work;
- production index-build parallelism;
- material SQLite schema/storage redesign;
- a new persistent short-query index or other material short-query search/storage structure unless roadmap review explicitly approves it after M17-S;
- ranking/relevance v2 (M18);
- continuous maintenance or Windows Service work (M19/M20);
- generic scheduler/resource-governance framework;
- heterogeneous-source fan-out architecture beyond what the current source-neutral boundary already requires;
- new benchmark infrastructure when the existing M16 harness is sufficient;
- unrelated Quick Search visual/UI polish;
- installer/package/release work.

## Implementation method

Measure before changing a hot path.

During iteration:

1. establish the smallest focused benchmark that reproduces the changed failing scenario;
2. implement the smallest justified optimization;
3. rerun only the focused affected scenario(s);
4. stop iterating on a path once it meets the target unless another concrete regression remains.

Do not run the full 8-scenario campaign after every change.

Concurrency, cancellation, SQL strategy, candidate strategy, and queue changes are implementation choices to be selected from evidence, not pre-approved solutions.

## Acceptance criteria

M17 is ready for independent QA when:

- the final candidate meets all M16 median targets and per-sample guardrails in one final 8-scenario × 3 campaign on the intended physical-host corpus, unless an environment limitation requires user-owned execution of the unchanged canonical harness;
- normal filename/prefix search remains effectively immediate;
- one- and two-character searches no longer depend on seconds-scale delay or blocking;
- broad-result search no longer creates the measured clearly perceptible wait;
- `warm-repeated`, fresh-process, and rapid-typing regressions remain inside their budgets;
- focused correctness tests for changed search/candidate/scheduling behavior pass;
- Release builds for affected production projects pass;
- no ranking/relevance, build/rebuild, schema, maintenance, or architectural scope was silently absorbed.

## Verification

Follow `docs/verification-playbook.md`.

Expected verification shape:

- focused automated tests for changed SQL/candidate/coordinator/concurrency behavior;
- focused M16 benchmark scenarios during implementation;
- affected Release builds after the final implementation candidate;
- one final canonical M16 8×3 regression campaign, not repeated merely for confidence;
- short user-owned manual Quick Search smoke only if directly observable UX confirmation remains useful after automated performance evidence.

Do not repeat installer, Quail-Lab, packaging, M15 architecture campaigns, or other historical verification unless the implementation actually changes those boundaries or a concrete regression implicates them.

## Stop conditions

Stop and return to roadmap planning instead of expanding M17 if meeting the target requires any of the following:

- replacement of the overall search/storage architecture;
- a material persistent schema/index redesign or new durable short-query structure;
- material build/sync/index-lifecycle redesign;
- weakening index integrity, durability, privilege, or security guarantees;
- a general scheduler/resource-governance framework;
- M17.5 rebuild optimization;
- M18 ranking/relevance redesign;
- another material roadmap-level scope change.

The first M17 candidate has already triggered the short-query storage stop condition. M17 remains paused until M17-S completes and the roadmap explicitly decides whether to amend this contract, change the target/product behavior, or take another bounded path.

If a bounded optimization attempt fails to reach the target, preserve the measurements and explain the remaining bottleneck rather than hiding it behind a larger fixed UI defer.

## Completion boundary

The implementation-agent boundary is a clean branch plus PR containing the verified M17 implementation and durable performance evidence ready for independent QA.

Do not merge, delete branches, force-push, tag, publish a release, or begin M17.5 without the appropriate next approval/workflow step.
