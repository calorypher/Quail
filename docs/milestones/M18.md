# M18 — Ranking / Relevance v2

## Status

**ACTIVE — implementation contract approved on 2026-09-05.**

M18 is a bounded filesystem-search relevance milestone. It must improve top-N usefulness without sacrificing the latency envelope established by M16/M17 and without expanding into learned/personalized ranking or fuzzy matching.

## Goal

Make the intended filesystem result appear high enough that fast search is also useful search.

The milestone has two primary correctness goals:

1. fix the known candidate-recall failure where an over-limit candidate set inside the same text-match tier can hide a result that the final ranker would prefer because of location/path context;
2. improve deterministic ranking behavior for realistic duplicate and near-duplicate filename workflows while preserving useful visible/user-space results above internal/system-heavy noise where appropriate.

## Current known problem

For queries of three or more characters, the current FTS path retrieves a bounded candidate set before final ranking. Candidate expansion can query exact/prefix/token-prefix/substring classes separately, but each class remains bounded by the requested result limit. Therefore a better candidate inside the same text tier can still be omitted before the final comparator sees it.

M18 must fix that failure as a correctness property. Simply increasing an arbitrary oversampling constant is not sufficient unless evidence proves a bounded scheme is complete for the accepted ranking policy.

## Baseline before implementation

Before changing production ranking/search behavior, create a small deterministic relevance baseline using the current `main` behavior.

The baseline should include representative cases for:

- exact vs prefix vs token-prefix vs substring;
- an over-limit same-text-tier candidate set with the preferred location/path result deliberately late in candidate order;
- current-user visible, other visible/user-space, current-user internal/AppData, other internal, and system-heavy locations;
- common duplicate names such as `README.md`, `config.json`, or equivalent deterministic fixtures in multiple locations;
- identical names across multiple filesystem indexes;
- shallow vs deep paths;
- many duplicate or near-duplicate names;
- one- and two-character queries where the same product relevance policy applies.

Do not use private real filenames/paths in committed fixtures. Real local queries may be used as ignored exploratory evidence under `artifacts/m18/`.

Record simple, interpretable metrics over the deterministic set, preferably:

- top-1 success;
- top-5 success;
- mean reciprocal rank (MRR);
- explicit mandatory expected-order assertions for critical cases.

Do not build a general relevance-evaluation framework.

## Ranking policy

The existing ranking dimensions are the starting point, not an immutable implementation:

- location/visibility;
- text-match quality;
- path depth;
- path length;
- deterministic name/path/file-id tie-breakers.

M18 may refine the precedence or combine these dimensions differently if the deterministic relevance set demonstrates that the current lexicographic order is too rigid.

In particular, treat as a hypothesis rather than a requirement whether a current-user substring should always outrank an exact or prefix match in another normal visible location. Preserve the important distinction between ordinary visible/user-space results and internal/system-heavy noise.

Any scoring or comparator design must remain deterministic, explainable, and bounded. Avoid magic scalar weights unless their ordering properties are explicitly demonstrated by tests and the implementation remains easy to reason about.

## Candidate retrieval

The final ranker must receive enough information to preserve the accepted ranking semantics.

Allowed implementation directions include bounded query decomposition, ranking-aware candidate retrieval, or reuse of existing filesystem ranking metadata where that gives a demonstrably complete result for the accepted policy.

Do not assume the existing `compact-short-query-v3` representation must change. Prefer to reuse current derived state where practical.

If a correct M18 solution requires any of the following, stop and return with evidence before implementing the broader change:

- a new persistent ranking index or substantial new derived-state representation;
- a `compact-short-query-v3` format change;
- a material filesystem schema redesign;
- a broad search-architecture replacement.

The execution thread may then decide whether the required change remains a bounded 0.3 implementation detail or needs separate planning.

## Short-query consistency

One- and two-character search must follow the same product relevance policy as longer queries unless a concrete storage/performance constraint requires a documented exception.

The compact short-query path already separates location and text-match classes and applies static ordering. Reuse that structure where possible rather than replacing it.

Do not regress the accepted short-query recall, generation, mutation, or latency behavior from M17.

## Multi-index behavior

Multiple filesystem indexes must still produce one deterministic globally ranked result set.

A locally preferred result must not be lost merely because one index truncates candidates before the global merge.

Add deterministic multi-index coverage for identical or near-identical names in different volumes/locations where it helps prove the new candidate-recall property.

Do not introduce generalized cross-provider ranking; only the existing filesystem source is in scope.

## Representative relevance regression set

The durable deterministic suite should be small enough to understand and maintain. Prefer focused named cases over a large synthetic corpus.

Mandatory categories:

1. text quality ordering;
2. same-text-tier late preferred candidate;
3. visible vs internal/system-heavy;
4. duplicate exact names in different locations;
5. duplicate/near-duplicate names with depth/path distinctions;
6. multi-index merge;
7. short-query policy consistency;
8. deterministic tie-breaking.

A relevance change that improves aggregate metrics but breaks a mandatory case is not accepted without an explicit evidence-based contract change.

## Performance boundary

M18 changes production Search/ranking behavior, so the final candidate must preserve the accepted M16/M17 latency targets and per-sample guardrails.

Targets remain:

| Scenario | Median target | Per-sample guardrail |
| --- | ---: | ---: |
| ordinary-name | <= 50 ms | <= 100 ms |
| strong-prefix | <= 50 ms | <= 100 ms |
| broad-result | <= 150 ms | <= 250 ms |
| one-character | <= 150 ms | <= 250 ms |
| two-character | <= 150 ms | <= 250 ms |
| warm-repeated | <= 100 ms | <= 150 ms |
| fresh-process-first-search | <= 125 ms | <= 150 ms |
| rapid-typing final input | <= 75 ms | <= 125 ms |
| rapid-typing prescribed burst | <= 600 ms | <= 700 ms |

The M17 final accepted campaign remains the comparison baseline. In particular, the broad-result path has limited margin and must not become an unbounded full-rank/full-path scan over every match.

During implementation, use focused deterministic and micro/perf checks first. Do not repeatedly run the full physical campaign during iteration.

## Final performance verification

After the final correctness candidate is stable:

- run exactly one canonical M16 8-scenario x 3-repetition campaign using the existing harness and methodology;
- preserve raw evidence under `artifacts/m18/`;
- compare every scenario against the existing target and guardrail;
- do not relax a target merely to accept the ranking change.

If the final candidate misses an accepted target and the cause cannot be corrected inside the approved M18 scope, stop with evidence.

## Acceptance criteria

M18 passes only when all of the following are true:

- the known same-text-tier candidate-cutoff failure is deterministically reproduced on baseline and fixed in production;
- all mandatory relevance regression cases pass;
- deterministic top-1/top-5/MRR over the accepted fixture set improve against baseline overall, with no unexplained material regression;
- duplicate and near-duplicate filename workflows produce useful top-N ordering;
- one-/two-character and longer-query paths follow compatible relevance semantics or have a documented justified exception;
- multi-index merging preserves the intended global order;
- ordering is deterministic across repeated runs;
- no Search/ranking semantics are duplicated in App/CLI;
- the final canonical M16 8x3 campaign passes all existing targets and guardrails;
- a short manual Quick Search smoke confirms representative normal queries and opening the intended result;
- focused tests and affected Release builds pass;
- `git diff --check` passes.

## Evidence

Expected durable artifacts:

- `docs/milestones/M18-results.md`;
- a compact deterministic relevance baseline/results JSON such as `docs/milestones/M18-baseline.json`, or two small JSON files if separating before/after is materially clearer;
- only minimal benchmark/helper changes required to produce deterministic relevance evidence.

Ignored local evidence may live under:

- `artifacts/m18/`.

Do not commit private real-query text, usernames, profile paths, or other unnecessary host-specific data.

## Out of scope

Do not implement in M18:

- fuzzy matching or typo tolerance;
- interaction-history ranking;
- last-opened/frequently-opened boosts;
- recency/activity boosts;
- learned ranking;
- ML/LLM ranking;
- content search;
- generalized cross-provider ranking;
- query-language redesign;
- Full Search UI;
- M19/M20 maintenance/service work;
- new provider/plugin frameworks;
- unrelated indexing/build optimization;
- post-0.3 frontend/coordinator refactors.

These remain valid future product directions but must not be pulled into the deterministic 0.3 ranking baseline.

## Verification approach

Use the repository verification playbook and change-impact principle.

Expected sequence:

1. verify branch/worktree/main relationship;
2. read canonical sources and current ranking/search implementation;
3. record deterministic relevance baseline before production changes;
4. implement the smallest correctness-preserving candidate-recall/ranking change;
5. run focused relevance/search/multi-index/short-query tests;
6. run focused performance checks and iterate only on measured regressions;
7. run affected Release builds;
8. run one final canonical M16 8x3 physical campaign;
9. perform a short manual Quick Search smoke;
10. record durable results and prepare PR for independent QA.

Do not add extra full campaigns merely for confidence. If one campaign has an obvious infrastructure problem, preserve it as invalidated evidence, correct the environment once, and rerun once.

## Stop conditions

Stop and report evidence instead of broadening the milestone if:

- correctness requires a substantial new persistent ranking representation/schema change;
- `compact-short-query-v3` must materially change;
- the accepted M16/M17 latency targets would need to be weakened;
- fuzzy/history/recency/learned/ML ranking becomes necessary to satisfy the deterministic baseline;
- generalized cross-source/provider ranking becomes necessary;
- a broad search architecture replacement appears necessary;
- unrelated local changes or canonical-source conflicts appear;
- the final representative physical campaign remains invalid after the allowed infrastructure correction.

## Completion boundary

M18 ends at a verified branch and PR ready for independent QA with durable relevance and performance evidence.

Do not merge, delete the branch, tag, publish a release, or perform other gated operations without explicit user approval after independent QA.
