# M19 — Continuous Maintenance Boundary Spike

## Status

**READY FOR INDEPENDENT QA — architecture approved in the Quail 0.3 execution thread on 2026-09-06; implementation remains deferred to M20.**

M19 selects the smallest safe privileged/background boundary for automatic
maintenance of configured local NTFS indexes. It does not implement production
continuous maintenance. The milestone stops at an explicit architecture
decision gate before M20.

## Goal

Resolve enough real Windows, NTFS, privilege, storage, lifecycle, concurrency,
and installer unknowns to give M20 a closed implementation contract for keeping
healthy filesystem indexes current without routine manual Refresh or routine
UAC prompts.

## Baseline to verify

- App Build/Rebuild/Refresh launches the current `Quail.exe` through `runas` as
  a narrow elevated `AdminIndexWorker`.
- The worker revalidates the local fixed NTFS volume, stable volume identity,
  user catalog entry, deterministic database path, protected storage, and the
  per-volume operation lock before mutation.
- Managed databases are protected under `%PROGRAMDATA%\Quail\Indexes`; ordinary
  users receive read/execute while Administrators and SYSTEM write.
- The catalog is versioned JSON under the current user's
  `%LOCALAPPDATA%\Quail\indexes.json` and includes `EnabledForSearch`.
- USN synchronization is one-shot catch-up from a persistent checkpoint.
- Protected mutations use WAL with `synchronous=FULL`, then checkpoint and
  return the quiescent database to DELETE journal mode so ordinary read-only
  search needs no writable sidecars.

Current code and runtime evidence override this baseline if they disagree.

## Candidate set

Evaluate only:

1. an unelevated user-session maintainer as a control candidate;
2. a narrowly pre-authorized elevated background task/helper;
3. a Windows Service with the smallest justified responsibility.

Do not assume a service is required. Reject or select candidates using evidence
covering privilege feasibility, automatic start and catch-up, idle behavior,
configuration ownership, control/IPC, concurrent readers and writer, integrity
and recovery, installer impact, attack surface, implementation complexity, and
expected M20 maintenance burden.

## Investigation scope

### Privilege and identity

Determine actual requirements for raw local-volume access,
`FSCTL_QUERY_USN_JOURNAL`, `FSCTL_READ_USN_JOURNAL`, protected ProgramData
writes, checkpoint/index mutation, and Build/Rebuild. If a service remains
credible, evaluate LocalSystem as the simple compatible baseline and at most one
materially credible lower-privilege identity.

### Configuration ownership

Resolve the LocalAppData catalog boundary without allowing a SYSTEM process to
use SYSTEM's profile as user configuration. Define the minimum coherent split
between machine maintenance targets and protected database identity on one side,
and per-user search/UI preferences including `EnabledForSearch` on the other.
Do not create a generic multi-user configuration framework.

### Privileged command and control

If a persistent privileged component needs App control, define the minimum
local IPC shape. Record allowed callers and ACL, identity assumptions, bounded
commands, request validation, privileged revalidation of volume/configuration,
status responses, failure behavior, and whether ordinary search uses IPC.
Unelevated callers must never supply an arbitrary privileged filesystem path.

### USN and recovery lifecycle

Define persistent checkpoint, ordinary incremental consumption, no-change idle,
process/service and Windows restart, catch-up after downtime, sleep/resume where
needed, journal identity/range validation, gap/error handling, explicit
`RebuildRequired`, and automatic recovery only where correctness is unambiguous.
Do not add file history or deleted-item retention.

### Idle and concurrency

Investigate blocking or bounded USN waiting before accepting periodic polling.
Demonstrate representative compatibility between unelevated Quick Search readers
and the privileged Sync writer, including WAL/checkpoint/protected-storage
behavior. Do not redesign search or introduce speculative shared scheduling.

### Existing worker and installer

Choose explicitly whether `AdminIndexWorker` is replaced, retained, or narrowed
to bootstrap/recovery. Record only the registration identity, startup type,
uninstall, initial privileged setup, and genuinely necessary upgrade/config
implications needed by M20/M21. Do not build an updater or deployment framework.

## Focused threat analysis

Cover concrete paths involving unelevated influence over privileged paths,
mount-point or arbitrary-path injection, volume mismatch, tampered user
configuration, local IPC authorization, protected-storage reparse points,
service executable/config permissions, writable binary/config paths, SQLite
sidecars and locks, concurrent writers, stale client data, and silent trust in an
index after USN continuity loss. Reuse existing protected-storage defenses where
they already close a risk. Additional mechanisms require a concrete risk, an
explanation of why the simpler defense is insufficient, and their ongoing test
and maintenance cost.

## Evidence and deliverables

- compare all three bounded candidates and explicitly reject disqualified ones;
- obtain focused Quail-Lab evidence for material privilege, protected-storage,
  idle/wait, restart/catch-up, and Search+Sync questions where prior evidence is
  insufficient;
- retain machine-specific raw evidence only under ignored `artifacts/m19/`;
- record factual findings and the recommended architecture in
  `docs/milestones/M19-results.md`;
- include a proposed closed M20 contract in the results for review, but do not
  create or promote `docs/milestones/M20.md` before the decision gate.

## Acceptance criteria

Before the architecture decision gate, M19 must:

- resolve whether unelevated-only maintenance is viable and whether a service or
  task is required;
- verify material privilege assumptions;
- define configuration ownership and the minimum privileged trust boundary;
- define the intended control/IPC shape, restart/catch-up behavior, continuity
  and rebuild-required semantics, and practical no-change idle strategy;
- demonstrate representative concurrent Search+Sync viability or identify a
  blocker;
- decide the future of `AdminIndexWorker` and record installer implications;
- complete focused threat analysis;
- select one recommended architecture and list remaining uncertainties;
- provide a draft closed M20 boundary without implementing it.

No production continuous-maintenance implementation is required.

## Verification approach

Use the repository verification playbook and canonical Quail-Lab procedures.
Prefer current implementation inspection, focused existing tests, and the
smallest real runtime probes that resolve independent OS unknowns. Do not repeat
unaffected installer, GUI, performance, or release campaigns. Before the gate,
inspect the diff, run `git diff --check`, commit and push the coherent Phase-1
investigation, and report exact branch and HEAD.

## Stop conditions

Stop rather than expanding scope if:

- the safe design needs a substantially broader privileged service;
- a credible privilege-escalation or protected-storage integrity issue remains;
- correct continuity handling requires a major storage redesign;
- multi-user support requires a generalized system architecture;
- generic IPC, provider, background-agent, updater, or service-management
  frameworks appear necessary;
- required lab evidence needs a destructive journal operation without explicit
  approval;
- canonical sources materially conflict; or
- the direction changes the approved 0.3 boundary or major cross-version
  architecture.

Do not restore, delete, rename, or overwrite Hyper-V checkpoints; do not attach
physical disks; do not perform destructive experiments on the physical host.

## Decision gate

When evidence supports one recommendation, stop. Do not start M20, create
production service/task/IPC code, create `docs/milestones/M20.md`, or open the
final M19 PR. Present the recommendation for explicit in-version architecture
approval. After approval, the same branch/session may perform the short M19
closure, create the canonical M20 contract, finalize roadmap state and bounded
verification, and open the PR for independent QA.
