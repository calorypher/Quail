M20 implements the architecture selected by M19. It does not reopen the

boundary without triggering a stop condition.

## Goal

Keep configured healthy local NTFS indexes current without manual Refresh or
routine UAC while preserving direct unelevated search, durable checkpoint
integrity, and fail-closed behavior whenever USN continuity cannot be proven.

## Approved architecture

```text
unelevated Quail App
  -> per-user LocalAppData search preferences / EnabledForSearch
  -> direct read-only SQLite search and health reads
  -> runas narrow AdminIndexWorker only for exceptional administration
       -> bounded administrator-only local control

LocalSystem Quail maintenance service
  -> protected ProgramData machine maintenance targets and health
  -> stable NTFS volume identity validation
  -> cancellable per-volume USN wait and restart/resume catch-up
  -> sole IndexStore Build/Rebuild/Sync writer
  -> protected ProgramData databases and locks
```

The service owns all index mutation after this boundary is activated. Ordinary
Search never depends on the service IPC path and continues to open complete,
compatible protected databases directly in read-only mode.

## In scope

- one dedicated, non-interactive Windows Service executable running as
  LocalSystem and managed through the Service Control Manager;
- protected, versioned machine maintenance-target and health persistence under
  `%PROGRAMDATA%\Quail`;
- strict separation between machine maintenance authority and the existing
  per-user `%LOCALAPPDATA%\Quail\indexes.json` search preferences;
- a bounded administrator-only local control channel for register-and-build,
  explicit rebuild, unregister, and operation status;
- narrowing `AdminIndexWorker` to the UAC-authorized bootstrap, recovery, and
  control client, with no independent mutation implementation;
- one cancellable asynchronous USN wait per configured ready volume;
- startup, service-restart, Windows-restart, and sleep/resume revalidation and
  catch-up from the durable checkpoint;
- bounded retry for transient volume or journal unavailability;
- reuse of the current transactional Sync and staged Build/Rebuild publication
  paths with the service as sole writer;
- explicit machine-readable health covering healthy, catching up, unavailable,
  retrying, error, and rebuild required;
- focused installer service registration, start, controlled replacement, stop,
  recovery, and uninstall behavior;
- affected automated tests, Quail-Lab runtime/security/lifecycle evidence, and
  independent adversarial review of the final privileged boundary.

## Configuration ownership

### Machine maintenance targets

The service owns a protected, versioned and atomically replaced document under
`%PROGRAMDATA%\Quail`. Targets are identified by stable volume identity. A mount
point may be stored for display or discovery but is never trusted as identity or
as a client-selected privileged path.

Only administrator-authorized control requests may add or remove targets. The
service independently discovers the current fixed NTFS volume, validates its
identity, derives the managed database path, validates protected storage, and
acquires the existing per-volume operation lock before mutation.

### Per-user search preferences

The existing `%LOCALAPPDATA%\Quail\indexes.json` remains authoritative only for
that user's search choices, including `EnabledForSearch`. The LocalSystem service
must not read configuration from its own LocalAppData profile and must never use
an unelevated user's catalog as maintenance authority.

Disabling an index for one user does not unregister machine maintenance.
Unregistering a target is a separate administrator-authorized operation. Generic
multi-user ownership or impersonation is not part of M20.

## Privileged control contract

Use the smallest practical local mechanism: an administrator-only named pipe or
an equivalently narrower Service Control Manager mechanism if implementation
proves it sufficient.

The control boundary must:

- allow only LocalSystem and Builtin Administrators through an explicit ACL;
- reject remote clients and fail closed when caller authorization cannot be
  established;
- use a versioned, length-bounded request/response format with deadlines;
- accept only register-and-build, explicit rebuild, unregister without deleting
  index data, and bounded operation-status requests;
- never accept an arbitrary filesystem path, database path, executable, command
  line, shell operation, plugin, or generic RPC method;
- make the service independently reload protected configuration, rediscover and
  revalidate the volume, derive all protected paths, and acquire the existing
  lock before acting;
- reject malformed, oversized, unauthorized, stale, duplicate, volume-mismatch,
  or unknown requests without changing configuration or index state;
- return only bounded accepted, busy, succeeded, rebuild-required, unavailable,
  rejected, or error state plus an operation ID and bounded diagnostic.

The implementation may choose between holding a connection for short operations
and returning an operation ID for later status. Long Build/Rebuild work must not
create an unbounded connection or response contract.

## Continuous maintenance lifecycle

For each configured ready volume:

1. Discover the fixed NTFS volume and revalidate stable identity.
2. Open and validate the protected index metadata and persisted checkpoint.
3. Query the current USN journal and prove the complete continuity contract
   below before trusting the index, catching up, or entering idle wait.
4. Consume available records through the existing bounded transactional Sync
   batches, persisting each batch and its checkpoint atomically.
5. Checkpoint WAL and return the database to its quiescent read-only-compatible
   state. Keep no SQLite connection or transaction open while idle.
6. Issue one cancellable overlapped `FSCTL_READ_USN_JOURNAL` request with nonzero
   `BytesToWaitFor` from the committed frontier.
7. Treat completion as a change signal. Cancel/close the wait as required, then
   rerun authoritative journal/checkpoint validation and Sync from the persisted
   database checkpoint rather than trusting an uncommitted wait buffer.
8. On service stop, target removal, or volume loss, cancel outstanding I/O and
   await loop completion without abandoning a SQLite transaction.

On service or Windows restart and on sleep/resume, rediscover the volume and
re-query journal identity, range, and frontier before consuming or waiting.
Healthy downtime is ordinary catch-up and does not require a rescan.

Per-volume waits use asynchronous I/O rather than permanent dedicated threads.
Mutation concurrency and retry/backoff are small and bounded so maintenance does
not oversubscribe CPU/I/O or starve interactive search. M20 must not introduce a
generic scheduler framework.

## Checkpoint and continuity contract

The persisted checkpoint invariant is: every journal record before persisted
`next_usn` has been applied in the same committed SQLite history.

Before the index can be trusted, caught up, searched as current, or placed into
idle wait, all of these conditions must hold:

- the persisted journal ID matches the current journal ID;
- persisted `next_usn` is at or after every required readable lower bound,
  including current `FirstUsn` and `LowestValidUsn` as applicable;
- persisted `next_usn` is not greater than the current journal `NextUsn`;
- the complete range from persisted `next_usn` through current `NextUsn` is
  readable and sufficient to prove unambiguous catch-up;
- the checkpoint, schema, derived state, volume identity, and protected database
  metadata are mutually consistent.

`next_usn == NextUsn` is the valid no-change case and may enter the cancellable
wait. `next_usn < NextUsn` is valid only when the entire required intervening
range is readable and must catch up before idle.

Any journal-ID mismatch, checkpoint below the readable range, checkpoint greater
than current `NextUsn`, impossible ordering, malformed value, incompatible or
missing required state, or other inconsistent relationship fails closed to a
stable `RebuildRequired` reason. The service must not wait for the journal to
reach a future checkpoint, advance or repair the checkpoint speculatively, or
leave the index trusted for Search.

A failed Sync transaction leaves the checkpoint unchanged. Already committed
earlier batches remain authoritative and can be resumed when validation succeeds.
A temporarily absent volume or retryable open/query failure publishes unavailable
or retrying health, preserves the last committed checkpoint, and retries with
bounded backoff or on rediscovery; it is not itself proof of continuity loss.

M20 never automatically performs a full rebuild after continuity loss. Recovery
requires an explicit administrator-authorized Rebuild using the existing staging
and atomic publication path. The previous database is replaced only after the
new database and checkpoint are complete and valid.

## Reader/writer and storage semantics

- The service is the only index writer.
- Mutations remain serialized per protected volume with the existing lock.
- Quick Search opens complete compatible databases read-only and uses a stable
  SQLite snapshot.
- Protected mutation retains `synchronous=FULL`, transactional namespace and
  checkpoint updates, WAL during the operation, bounded checkpoint/finalization,
  and return to DELETE journal mode when quiescent.
- A search already in progress may finish against its original snapshot; a later
  search observes the committed state.
- A bounded busy/finalization failure must publish failure or unavailable health;
  it is not permission to kill readers, introduce another writer, or trust a
  partially finalized index.

## Health behavior

Service-owned protected health must be sufficient for the existing App and later
M21 UI without exposing privileged internals. At minimum it records stable target
identity, current state, last successful checkpoint/refresh time, operation ID,
and a bounded stable reason where action is needed.

Only `Complete` and compatible indexes selected by the user's search preferences
are active search sources. `RebuildRequired`, incomplete, or incompatible indexes
fail closed out of active Search. Transient unavailable, retrying, or catching-up
maintenance health does not by itself disable an otherwise complete compatible
read-only index; explicit `RebuildRequired` health remains a hard invalidation.
Ordinary health reads require no privileged IPC.

## Installer contract

- Install one dedicated service executable beneath the canonical
  `C:\Program Files\Quail` payload.
- Register a uniquely named LocalSystem service with a fixed quoted binary path,
  normal Automatic (not Delayed Start), non-interactive behavior, and bounded SCM restart
  recovery.
- Validate that ordinary users cannot modify the executable, its directory,
  protected machine configuration, or service configuration.
- Start the service after successful installation; stop it before replacing its
  executable during a supported update.
- Stop and remove service registration during uninstall before payload removal.
- Preserve protected indexes, maintenance configuration, and per-user catalogs
  on uninstall unless a separate explicit data-removal action is approved.
- Do not add updater, download, remote administration, alternate install-root,
  or broad legacy migration responsibilities.

The existing Inno Setup remains the packaging baseline.

## Focused security requirements

M20 must fail closed against:

- unauthorized, unelevated, malformed, oversized, stale, duplicate, and remote
  control requests;
- arbitrary-path, mount-point, database-destination, command-line, and executable
  injection;
- stable-volume-identity mismatch or volume substitution;
- LocalAppData tampering used as attempted privileged authority;
- named-pipe squatting or permissive endpoint ACLs;
- writable service binaries, directories, service configuration, machine target
  configuration, or health state;
- ProgramData junction, symlink, reparse, SQLite sidecar, staging, previous, or
  lock redirection;
- multiple or bypass writers and client-supplied checkpoint state;
- partial SQLite publication and silent trust after continuity loss.

Reuse the existing `PrivilegedIndexStorage` defenses and deterministic path
derivation. The service provides no shell, updater, network client/server, remote
API, arbitrary command execution, plugin loading, or user impersonation.

The final stable implementation requires independent adversarial review focused
on service replacement/control, authorization, protected storage, journal and
checkpoint invariants, crash behavior, and concurrent reader/writer failure
modes. Blockers must be fixed and focused re-review plus runtime verification
completed before merge recommendation.

## Out of scope

- M21 Settings redesign and launch-on-startup UI;
- generic multi-user ownership or user impersonation;
- file history or deleted-item retention;
- non-NTFS, removable, network, cloud, mail, browser, or other source work;
- generic provider, service, IPC, lifecycle, worker-pool, or scheduler frameworks;
- updater, download, package-authenticity, remote administration, or remote API;
- dynamic plugins or public extension SDKs;

- automatic full rebuild after continuity loss;
- search, ranking, index-format, or storage redesign unless a concrete in-scope

## Acceptance criteria

- Install, start, stop, restart, recovery, update-stop, uninstall, and reboot
  lifecycle works on Quail-Lab with finite waits and complete cleanup.
- A real standard-user context cannot query/read the required journal or mutate
  protected storage; LocalSystem can perform required journal and storage work.
- CREATE, RENAME, MOVE, and DELETE become searchable without manual Refresh or
  routine UAC.
- Service restart, Windows restart, ordinary downtime, and sleep/resume catch up
  exactly from the last committed checkpoint when continuity is valid.
- No-change waiting wakes promptly for a change, cancels promptly on stop or
  reconfiguration, holds no SQLite transaction, and has practically zero idle CPU
  without aggressive polling.
- Journal-ID mismatch, checkpoint below the readable range, checkpoint above
  current `NextUsn`, and other impossible or inconsistent checkpoint/journal
  fixtures deterministically enter `RebuildRequired`, do not wait indefinitely,
  and cannot leave the index trusted for Search.
- Transient volume/journal unavailability preserves the committed checkpoint and
  follows bounded retry/rediscovery behavior without false continuity loss.
- Explicit Rebuild recovers through staging and atomic publication; no continuity
  failure triggers an automatic full rebuild.
- Representative Quick Search overlaps service Sync without corruption,
  incorrect snapshot behavior, or an unavailable protected database.
- App/user catalog and service/machine configuration authority remain separate.
- Unauthorized, remote, arbitrary-path, volume-mismatch, reparse,
  writable-binary/config, SQLite sidecar, malformed framing, and concurrent-writer
  probes fail closed.
- Affected focused/full tests and required Release builds pass, and durable lab
  evidence records exact binaries, identities, lifecycle, cleanup, and outcomes.
- Independent adversarial review and independent project QA recommend merge.

## Stop conditions

Stop rather than broaden M20 if implementation requires:

- a service with shell, updater, network, arbitrary-path, or generic privileged
  responsibilities;
- permissive local control, ordinary-user privileged commands, or user
  impersonation/multi-user architecture;
- another index writer, weakened ProgramData protection, or speculative
  checkpoint repair;
- aggressive polling, routine UAC for freshness, or automatic rebuild after
  continuity loss;
- generic IPC, provider, service-management, background-agent, worker-pool, or
  scheduling frameworks;
- a major index/storage redesign or change to the approved Quail 0.3 boundary;
- destructive journal manipulation without explicit approval;
- acceptance of an unresolved privilege-escalation, service-replacement,
  protected-storage, continuity, or data-integrity risk.
