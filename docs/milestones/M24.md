## M24-A goal

Prove that the post-M23 0.3 candidate can be installed over the normal released
0.2 deployment, start with Windows, maintain a configured NTFS index without
manual Refresh or Rebuild, and recover trustworthy searchable state after a
normal Windows restart.

## Scope

- establish candidate `0.3.0` product metadata through the existing canonical
  version source and installer build path;
- close M23 as merged in the roadmap and record M24 as active;
- build and inspect the exact framework-dependent installer payload;
- test one representative released `0.2.0` to `0.3.0` transition on Quail-Lab,
  preserving user-owned state and using only a supported safe recovery path if
  old index state cannot be reused;
- validate installation, the LocalSystem `QuailMaintenance` service, normal
  start/stop/start, uninstall preservation, and the owned startup registration;
- prove create, rename, move, delete, and restart/catch-up behavior on the
  disposable Quail-Lab data volume without manual Refresh or Rebuild;
- record reproducible evidence in `M24-A-results.md` while reusing unchanged
  M20 and M21 evidence.

## Out of scope

- M24-B performance, relevance, memory, benchmark, or resource work;
- M24-C signing, certificate, SAC policy, final security review, RC freeze,
  release notes, release, tag, or GitHub Release work;
- installer replacement, updater, generalized migration support, new UI,
  source, filter, or provider work;
- broad compatibility for arbitrary historical development builds.

## Acceptance criteria

1. M23 is recorded as merged and M24 as active.
2. Candidate version identity is consistently `0.3.0` / `0.3.0.0` without a
   tag or release.
3. The exact installer, payload, Release build, and automated regression have
   durable evidence.
4. The normal released `0.2.0` to candidate `0.3.0` transition does not
   silently lose user-owned data and fails safely if state is incompatible.
5. Installer, service, startup, uninstall, continuous maintenance, and restart
   behavior pass at representative Quail-Lab scope.
6. No M24-A release-blocking integration, deployment, or lifecycle defect
   remains on the candidate branch.

## Verification strategy

Use the canonical `prepare-milestone.ps1` and `build-installer.ps1` paths.
Run broad Release build/test evidence once for the candidate metadata, focused
installer-contract tests, payload inspection, and a disposable Quail-Lab
installed-state lifecycle campaign. Reuse M20/M21 security and startup evidence
when the current change does not affect those boundaries. Keep visual sign-in
checks user-owned when the available VM session cannot prove them directly.

## Stop conditions

Stop and report rather than broaden scope if released user-owned data appears
at risk, a safe transition needs general migration architecture, M20 needs a
major redesign, signing or a security-policy change is required, a required tool
is unavailable, checkpoint restoration/deletion/overwrite would be needed,
unrelated changes appear, or the issue belongs to M24-B or M24-C.

## Completion boundary

M24-A ends with a verified branch and pull request ready for independent QA. It
does not merge, delete branches, create tags, create a GitHub Release, or
publish release assets.
