# Quail 0.3.1 Release Notes

## Status

**Published as `v0.3.1` on 2026-09-23.** The immutable tagged/package source
is `4e870df444b03ea73cc429a57e24bd98e26f4cbe`; the final hotfix merge on `main`
is `304e1699a36a35d3bd6c288d94cc474cf19306a7`. The published installer is
`Quail-0.3.1-Setup.exe` (10,248,326 bytes, SHA-256
`90FFFC9BC9086B0A319C5311F262048C623DA1D2965C92208BAA5CA242135D1D`).
Quail 0.3.0 remains withdrawn. Its `v0.3.0` tag, source commit, and historical
installer asset are unchanged. Do not install 0.3.0.

## What was wrong in 0.3.0

On a system where a watched NTFS volume and Quail's protected state both live
on C:, the maintenance service could sustain roughly one logical CPU of work
and continuous disk writes while the index was nominally current. The visible
symptoms included persistent SQLite WAL/SHM churn and advancing checkpoints and
health timestamps without user filesystem activity.

The confirmed cause was a frontier mismatch. `IndexStore.Sync` returned and
persisted the last journal frontier it had authoritatively applied. The sync's
own SQLite finalization and the service's subsequent health publication then
created newer USN records on C:. The service began its wait from the older
applied frontier, immediately observed those Quail-owned records, performed
another sync and publication, and generated the next wake source. Separate
volume maintenance did not exhibit the loop because its protected state was
written on C: while its journal wait was on the other volume.

The first authorized physical recovery later exposed the same feedback at an
earlier boundary during a large catch-up. One `IndexStore.Sync` queried a
finite journal frontier, but its native read loop continued toward the moving
live tail. Applying each batch wrote the protected C: database and generated
newer C: journal records for that same invocation to consume. The sync retained
one logical processor, produced extremely high logical journal-read counters,
never returned to the post-Sync gap logic, and prevented the queued Rebuild
from reaching its build phase.

## The 0.3.1 fix

After each authoritative sync and health publication, same-volume maintenance
inspects the bounded journal gap while it still owns the protected writer
boundary. It advances only an in-memory wait frontier when every record in that
gap is an exact Quail-owned protected-state artifact. The durable checkpoint in
SQLite remains the last authoritatively applied frontier.

If the gap contains any external or unknown record after steady-state has been
reached, the service starts a fixed 60-second coalescing window before the next
authoritative sync; later changes do not reset or extend that deadline. Startup
catch-up is not coalesced. If journal identity or readable
continuity cannot be proved, or a record is malformed or unsupported, the
existing fail-closed `RebuildRequired` semantics apply. Transient inspection
failures enter the existing bounded retry path without advancing the durable
checkpoint. A change arriving after inspection but before the wait is not lost:
the wait begins at the inspected cursor and completes immediately on that newer
record. A crash or restart resumes from the older durable applied checkpoint
and catches up normally.

Every Sync now captures `journal.NextUsn` before reading and processes the
half-open range from its durable checkpoint to that fixed frontier. If a native
1 MiB result buffer crosses the frontier, only records below it are applied and
the durable checkpoint advances exactly to the captured value. Records created
during the read or batch application—whether external or Quail-owned—remain
for the post-Sync inspection and, when necessary, the next authoritative Sync.
The initial-build journal handoff and post-Sync inspection use the same bounded
semantics. This removes the inner self-chasing loop without polling, debounce,
a batch-count limit, or weakened durability.

### External-churn coalescing

The first physical acceptance observation found a different scheduling
amplification under ordinary system-volume churn. Read-only attribution of USN
range `[2392064272, 2392246080)` found 1,274 records: 153 external or
unresolved records (12.0%) distributed across the whole sample, followed by
1,121 Quail-owned database/WAL/SHM or maintenance-health records (88.0%). An
external record in the post-Sync gap previously caused an immediate next Sync,
which wrote protected state and health and repeated that amplification.

Continuous steady-state maintenance now coalesces those external/unknown wakes
in one fixed 60-second window. The deadline is established by the first wake
and is never reset by later changes. The durable checkpoint remains unchanged
while waiting and advances only with the next successful bounded Sync. The
wait uses target-loop cancellation, so Stop and explicit Rebuild do not wait
for the window. Crash or restart during the wait leaves the unapplied USN range
for immediate startup catch-up. Search remains direct read-only SQLite; this
hotfix adds no RAM-visible overlay.

The first physical-host acceptance run did not reproduce the withdrawn
self-wake loop, but it exposed a second bounded blocker in the existing
short-query derived index. Repeated normal insert/delete churn can exhaust one
local midpoint rank-label gap. Leaf insertion had local recovery; directory
insertion in the same gap instead marked the complete filesystem index
`RebuildRequired` with `rank-label-gap-exhausted`.

Quail 0.3.1 now treats any typed rank-label exhaustion, for both leaf and
directory insertions, as recoverable derived-state work. The authoritative
namespace finishes the journal batch, including later creates and deletes, and
the short-query state is regenerated once from the final namespace inside the
same SQLite transaction. There is no production local leaf-relabel fallback.
Namespace, derived generation, and the durable checkpoint become visible
together only after a successful commit. Rollback restores all of them
together, and unrelated structural failures remain fail-closed. Existing
indexes with fragmented labels are repaired by this path; increasing initial
spacing alone was not used.

On Quail-Lab, the exact directory exhaustion scenario committed and remained
healthy/trusted. A deterministic 500,002-record regeneration completed in
3.086 seconds wall time and 3.094 seconds CPU time, with correct Search results,
no final database growth, and no repeated regeneration. This is a bounded O(N)
fallback, not the normal incremental path.

This remains a narrow patch. It does not change search ranking, the Quail 0.4
goal, the protected sole-writer boundary, direct read-only SQLite search,
durability, or the protected-storage ACL/reparse model.

## Regression and release gates

Quail 0.3.1 adds focused coverage for the same-volume owned gap, an external
change in the Sync-to-wait window, USN v2/v3 file identifiers, continuity loss,
separate-volume behavior, and the immutable durable checkpoint. It also covers
captured finite Sync frontiers, self-generated writes during batch application,
native buffers crossing the frontier, later-iteration catch-up, split-batch
checkpoint exactness, and rollback before an uncommitted cursor. It also covers
directory and leaf rank-gap exhaustion, more than twelve insertions into one
gap, a later DELETE after fallback activation, rename/move parent labels,
rollback/replay, generation consistency, deterministic equivalence to a clean
derived build, and Search correctness.

Release acceptance now measures service CPU, working set, private bytes,
read/write bytes, read/write operation counts, handles, threads, checkpoint
progression, and WAL/SHM lifecycle. The physical-host gate requires:

- normal installation with `QuailMaintenance` running;
- a complete and healthy C: target with `%ProgramData%\Quail` on C:;
- several minutes of idle observation without monotonic Quail-owned write
  workload or autonomous WAL/SHM churn;
- searchable CREATE, correct metadata update, RENAME, MOVE, and DELETE on C:;
- a return to quiescent idle;
- Windows restart, downtime catch-up, and a second quiescent observation;
- a registered D: target as the separate-volume control where available.

Bounded before/after counter evidence is required. Normal filesystem activity
means the acceptance criterion is not absolute zero bytes per second; it is the
absence of the continuous Quail-owned self-sustaining workload seen in 0.3.0.

The final Quail-Lab coalescing run recorded three C: commits at 53.127 s,
113.531 s, and 173.404 s under controlled churn (60.404 s and 59.873 s
between commits). Its marker was not searchable immediately or after five
seconds and became searchable after approximately 59 seconds. WAL and SHM
appeared in one short sample group only. A queued canonical Rebuild issued with
about 55 seconds left in a coalescing window reached build start in 502.638 ms.
In a separate lifecycle check, Stop completed in 268.3 ms, startup made the
pending marker searchable in 1.351 s, and D: CREATE/DELETE converged in
60.482 s and 60.070 s while both targets remained healthy/trusted.

## Installation and compatibility

The release version is `0.3.1`; assembly and file versions are `0.3.1.0`.
The installer supports bounded upgrades from released 0.2.0 and withdrawn
0.3.0 at the canonical `C:\Program Files\Quail` path. Other historical
development builds remain uninstall-first. Existing ProgramData and
LocalAppData are preserved.

Final package acceptance must also verify the installed service policy, not
only binary provenance: `QuailMaintenance` must be `AUTO_START`, restart after
5,000 ms and 30,000 ms, reset its failure count after 86,400 seconds, and have
`FAILURE_ACTIONS_ON_NONCRASH_FAILURES` enabled. These are the intended
production settings; temporary physical-host containment settings used while
the previous looping candidate was installed are not release defaults.

The final Quail-Lab package smoke installed the candidate normally and verified
`DisplayVersion` `0.3.1`, ProductVersion
`0.3.1+4e870df444b03ea73cc429a57e24bd98e26f4cbe`, FileVersion `0.3.1.0`,
`LocalSystem`, `AUTO_START`, both configured restart delays, the 86,400-second
reset period, and recovery on non-crash failures. The packaged service stopped
in 321.834 ms, reached healthy/trusted C: and D: 1,321.986 ms after start, and
proved the fixed coalescing behavior with a C: marker that was absent from
Search at five seconds and converged in 51,530.706 ms.

Quail remains unsigned. Windows SmartScreen or Smart App Control may warn about
or block the installer or binaries. Disabling Windows security features is not
a supported workaround.

## Final physical-host acceptance

The final package was installed normally on the physical PC that reproduced the
0.3.0 defect. It matched final provenance: installer SHA-256
`90fffc9bc9086b0a319c5311f262048c623da1d2965c92208baa5ca242135d1d`, service
SHA-256 `D5696C1ED17DCD87DD56E707AC76F5600FDB7C56DFE255EC658594E9AADFBE9F`,
ProductVersion `0.3.1+4e870df444b03ea73cc429a57e24bd98e26f4cbe`, and
FileVersion `0.3.1.0`. Fresh normal product builds completed for C: (532,670
records, 68.25 s) and D: (24,390 records, 1.96 s); both were complete, healthy,
and trusted.

The pre-reboot same-volume idle gates used 1.48% and 0.90% of one logical CPU,
with logical writes of 229 KB/s and 120 KB/s. WAL/SHM occurred in short bursts,
not continuously. C: CREATE, metadata update, RENAME, MOVE, and DELETE all
converged through Search in bounded windows of about 26--61 seconds.

A marker absent from Search before a normal Windows reboot became searchable
after startup without a manual operation; the C: checkpoint advanced from
2,471,499,424 to 2,474,250,648. Marker DELETE converged in 49.323 s. The final
post-reboot five-minute observation consisted of five finite coalesced batches
about 60--71 seconds apart: WAL/SHM appeared in 18/301 samples and were absent
at the endpoint. One larger finite batch raised logical process counters and
memory temporarily, then released memory and did not restart the service or
make either target untrusted. It was not the continuous one-core, multi-MB/s
self-generated workload withdrawn in 0.3.0. Final D: CREATE/DELETE converged
in 47.331 s and 60.141 s; both targets remained healthy/trusted.

Logical process I/O counters are not physical SSD throughput. Independent final
QA remains required before publication.
